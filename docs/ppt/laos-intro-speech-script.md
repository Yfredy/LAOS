## P1 封面

**页面要点**：laos · Linux AgentOS ｜ Linux 内核的 Agent 治理层——内核强制的能力边界，而不是提示词恳求 ｜ 版本与测试锚点。

**建议时长**：1 分钟

**逐字讲稿**：

> 大家好，今天给大家介绍一个我个人研制的项目——laos，全称 Linux AgentOS。先用一句话说清它是什么：**laos 是 Linux 内核的 Agent 治理层，它解决的是"内核强制的能力边界"，而不是"提示词恳求"**。这句话里有两个关键词，一个是"治理层"——它不是重写一个操作系统，恰恰相反，它一行内核代码都不改；另一个是"强制"——它给 AI Agent 的每一次工具调用装上的是系统调用级别的闸门，不是写在提示词里的"请不要做危险的事"。这个项目从今年 9 月 4 号第一个版本开始，到今天已经迭代到 v0.39.0——39 个语义化版本，主库 1146 项测试全绿，代码 51 个模块纯 Python 标准库实现。接下来 25 分钟，我会讲清楚四件事：它要解决什么问题、它的核心机制长什么样、它和市面上的 AgentOS 有什么不同、以及它的工程质量是如何被 1158 项测试和 116 份调研文档兜住的。

**过渡句**：要理解 laos 为什么存在，先看今天 AI Agent 面临的一个真实困境。

**问答预案**：
- Q：为什么叫 laos？A：L-A-O-S，Linux Agent OS 的缩写；对外品牌名 nanoLAOS，技术名/CLI 名保持 laos 不变。
- Q：一个人做的项目？A：是，从设计、实现、测试到调研文档全流程单人完成，所以工程纪律（TDD/SemVer/发版链）是被刻意制度化的。

## P2 问题

**页面要点**：Agent 拿着用户的全部权限在裸奔；一条 `rm -rf` 删光家目录；恶意 MCP 工具外发剪贴板/通知；提示词是恳求不是强制；缺的是操作系统。

**建议时长**：2 分钟

**逐字讲稿**：

> 先看问题。今天的 AI Agent——不管是 Claude Code、Cursor 还是各种自动化框架——本质上都运行在用户态，**拿着用户的全部权限在裸奔**。为什么这么说？因为一个能帮你干活的 Agent，必须能执行 shell 命令、读写文件、访问网络。于是一条构造巧妙的指令或者一个恶意的 MCP 工具，就能 `rm -rf` 删光你的家目录，就能把你的剪贴板和通知内容发到服务器上。更根本的问题在于防御手段：今天业界的标准做法是把"不要做危险的事"写进 System Prompt。但 System Prompt 是什么？是一段**文本**。文本可以被覆盖、被绕过、被注入攻击——prompt injection 就是 Agent 世界的提权攻击。所以我说，**提示词是恳求，不是强制**。缺的从来不是更聪明的模型——模型再聪明，也可能被一段网页里的隐藏文字骗过去；缺的是操作系统：能力边界、资源配额、操作审计、不可逆记账、进程隔离。这些概念操作系统五十年前就解决了，问题是：怎么把它们带给 Agent 这个新物种。

**过渡句**：laos 的答案是一句话——不改内核一行代码，把 Linux 变成 Agent 的操作系统。这就是我们的命题。

**问答预案**：
- Q：这和容器/沙箱有什么区别？A：沙箱只是隔离，回答" Agent 能碰什么"；laos 回答的是更细的四件事——每一次调用过闸、每一分配额记账、每一笔操作审计、每一个高危动作人审。沙箱是 laos 强制层三件套之一，不是全部。
- Q：模型自己变强了还需要这个吗？A：安全边界不依赖模型自觉，这是工程常识——就像再可靠的司机也需要刹车，而不是只靠驾照考试。

## P3 命题

**页面要点**：Linux AgentOS = Linux kernel + Agent + MCP；不改内核一行代码，复用四件内核遗产（namespace/cgroup/seccomp BPF/Landlock）；laosd 是薄内核，只做语义层。

**建议时长**：2 分钟

**逐字讲稿**：

> laos 的命题可以写成一个公式：**Linux AgentOS = Linux kernel + Agent + MCP**。注意这个等式的主客关系——基座是 Linux 内核，Agent 和 MCP 是内核之上的新负载和新设备，laos 不是给 Agent"装"一个操作系统，而是把内核治理延伸到用户态。这里有一个关键判断：我们不需要重写调度器、不需要新的进程模型，因为 Linux 内核已经给了我们四件强制原语：**namespace 做隔离视图、cgroup 做资源上限、seccomp BPF 做系统调用白名单、Landlock 做路径沙箱**——这四件套都是内核级的强制执行，不是公约。laosd，也就是 laos 的守护进程，把自己定位成"薄内核"：它只做语义层——能力、调度、审计、记账这四件事，然后把所有的"设备"留给 MCP 驱动。所以你看这个架构的克制之处：重的东西全在内核，已经在监狱里跑了几十年；语义的东西在用户态，可以快速迭代。这是 laos 全部设计的出发点。

**过渡句**：这个"薄内核"具体怎么薄、又怎么硬？看这张类比表。

**问答预案**：
- Q：为什么不做成真内核模块？A：两个原因。一是迭代速度——用户态治理可以天级发版（我们 39 个版本只用了 40 天）；二是部署现实——目标场景大量在 Android/proot 环境，拿不到 root。等理念验证完，L3 层可以再讨论 libOS 化。
- Q：零内核改动会不会限死能力？A：我们用的是 Linux 既有原语的组合，landlock+seccomp 对工具调用场景完全够用；真不够的原语（比如精确到文件偏移的沙箱）才需要考虑内核侧，目前没撞到。

## P4 一张类比表

**页面要点**：Linux↔laos 五行对照——进程↔Agent（PCB/能力集/预算）、系统调用↔MCP tool call、设备驱动↔MCP Server、内核↔laosd 薄内核、insmod↔kernel.load_driver。

**建议时长**：2 分钟

**逐字讲稿**：

> 这张表是理解 laos 的钥匙，我逐行讲。第一行，**进程对应 Agent**——在 laos 里 Agent 不是一段脚本，是一个有身份、有能力集、有预算额度的受管实体，就像进程有 PCB。第二行，**系统调用对应 MCP tool call**——这是全片最核心的一行：每一次工具调用，在 laos 里不是一次普通的 HTTP 请求，是一次要过闸的"系统调用"。第三行，**设备驱动对应 MCP Server**——麦克风、ASR、屏幕操控，这些都是"设备"，MCP Server 就是它们的驱动。第四行，内核对应 laosd 薄内核，第五行最有意思：**insmod 对应 kernel.load_driver**——任何符合 MCP 协议的服务器，可以像加载内核模块一样被外挂进 laos，一行命令。这个类比不是修辞，是设计约束：它意味着 laos 里的每一个概念，你都可以在操作系统教科书里找到对应物，都可以用五十年的系统智慧来推理。举个小例子说明它的解释力：当我们说"驱动子进程要限 CPU 和内存"，资深的系统工程师立刻明白这是 cgroup 的事，不需要我解释为什么要资源隔离。

**过渡句**：类比表讲的是"像"，下一页讲"硬"——每一次工具调用具体怎么过闸。

**问答预案**：
- Q：MCP 之外的自定义协议能接吗？A：可以写适配驱动，但治理面只认 MCP——这是刻意的，协议收敛才能让闸门链通用。
- Q：Agent 的"PCB"具体存什么？A：能力集、当前任务作用域、预算余额、审计流水号、污点标记——和 PCB 存寄存器/页表/打开文件是同一思想。

## P5 syscall 闸门链（核心卖点）

**页面要点**：八环链——能力表→task_scope→schema 校验→EDQUOT 预算→FleetLedger 不可逆计价→Jev 预审→确认横幅→派发+全量审计。每一次调用都过闸、都落账。

**建议时长**：3 分钟（全片核心页，可超时）

**逐字讲稿**：

> 这是全片的核心页，讲 laos 最硬的一个机制：**syscall 闸门链**。任何一次工具调用，从 Agent 嘴里说出来到真正执行，要过八道闸，我按顺序讲，每一道都对应一种真实攻击。第一环，**能力表**——这个 Agent 有没有 screen.* 这个能力域？没有，直接拒，对应 Linux 的权限位。第二环，**task_scope**——就算有 screen 能力，任务作用域限定你只能操作白名单里的 App、只能访问某个路径前缀、只能在某个时间窗内活动；越界即拒。第三环，**schema 校验**——参数不合法直接拒，这是 EINVAL 语义。第四环，**EDQUOT 预算**——每个 Agent 有配额，配额耗尽即拒，对应磁盘配额思想。第五环是最有特色的，**FleetLedger 不可逆计价**——先扣账、后派发：发一条消息、删一个文件、花一笔钱，这些都是不可逆操作，执行前先把"风险分"扣掉，账上不够，操作就不被执行。第六环，**Jev 预审**，一个可选的判断层，回答"这件事值不值得做"。第七环，**确认横幅**——高危操作必须人审。第八环，派发，并且**全量审计**：每一次调用都留痕，事后可以完整回放"谁在何时用掉了什么权限"。给大家一个具体例子：Agent 想点击屏幕上的一个按钮，但目标 App 不在白名单里——第二环就拒了，adb 命令根本不会发出去，设备上什么都没发生。这八环的意义在于：**安全不依赖任何单点的智能，它是一套制度**。

**过渡句**：制度需要强制执行的人。laos 的"法警"是内核级强制层三件套。

**问答预案**：
- Q：八环全过性能不是爆炸？A：链上全是纯内存检查和一次 JSON 校验，微秒级；贵的是驱动执行本身。我们用 1158 项测试兜住行为，其中专门有时延用例。
- Q：Jev 是什么？A：一个判断层模型，用三原语做快问快答，第 9 页专门讲，这里先记住它是 opt-in 的、有诚实教训的。
- Q：和 OPA/策略引擎的区别？A：OPA 是"算完了告诉你违规了"；laos 是"不过闸就不派发"，且不可逆操作带预扣账——策略执行（PEP）和风险定价的合体。

## P6 强制层三件套

**页面要点**：seccomp BPF 进程级 syscall 白名单；cgroup v2 驱动子进程 CPU/内存上限；eBPF profiler + CoW 行为画像与执行隔离。

**建议时长**：1.5 分钟

**逐字讲稿**：

> 闸门链管的是"语义层"的决定，但任何熟悉系统的人都会问：**如果驱动子进程本身不听话呢？**这就是强制层三件套要回答的。第一件，**seccomp BPF**——每个驱动子进程在启动时被打包一个系统调用白名单，比如 drv_screen 只允许 exec adb 和写 socket，它想 fork 一个 curl 外传数据，内核直接杀掉进程。真拦截，不是约定。第二件，**cgroup v2**——每个驱动子进程有独立的 CPU 和内存上限，一个驱动陷入死循环或者内存泄漏，拖不垮宿主。第三件，**eBPF profiler 加写时复制**——我们从行为侧给驱动做画像，同时上下文分支用 CoW 隔离，Agent 在分支上试错不影响主线。这三件套全是内核既有能力，laos 做的是把它们编排成"驱动治理"的默认姿态。一句话总结：**语义层靠制度，执行层靠内核**。

**过渡句**：制度有了，法警有了，接下来看 laos 管着哪些"设备"。

**问答预案**：
- Q：seccomp 白名单写错了驱动起不来怎么办？A：启动期有 smoke 测试，白名单是 per-driver 声明式配置，改配置不改代码；失败时驱动以 degraded 模式上报而不是静默。
- Q：Windows/macOS 上这套还有吗？A：强制层三件套是 Linux 专属，这是 laos 的部署前提；跨平台场景（比如 macOS Seatbelt）在调研里有对标记录，属远期。

## P7 驱动即设备

**页面要点**：17 个内建驱动全景（mic/ear/screen/apps/notify/comms/battery/events/npu/audio/genie/fs/proc/sys/rec/clef/evolve）；外挂路线：kernel.load_driver 把任意 MCP 服务器 insmod 成内核驱动，遥测必须关。

**建议时长**：2 分钟

**逐字讲稿**：

> laos 现在有 **17 个驱动**，按器官分三类。听觉类：drv_mic 负责录音——注意，录音只由显式 syscall 触发；drv_ear 负责转写和音频评估；drv_rec 负责回放。手机操控类：drv_screen 通过 adb 做点击/输入/截屏，drv_apps 管应用列表和启停，drv_notify 管通知，drv_comms 管通信录和短信——这一整类回应的是"Agent 操作手机"的场景。系统类：drv_fs、drv_proc、drv_sys 提供文件、进程和系统状态的只读或受控视图，drv_npu 对接端侧 NPU，drv_audio 是后来加的音频专用驱动，还有 drv_clef、drv_genie、drv_evolve 分别对应密钥管理、代码进化和元认知实验。这里必须强调一个治理事实：**所有这些驱动都是受闸门治理的**——screen.* 要过 App 白名单，fs.* 要过路径前缀，没有例外。另一条路线是外挂：任何符合 MCP 协议的第三方服务器，可以用 kernel.load_driver 一行"insmod"进来——我们评估过社区的 mobile-mcp，路线可行，但前提是遥测必须关，这是红线。

**过渡句**：驱动里最有讲头的是听觉管线——它是 laos 隐私哲学的完整演示，就是这个四段漏斗。

**问答预案**：
- Q：17 个驱动會不會太多？A：每个驱动对应一类真实"设备"，且都过同一套闸门链——这正是"驱动即设备"的意思，多不是问题，不治理才是。
- Q：第三方 MCP 服务器安全怎么保证？A：外挂驱动默认低能力+低预算起步，先过闸跑一段，审计正常再按需提权——和 Linux 里新硬件的信任建立一个逻辑。

## P8 听觉管线 · 四段漏斗（隐私哲学演示）

**页面要点**：①常驻检测（VAD/PCEN，µW 级，不落盘）→②触发捕获（环形缓冲/唤醒词）→③即时蒸馏（SenseVoice 本地 ASR+情感）→④即焚（TTL）。红线：显式 syscall 触发/LAOS_REC=0 全局禁录/每次调用审计/ASR 全本地。

**建议时长**：3 分钟

**逐字讲稿**：

> 这一页是 laos 隐私哲学的完整演示，我建议放慢速度。场景设定：一个全天候在线的听觉 Agent，怎么做到"随时待命"又不变成一个偷录音的窃听器？答案是四段漏斗。第一段，**常驻检测**——一个软件 VAD 能量门一直开着，但它不落盘、不留缓存，只回答一个问题："现在有没有人声？"没声，什么都没有。第二段，**触发捕获**——有声了，环形缓冲开始记，同时唤醒词模型判断"是不是在叫我"。第三段，**即时蒸馏**——确认要处理，SenseVoice 本地转写、情绪分析，**只把文本和标签送进记忆系统**。第四段，**即焚**——原始音频按 TTL 删除，默认 6 小时，不留。注意这个设计的本质：**音频必须落盘才能送 ASR，但原始音频在系统里活不过 TTL**；进记忆的是蒸馏产物，不是声音本身。配合四条红线：录音只由显式 syscall 触发；LAOS_REC=0 环境变量一票否决全局禁录；每次 mic 调用落审计；ASR 全本地，一个字节都不出设备。前不久我拆解了阶跃刚发布的 STEPX Neo 智能体手机，它的六麦阵列加低功耗音频芯片把这个漏斗做进了硬件；而 Apple Watch 的 S12 芯片被验证过同构路线——说明这不是我一个人的偏执，是行业的收敛方向。区别在于：laos 用软件能量门在没有专用芯片的 Android 环境里，把同一套隐私账算平了。

**过渡句**：漏斗解决"耳朵"的问题，但 Agent 还需要"判断力"——这就是 Jev 层，以及它最值得讲的一个教训。

**问答预案**：
- Q：即焚了用户想回味上周的对话怎么办？A：回味的是日记文本，不是音频——这是刻意取舍：隐私和便利冲突时隐私优先。想要音频留存的场景，可以把 TTL 设长，但那要过单独同意门。
- Q：VAD 误触发怎么办？A：能量门+滞回+最短段过滤，误触发的代价是"多跑一次 ASR"，不是"多录一段音"——失败方向是安全的。
- Q：PCEN 是什么？A：按信道能量归一化，比裸能量门抗噪，轻量版已在实验分支，主库用能量+滞回先跑通链路。

## P9 Jev 判断层 · 快问快答

**页面要点**：三判型（Noul 是非/Choice 2-255 选项/Score 2-10 级）；四闸门（高危预审/记忆过滤/压缩选择/技能质量）；诚实教训：rule 后端 accuracy 0.519、高置信桶错误率 33% → AUTOGATE 禁配 rule 后端。

**建议时长**：2 分钟

**逐字讲稿**：

> 闸门链的第六环留了一个位置给"判断"——这件事该不该做、值不值得做、可不可逆。这个角色叫 Jev。它的设计有一个反直觉的点：**不生成文本，只回答结构化问题**。三种判型：Noul 回答是非，Choice 在 2 到 255 个选项里选，Score 打 2 到 10 级。为什么这样设计？因为判断要的是结论和置信度，不是一段可能跑题的解释——并行求值下，加题几乎不增延迟。它挂在四个闸门上：高危操作预审、记忆写入过滤、上下文压缩选择、技能质量评估。但这页最重要的内容是右下角这个**诚实教训**：我们实测过 rule 后端——一个本地规则模型——校准精度 accuracy 只有 0.519，更糟的是高置信桶的错误率高达 33%——它越自信越离谱。所以 laos 立了一条规矩：**AUTOGATE 禁配 rule 后端，校准先于自动化**。一个会把"低质量判断"自动放行的系统，比没有判断层更危险。这个数据我们是第三方复现口径，不是厂商宣称值——顺带说，这也是整个项目的气质：**宁可记一个难看数字，不要一个漂亮故事**。

**过渡句**：这套判断和治理不是拍脑袋设计的——背后是 19,792 篇论文和 3,724 个开源项目。

**问答预案**：
- Q：0.519 是什么概念？A：约等于抛硬币。高置信桶 33% 错误率意味着"它说非常确定的时候，三分之一是错的"——这就是必须人审或更强后端的原因。
- Q：Jev 现在用哪个后端？A：默认 none→RuleBackend 零依赖兜底；云端和端侧 ONNX 后端 opt-in。全部过同一接口，换后端不改治理面。

## P10 研究语料（不是拍脑袋设计）

**页面要点**：双会议全量遍历 19,792 篇（Interspeech 5,507 + ICASSP 14,285）；OSS 普查 3,724 仓库；采纳总纲逐条映射（已落地/推荐/不做）。

**建议时长**：2 分钟

**逐字讲稿**：

> laos 的每一个设计决定都有出处，这一页讲家底。第一，**论文语料**：我们把语音领域两大顶会 Interspeech 和 ICASSP 从 2021 到 2026 的论文做了全量遍历——Interspeech 5,507 篇，ICASSP 14,285 篇，合计 19,792 篇，元数据 100% 覆盖。第二，**开源普查**：3,724 个 GitHub 仓库，按 topic 切片去噪。第三，也是最重要的，**采纳总账**：每一条调研都落成三条之一——已落地、推荐待做、明确不做；"不做"的也写清理由。到今天，调研文档积累了 116 份。举两个例子说明这套家底怎么用：Speaker 分离为什么用 7 带谱质心做到达顺序聚类？因为调研发现所有要做"身份"的方案都撞 PIPL 敏感个人信息红线，于是我们选了会话内无身份语义的那条路。JAEC 回声消除为什么只放在驱动侧可选位？因为它的许可证是 CC BY-NC，禁商用——这种硬门槛不试不知道，试过就必须记账。**不是拍脑袋设计，是 19,792 篇论文加 3,724 个仓库给的底气。**

**过渡句**：光有论文不够，能复现的论文我们全部复现——这是 71 项测试的复现隔离区。

**问答预案**：
- Q：19,792 篇都读了？A：元数据和摘要全量入库，按主题切片筛出相关子集精读；全量覆盖保证"不会有漏网的瞎打"。
- Q：调研文档写来干嘛，能当饭吃？A：两个用途：对外是"design by evidence"的证明；对内是跨会话记忆——我这 40 天做了 39 个版本，没有这套文档我记不住自己两周前为什么这么决定。

## P11 复现隔离区（六来源 71 测试）

**页面要点**：BS.1770-4 响度（−23.00 LUFS ±0.1）｜FxLMS 主动降噪（>20dB）｜说话人朝向论文全管线（冒烟 holdout 56.5°）｜PhaseCoder 麦位编码（对齐官方 JAX）｜Pipecat 帧管道｜unique_lock 语义。方法论：TDD、零新依赖、论文数字不作断言、偏差全记档。

**建议时长**：2 分钟

**逐字讲稿**：

> 这一页讲 laos 最"笨"也最真的部分：**论文复现隔离区**。调研发现一篇有用的论文怎么办？我们的做法是进 Repro 隔离区，用测试把它复现出来，跑通了才谈落地。现在已经复现了六个来源、71 项测试。举三个：第一，**BS.1770-4 响度计量**——这是广播级标准，我们的实现在 R128 校准点上是 −23.00 LUFS，误差 ±0.1，这个数字是和行业标准对过表的。第二，**FxLMS 主动降噪**——一个经典自适应滤波算法，纯 Python 实现降噪量超过 20 分贝。第三，**说话人头部朝向估计**——复现了一篇论文的完整管线，在冒烟测试集上 holdout 精度 56.5 度。注意这三个数字的策略：**论文里写的数字我们不当断言，自己跑出来的才记**；跑不动的——比如原论文 4 万个样本我们只跑得起百样本冒烟——偏差全记档，等比缩距并写明。还有 PhaseCoder 那个更典型：为了验证麦位编码实现，我们逐行对齐了官方 JAX 源码，跨实现 diff 为零。这套方法论的纪律就四句话：TDD、零新依赖、论文数字不作断言、偏差全记档。

**过渡句**：最后讲这套东西怎么管理自己——版本治理。

**问答预案**：
- Q：56.5 度是不是很差？A：是冒烟 holdout，目的是"管线真的在学"而不是刷指标；原论文全量数据我们算力不够，这点在记档里写明了。
- Q：为什么复现区要隔离？A：复现代码常有实验依赖，隔离保证主库"纯标准库"承诺不破；采纳的再按裁决搬进主库。

## P12 版本治理与路线

**页面要点**：v0.1.0→v0.39.0 语义化版本+Keep a Changelog+GitHub Release；一个完整需求波次=一次 MINOR；合规红线（EU AI Act 职场情绪识别禁令/PIPL 声纹单独同意）；Roadmap。

**建议时长**：1.5 分钟

**逐字讲稿**：

> 最后一页，讲 laos 怎么管理自己。版本治理：**语义化版本加 Keep a Changelog 加 GitHub Release 页**——从 9 月 4 日第一个版本到今天，39 个 MINOR，每个版本有 tag、有 Release、有归档；纪律是"一个完整需求波次等于一次 MINOR"，不允许把半成品发上去。合规红线单独列：EU AI Act 对职场和教育场景的情绪识别有禁令——所以 laos 的情绪分析能力有场景限制说明；PIPL 把声纹列为敏感个人信息，需要单独同意——所以 laos 不建跨会话声纹库，这是红线不是功能欠缺。路线图三件事：drv_screen 的多轮真机验收、外挂驱动的概念验证、以及响度模块合入主库后的更多论文复现。最后用一句话收尾：**Agent 需要的不是更强的模型，是一个会说"不"的内核**——模型的聪明是概率，治理的边界才是确定性。laos 就是用 Linux 五十年的确定性强制度，去约束 Agent 时代概率性的不确定。我的介绍就到这里，谢谢大家。

**过渡句**：（进入问答）

**问答预案**：
- Q：项目最大的风险？A：单人项目的持续性风险——缓解是文档化：116 份调研+48 份计划+发版链全自动，换个贡献者看 ONBOARDING 能直接上手。
- Q：会开源/商业化吗？A：仓库在 GitHub 公开（Yfredy/LAOS）；治理内核本身开源，商业空间在驱动生态和合规服务——但那是后话。
- Q：和 Anthropic 的 containment、AIOS 论文什么关系？A：它們是我调研归档里的印证链——学术线（AIOS/MemGPT）、商业线（STEPX Neo 刚发布的 AgentOS 手机）、安全线（containment）都指向同一个结论：Agent 需要操作系统级治理。laos 是把这个结论做成可运行原型。
