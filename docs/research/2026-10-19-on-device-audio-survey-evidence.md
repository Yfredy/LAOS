## 1. 范围合同

### 1.1 主题与核心问题
- 主题：**端侧音频智能**（on-device / edge audio intelligence）——在资源受限设备上完成采集、前处理、推理与响应的音频模型与系统。
- Q1：「端」分哪几档硬件？各档的三本预算账（mW / ms / MB）是多少？
- Q2：三类任务（音频事件识别 AED / 声学情感 SER / 增益控制 AGC）在端侧各落到什么规模与精度？
- Q3：端侧音频真正的瓶颈是**模型体积、算力，还是信号前处理与常驻功耗**？
- Q4：NAS / 蒸馏 / 量化 / 二值化 / 专用硅这五条降本路线各换来什么、代价是什么？
- Q5：2026 年的新边界在哪——开放词表与小型音频语言模型能否真正落在端侧？

### 1.2 时间窗与读者
- 窗：2017-01-01 至 2026-10-19；重点 2022–2026。
- 读者：端侧音频工程师与 laos/nanoLAOS 技术评审；默认读者懂 Python 与嵌入式部署，不默认懂音频领域。
- 交付物：综述正文 + 本证据附录 + HTML 阅读版；不交付 benchmark 重跑与硬件实测。

### 1.3 纳入标准
至少满足一条：①给出参数量 / 算力 / 延迟 / 功耗并在真实或明确硬件上测量；②给出端侧 runtime 或量化导出证据；③给出常驻（always-on）场景的能耗或自适应证据；④给出端侧音频的隐私或系统设计结论。

### 1.4 排除标准
纯云端大模型（无端侧路径）、纯音乐生成、纯 ASR（不涉及端侧约束）、纯视觉、只有营销口径的产品稿。与端侧无关的通用音频分类方法（不报任何资源数字）亦排除。

### 1.5 这篇综述不写什么
**不写"如何在某个具体芯片上移植模型"的操作手册**——那是 runbook 而非综述；不重跑任何 benchmark；不做采购建议。凡涉及硬件档位的功耗数字，一律**引用本仓既有的 `always-on-recording/hardware-power.md` 与三个领域表的表格核实口径，不另起一套、不重算**（本仓既有约定：功耗数字直接引用，不另起一套）。

## 4. 单篇卡片

编号与正文 §3 的 `纳入 Sxx` 一一对应，不重排。六字段固定：问题 / 方法 / 数据 / 指标与条件 / 局限 / 对话。数字一律带数据集·指标·硬件条件；未给出即写"未给出"，不估算。

### [S01] Oído: Open-Vocabulary Speech Recognition on a $5 Microcontroller without a Neural Accelerator
- 问题：低成本 MCU 上的语音识别实际上被限制在关键词检测或固定命令表内，开放词表 ASR 被认为不可能。
- 方法：推理引擎 Oído，在 **ESP32-S3**（240 MHz 双核 Xtensa LX7、512 KB SRAM、8 MB PSRAM、16 MB flash、**无神经网络加速器**）上运行 **13M 参数 Conformer-CTC**：int8 权重 + 逐帧动态 int8 激活 + int8 注意力，全部落在该芯片的 SIMD 指令上；调度围绕 flash 与 PSRAM 带宽设计。另带片上 1.3M 参数语言模型与 transducer 头两个变体。
- 数据：LibriSpeech test-clean / test-other；另有真实噪声与混响条件。
- 指标与条件：端上算术达 WER **3.70% / 8.23%**（与全精度相差 0.12 点内）；加片上 LM 后 **3.33% / 7.15%**；transducer 头 **2.99% / 6.67%**；int4 变体可装进 **8.3 MB**。同芯片上比厂商识别器少 **2.3–2.8×** 错误，也优于笔记本上全精度的 Whisper tiny.en 与 Moonshine tiny。实板测得固件运行速度为 **1.97× 时长**（即约 2 倍慢于实时）。
- 局限：2× 慢于实时意味着**不能做流式实时转写**，只适合"说完再转"或离线批量；英文单语；ESP32-S3 单平台，未验证其他 MCU；1.97× 是实板测得，非仿真。
- 对话：与 [S02] Samsone 构成"端侧能跑多大模型"的两端——本条证明 **13M 的 Conformer 能进无 NPU 的 $5 MCU**，但代价是放弃实时；与 [S03] 同指一个方向：**瓶颈不在模型算子**。

### [S02] Samsone: A Family of Open Small Audio Language Models for On-Device Inference
- 问题：大音频语言模型动辄数十亿参数，而隐私与低延迟需求要求能在端侧执行的**小型音频语言模型（SALM）**。
- 方法：Samsone 系列，核心 **Samsone-134M**，并给出 **99M** 与 **356M** 两个缩放点以研究 SALM 的 scaling law；训练数据全部公开；发布训练代码、权重、移动端优化 checkpoint，以及一个开源 Android 应用演示实时端侧推理。
- 数据：未在本卡片核实层面取得（摘要口径）。
- 指标与条件：摘要自述 134M 在该尺寸级上取得 SOTA，且"与数量级更大的模型竞争力相当"。**具体基准数值未核实，本综述不引用**。
- 局限：摘要口径，未读全文，基准数字未核实；134M 在 MCU 档（<1 MB SRAM 级）仍不可用，其"端侧"实指手机/移动 SoC 档；未给出端侧实测延迟与功耗。
- 对话：与 [S01] 一起标记 2026 年的新边界——**端侧音频从"关键词检测"走到了"开放词表 + 语言模型"**；与 [S17] Tiny-Align 同属"把语言模型能力搬到端上"的一族，但本条是音频原生的。

### [S03] Sub-mW Keyword Spotting on an MCU: Analog Binary Feature Extraction and Binary Neural Networks
- 问题：KWS 是常驻负载，电池寿命被"持续运行"严重拖累；而既往优化几乎全部集中在模型本身。
- 方法：**模拟二值特征提取** + **二值神经网络（BNN）**，用模拟前端替换数字前处理。
- 数据：Speech Commands Dataset。
- 指标与条件：数据采集与前处理所需能量降低 **29×**，其占整系统能耗的份额从**主导性的 85% 降到 16%**。
- 局限：2022 年工作；模拟前端需定制电路，第三方 App 拿不到；任务仅为 KWS；未给出整系统绝对功耗（只给比例与倍数）。
- 对话：**本综述最重要的一条反直觉证据**——端侧音频的能耗大头在**前处理与采集**，不在模型。它与 [S06]（把 MFCC 到推理整条流水线一起评测）、[S05]（指出 MACs 是糟糕的延迟代理）共同构成"别只盯着模型"的论证链。也与本仓 AGC 侧的 8.62 µW 模拟前端 AGC 同向。

### [S04] MicroNets: Neural Network Architectures for Deploying TinyML Applications on Commodity Microcontrollers
- 问题：MCU 上的 DNN 推理受内存、延迟、能量三重约束，需要 NAS 自动设计满足约束的模型；而 NAS 的延迟/能量模型一直是难点。
- 方法：发现 MCU 模型搜索空间的一个性质——**在均匀先验下，模型延迟与算子数（op count）近似线性**；据此用可微分 NAS（DNAS）以 **op count 作为延迟的可行代理**搜索低内存、低算子数的模型。
- 数据：MCU 上的 TinyML 应用（含音频类）。
- 指标与条件：产出 MicroNet 模型族，在 MCU 内存/延迟/能量约束下取得当时可用的精度。**具体数值未核实**。
- 局限：2020 年工作，工艺与工具链已迭代；op count 作为延迟代理是**近似**，[S05] 明确指出这类粗代理会导致预测不准；未给出单一音频任务的独立数字。
- 对话：与 [S05] 构成 `方法→代价` 的承接——本条确立了"用便宜代理做 NAS"的范式，[S05] 量化了这种代理的误差并提出用时钟周期替代。

### [S05] InstMeter: An Instruction-Level Method to Predict Energy and Latency of DL Model Inference on MCUs
- 问题：预测 MCU 上 DNN 推理的能量与延迟，现有研究依赖 MACs、模型输入参数等**粗代理**，导致预测不准或需要大量数据采集。
- 方法：用 **MCU 时钟周期**作为预测依据——时钟周期是决定能量与延迟的基本量，且具有很强的线性性，因而预测器可以既简单又准确。
- 数据：不同场景、不同 MCU、不同软件设置下的评估。
- 指标与条件：相比 SOTA，能量预测误差降低 **3×**、延迟预测误差降低 **6.5×**，且所需数据采集量减少 **100×**。
- 局限：2026 年新工作；预测器本身不降低任何能耗，只是**让选型不再靠猜**；需针对具体 MCU/软件栈标定；未给出音频任务的独立数字。
- 对话：与 [S04] 是直接的 `能力→失效` 承接（粗代理 → 误差量化 → 换代理）。**它给本综述一条方法论结论：MACs 不是延迟，op count 也不是——这与本仓 AGC 侧"MACs ≠ 参数量"的裁定 4 是同一条纪律在另一个维度的投影。**

### [S06] End-to-End Efficiency in Keyword Spotting: A System-Level Approach for Embedded Microcontrollers
- 问题：既往 KWS 研究只评测模型推理，忽略整条流水线；而 MCU 上的真实成本包含特征提取。
- 方法：系统级评测，覆盖**从 MFCC 特征提取到神经推理的整条流水线**；对比 DS-CNN、LiCoNet、TENet 与提出的 **TKWS**（基于 MobileNet）；在三个 STM32 平台（N6、H7、U5）上基准。
- 数据：KWS 任务（数据集未在摘要明示）。
- 指标与条件：**TKWS（3 个残差块）以仅 14.4k 参数取得最高 92.4% F1**，在不损失精度的前提下降低内存占用；带神经加速的 **N6 MCU 取得最佳 EDP（能量-延迟积）**。
- 局限：2025 年工作；F1 的数据集与划分未在摘要明示；N6 依赖片上神经加速，非通用 MCU 可比；只到 KWS 单一任务。
- 对话：与 [S03] 同向且更彻底——[S03] 用模拟前端把前处理能耗打到 16%，本条证明**即使不改硬件，只把前处理纳入评测也会改变结论**（谁最优会变）。与 [S08]（NPU 加速 59×）共同说明"有没有专用加速"是档位分界线。

### [S07] MambaLite-Micro: Memory-Optimized Mamba Inference on MCUs
- 问题：Mamba 类架构在 MCU 上部署受限于内存、缺少原生算子支持、缺少嵌入式友好工具链。
- 方法：据作者自述为**首个在资源受限 MCU 上部署 Mamba 架构**的工作；全 C 实现的免 runtime 推理引擎，含（1）权重导出为轻量格式、（2）手工实现 Mamba 层与配套算子并做算子融合与内存布局优化。
- 数据：KWS 与人体活动识别（HAR）两个任务。
- 指标与条件：消除大型中间张量，**峰值内存降低 83.0%**；相对 PyTorch Mamba 实现的平均数值误差仅 **1.7×10⁻⁵**；与 PyTorch 基线**分类准确率 100% 一致**；已在 **ESP32S3 与 STM32H7** 两块 MCU 上验证可移植性。
- 局限：只验证 KWS 与 HAR 两个小任务；未给出延迟与能耗实测（只给内存与数值误差）；C 手写算子意味着换架构就要重写，工程复制成本高。
- 对话：与 [S01] 同为"把本来不该在 MCU 上跑的架构搬上去"的证据；与 [S13] DiTMoS、[S11] LiCo-Net 同属**架构/系统侧降本**一族，但本条的降本对象是**内存**而非算力。

### [S08] Implementing Keyword Spotting on the MCUX947 Microcontroller with Integrated NPU
- 问题：资源受限设备上的实时语音交互。
- 方法：MFCC 特征提取 + CNN 分类器，用**量化感知训练（QAT）**在精度损失最小的前提下压缩模型；部署在带集成 NPU 的 NXP MCXN947 上。
- 数据：KWS 任务（数据集未在摘要明示）。
- 指标与条件：利用 NPU 相比纯 CPU 执行取得 **59× 推理加速**；**97.06% 准确率**，模型体积 **30.58 KB**。
- 局限：依赖片上 NPU，结论不能外推到无加速器的通用 MCU；数据集与划分未明示；只到 KWS。
- 对话：与 [S06] 互为印证（都有片上加速才拿到最佳 EDP/59×）；与 [S01] 形成**直接反差**——Oído 在**无 NPU** 的 $5 MCU 上跑 13M 参数，本条在**有 NPU** 的 MCU 上跑 30 KB 模型；**"端侧"这个词必须写明有没有加速器，否则不可比**。

### [S09] EdgeSpike: Spiking Neural Networks for Low-Power Autonomous Sensing in Edge IoT Architectures
- 问题：边缘 IoT 的自主低功耗感知。
- 方法：软硬协同设计的脉冲神经网络（SNN）框架，四件套：①混合代理梯度 + 直接编码的训练流水线；②**受单次推理能量与内存预算约束**的硬件感知 NAS；③面向 Intel Loihi 2、SpiNNaker 2 与商用 ARM Cortex-M 的事件驱动运行时（含自定义稀疏脉冲 SIMD 内核）；④轻量局部可塑性规则，支持**无反向传播的端上持续自适应**。
- 数据：五个感知任务——KWS、振动机械故障检测、表面肌电手势识别、77 GHz 雷达人体活动分类、结构健康声发射监测；三个硬件目标。
- 指标与条件：平均分类准确率 **91.4%**，与强 INT8 CNN 基线（平均 92.6%）相差 **1.2 个百分点**以内，同时降低单次推理能量（具体倍数摘要未给全）。
- 局限：SNN 工具链成熟度远低于 CNN；1.2 pp 的精度差在安全相关任务上未必可接受；五个任务里只有 KWS 是音频；能量降低的具体倍数未在摘要给全。
- 对话：与 [S11] LiCo-Net、[S03] BNN 同属"换计算范式降本"一族；与 [S14]/[S15] 同有"端上自适应"能力，但本条靠局部可塑性、那两条靠微调/伪标签，路径不同。

### [S10] Embedded Machine Learning for Microcontroller-Class Edge Devices: Data, Feature, Evaluation, and Deployment
- 问题：通用机器学习介绍里**被隐藏的工程决策**——采样与缓冲、特征提取即降维、类别不平衡下的验证、模型/运行时协同设计、流式部署。
- 方法：系统导向的综合（synthesis），以两类信号贯穿全文：惯性动作识别（2 秒三轴加速度窗 → RMS 与频谱特征）与 **KWS（音频采样 → 抗混叠 → MFCC → 紧凑一维卷积网络）**。
- 数据：上述两类信号族。
- 指标与条件：以工程决策为主，**未给出单一可比基准数字**；结论以设计建议形式给出。
- 局限：2026 年预印本；是综合/教程性质而非提出新方法，故无独立实验；未给出跨任务量化表。
- 对话：本条是**本综述"前处理与工程决策"一节的骨架来源**；与 [S03]/[S06] 一起支撑"端侧音频的成本大头与决策大头都在模型之外"。

### [S11] LiCo-Net: Linearized Convolution Network for Hardware-efficient Keyword Spotting
- 问题：不同 ML 算子在低功耗硬件上的效率剖面是异构的；需要为 MCU 这类低功耗处理器专门设计架构。
- 方法：双阶段系统——**推理阶段只用高效的 int8 线性算子**，**训练阶段用流式卷积**以保持模型容量。
- 数据：KWS（数据集未在摘要明示）。
- 指标与条件：在硬件效率上优于 SVDF，检测性能持平。
- 局限：2022 年；只到 KWS；"硬件效率"未给出统一量纲的数字（不同论文口径不同）。
- 对话：与 [S06] 中被对比的 LiCoNet 同源；属**算子级降本**一族。

### [S12] Keyword Spotting System and Evaluation of Pruning and Quantization Methods on Low-power Edge Microcontrollers
- 问题：常驻边缘设备的内存、算力、功耗、成本都受限（如 Cortex-M 系列 MCU），却要满足深度学习的高算力与低延迟要求。
- 方法：小规模 KWS 系统跑在 **STM32F7（Cortex-M7 @216 MHz、512 KB SRAM）** 上；CNN 架构针对边缘约束简化算子数；系统评测**剪枝与量化**两类方法。
- 数据：KWS（数据集未在摘要明示）。
- 指标与条件：基线系统**每 37 ms 产出一次分类结果**。
- 局限：2022 年；37 ms 是单平台口径；数据集未明示；未给出量化后的精度损失数字（摘要层面）。
- 对话：与 [S06]/[S08] 同属 STM32 生态的实测证据链；与 [S11] 同属"压缩四件套"里的剪枝/量化一支。

### [S13] DiTMoS: Delving into Diverse Tiny-Model Selection on Microcontrollers
- 问题：现有方法主要是**压缩大模型**，代价是精度损失。
- 方法：反其道而行——**直接构造小/弱模型再提升其精度**。提出 selector-classifiers 架构，选择器把每个样本路由到合适的分类器。核心洞察：**弱模型的组合可以具有高多样性，其并集能显著抬高精度上界**。
- 数据：MCU 上的 DNN 任务（含音频类的可能性未明示）。
- 指标与条件：摘要未给全具体数值。
- 局限：数值未核实；路由本身引入额外决策开销；多分类器意味着总参数可能反而上升（省的是单次推理）。
- 对话：与 [S04] MicroNets、[S06] TKWS 同属"面向 MCU 的架构设计"，但路线相反——**NAS 找单个最优 vs 弱模型集成**。这是本综述"降本路线"一族里的一个重要分叉。

### [S14] On-Device Domain Learning for Keyword Spotting on Low-Power Extreme Edge Embedded Systems
- 问题：KWS 模型暴露到未见过的噪声环境时精度下降；现场自适应必须在设备本地完成。
- 方法：全端上域自适应系统。
- 数据：噪声条件下的 KWS；复杂语音噪声下的自适应实验。
- 指标与条件：在已经很强壮的 KWS 模型上再取得**最高 14% 精度增益**；端上学习**内存开销 <10 kB**；只用 **100 条标注语音**即可在自适应到复杂语音噪声后**恢复 5% 精度**；在超低功耗 MCU 上完成一次域自适应的能耗为 **806 mJ**、耗时 **14 s**。
- 局限：需要标注（哪怕只要 100 条），冷启动阶段仍需人工参与；806 mJ/14 s 是一次自适应的代价，频繁自适应在电池设备上不划算；只到 KWS。
- 对话：与 [S15] 同属"端上自适应"一族，差别在**要不要标签**——本条要 100 条标注，[S15] 用伪标签完全无标注。两者共同回答了"模型部署后如何在域移下不退化"。

### [S15] Self-Learning for Personalized Keyword Spotting on Ultra-Low-Power Audio Sensors
- 问题：部署后没有标注训练数据，无法做个性化微调。
- 方法：自学习方法——对新的录音帧，依据与**少量用户录音的相似度分数**打**伪标签**，据此增量训练（微调）个性化 KWS 模型；并利用 MCU 的异构处理引擎。
- 数据：两个公开数据集；模型参数量**最高 0.5M**；传感器系统由低功耗麦克风 + 高能效 MCU 组成。
- 指标与条件：相比在大量通用关键词上预训练的初始模型，精度提升最高 **+19.2%** 与 **+16.0%**。
- 局限：伪标签会累积错误（自训练的固有问题）；0.5M 参数上限意味着只覆盖小模型；相似度阈值的选取未见敏感性分析（摘要层面）。
- 对话：与 [S14] 直接对照（无标注 vs 100 条标注）；与 [S17] Tiny-Align 同属"端上个性化"需求。

### [S16] Environmental Sound Classification on An Embedded Hardware Platform
- 问题：大规模预训练音频 CNN 在资源受限嵌入式设备上的**实时部署**表现如何变化。
- 方法：在 **Raspberry Pi** 上部署，实证研究 **CPU 温度**、**麦克风质量**与**音频信号音量**对性能的影响。
- 数据：环境声分类（ESC）任务。
- 指标与条件：实验揭示——**持续 CPU 使用导致温度升高，会触发树莓派的自动降频机制，进而影响推理延迟**；廉价麦克风（如 Google AIY Voice）的质量与信号音量同样影响表现。
- 局限：树莓派属于通用 AP 档而非 MCU 档，结论的外推范围有限；未给出统一的精度/延迟表格（摘要层面）。
- 对话：**本综述"为什么实验室数字不等于端侧表现"的头号证据**——热降频是纯软件评测永远测不到、真机必现的失效模式。与 [S05]（预测器要按真实硬件标定）同向。

### [S17] Tiny-Align: Bridging Automatic Speech Recognition and Large Language Model on the Edge
- 问题：边缘 ASR-LLM 能提供自然音频交互，但现有模型在高算力环境训练、权重大，难以部署到端侧；且音频输入高度个性化，需要端上个性化训练。
- 方法：把 ASR 与 LLM 在边缘对齐（Tiny-Align）；分别微调 ASR 或 LLM 会导致次优，需联合考虑。
- 数据：未在本卡片核实层面取得（摘要口径）。
- 指标与条件：**未核实，本综述不引用具体数值**。
- 局限：摘要口径；"边缘"的具体硬件档位未明示（手机 SoC 还是 MCU 差别巨大）；端上训练的可行能耗未给。
- 对话：与 [S02] Samsone 同属"语言模型能力下端"一族；与 [S15] 同有端上个性化诉求。

### [S18] NeuralAids: Wireless Hearables With Programmable Speech AI Accelerators
- 问题：传统观点认为超紧凑、电池受限的无线助听器难以承载端侧语音 AI——流式深度学习模型算力需求高、I/O 约束严。
- 方法：全端上语音 AI 系统，三项贡献：①集成语音 AI 加速器的无线助听平台；②优化的双路径神经网络；③（第三项摘要未展开）。
- 数据：真实助听器形态的语音增强/降噪。
- 指标与条件：**未给出具体数值**（摘要层面）。
- 局限：数值未核实；助听器是极端的体积/功耗档，结论可迁移性待验；"可编程加速器"的可用性依赖厂商开放。
- 对话：与本仓 AGC 侧的经典 DSP 四件套构成对照——**助听器是"增益与增强必须同时端侧实时"的最强约束场景**，也是 [S29] WaveNorm 类神经增益组件的潜在落点。

### [S19] Towards Privacy-Preserving Audio Classification Systems
- 问题：音频信号能泄露谈话内容、健康状态、情绪、位置与个人偏好；设备录音普及使隐私成为硬性义务。
- 方法：研究现有音频分类系统的伦理与隐私问题，提出**隐私保护的音频特征**——能用于分类多类音频，同时具有隐私保护性质。
- 数据：未在本卡片核实层面取得（摘要口径）。
- 指标与条件：提出特征设计方向，**未给出精度-隐私权衡的量化表**（摘要层面）。
- 局限：摘要口径；"隐私保护"的定义与可验证性需明确（防的是重构还是属性推断）；未给出与不保护基线的精度差。
- 对话：与 [S20]（特征上云而非原始音频）同属端侧音频的隐私一支；**端侧处理本身就是最强的一种隐私保护**，这条把"为什么必须端侧"从性能论证扩展到合理论证。

### [S20] Robust Wake-Up Word Detection by Two-stage Multi-resolution Ensembles
- 问题：唤醒词检测要同时做到鲁棒、节能、快速，单一模型难以兼得。
- 方法：两级多分辨率集成——**端上轻量模型实时处理音频流**，**服务端验证模型**（异构架构集成）精炼检测；用时间对齐增强数据。为保护隐私，**上云的是音频特征而非原始音频**。
- 数据：真实生产场景的唤醒词数据。
- 指标与条件：该方案允许**分别优化两个工作点**（端上重召回/低耗，云端重精确）。
- 局限：摘要口径，无具体数值；两级方案意味着**端上结果不是最终判定**，与"全端侧"诉求有张力；仍需上云（哪怕只传特征）。
- 对话：与 [S01]/[S02] 构成"全端侧 vs 端云分工"的分叉；与 [S21] SAS 同为"是否转发"的路由决策问题。

### [S21] Selective Attention System (SAS): Device-Addressed Speech Detection for Real-Time On-Device Voice
- 问题：在 ASR 前的端侧部署约束下，系统必须在**转录之前**决定是否转发音频，且受严格延迟与算力限制。
- 方法：指出该任务在多说话人、时间上模糊的话语场景下，**建模为对交互历史的序贯路由问题**比" utterance 局部分类"更有效；形式化为 **SDAR（Sequential Device-Addressed Routing）** 并实现为 SAS。
- 数据：留出集 **60 小时多说话人英语**测试集。
- 指标与条件：主要**纯音频配置 F1 = 0.86**（精确率 0.89 / 召回 0.83）；可选摄像头时**音视频融合把 F1 抬到 0.95**（精确率 0.97）。
- 局限：加摄像头换 0.09 F1，代价是功耗与旁观者合规——本综述 §5 明确不推荐；60 小时英语单语；"设备寻址"依赖具体产品形态。
- 对话：与 [S20] 同为"转不转发"的路由问题；其音视频 +0.09 F1 是本综述**"多模态增量必须拿同协议对照说话"**的正面样本（它有明确绝对值，不像许多论文只报"显著提升"）。

### [S22] YAMNet（3.7M，MobileNetV1 + 521 类头）
- 问题：需要一个能在移动端跑的通用音频事件分类器。
- 方法：MobileNetV1 骨干 + 521 类 AudioSet 分类头；Google AI Edge 官方导出路径支持 **TFLite / TFLite Micro**。
- 数据：AudioSet（521 类）。
- 指标与条件：3.7M 参数；**约 72 MMACs/s**；INT8 量化路径官方支持；手机 / Cortex-M 可跑。体积约 **15 MB fp32 / ~4 MB INT8**。
- 局限：521 类是固定词表，加类要重训；72 MMACs/s 在常驻档偏贵；mAP 口径需标 AS-20K 或 AS-2M full 才可比。
- 对话：**端侧 AED 的事实基线**；与 [S23] EfficientAT 同台对比（同为小模型，后者参数更小且报了 AudioSet mAP）。

### [S23] EfficientAT（mn10_as 等，0.983M）
- 问题：在极低算力预算下做到可用的 AudioSet tagging 精度。
- 方法：MobileNet 系列 + 注意力/蒸馏等效率手段（系列含 0.98–17.9M 多个尺寸）。
- 数据：AudioSet。
- 指标与条件：**0.983M 参数、11 MMACs/s**（按 10 秒片段折算），**AS-2M full tagging mAP 0.432**。
- 局限：**只有官方 PyTorch 权重，未见公开 INT8 发布**——"参数量达标 ≠ 端侧有产物"；0.432 是 AS-2M full 口径，与 AS-20K 不可比。
- 对话：与 [S22] 的对比给出本综述一条硬结论：**参数量小不代表能部署，要看有没有量化/导出产物**。

### [S24] DCASE2025 Task 1 baseline（低复杂度 ASC）
- 问题：低复杂度声学场景分类的当前位置与天花板。
- 方法：CPJKU 官方基线系统。
- 数据：TAU Urban Acoustic Scenes 2022 Mobile，**10 类**，仅 25% 标签。
- 指标与条件：**61,148 参数**（fp16 122,296 B）、**29.42 MMACs/s**、宏平均准确率 **53.24%**；四年天花板 60.8%（2022）→ 62.7%（2023）→ 62.1%（2024）→ 61.5%（2025），**没有趋势性提升**；同期官方基线 44.2% → 53.2%。
- 局限：10 类 ASC 不是事件检测，不能与 mAP/PSDS 同表；53.24% 的 split 未在 README 复现；25% 标签使"标签效率收益"与"精度上限"混在一起。
- 对话：与 [S23] 一起界定**端侧 AED 的精度天花板**：不是"模型还能变大吗"，而是"在这个算力预算下四年没动"。

### [S25] RNNoise（0.085M）
- 问题：常驻降噪需要在 MCU 级算力下工作。
- 方法：GRU 预测频带增益（**降噪掩码**，非增益控制）；C 定点实现。
- 数据：DNS4 blind test。
- 指标与条件：**0.085M 参数、<10 MFLOPS**；DNSMOS OVLMOS **3.38**（DNS4 blind）；48 kHz / 20 ms 帧。
- 局限：输出掩码不改整体电平（不是 AGC）；42 维特征、单通道。
- 对话：**端侧音频"能常驻"的体积与功耗地板**；与 [S03] 的 85%→16% 结论配合——即使模型只占小头，把模型再缩小也解决不了大头。

### [S26] GTCRN（0.048M）
- 问题：更小的端侧降噪。
- 方法：卷积循环结构；官方支持 **ONNX Runtime Mobile INT8**。
- 数据：VoiceBank-DEMAND。
- 指标与条件：**0.048M 参数**；PESQ **2.87**（VoiceBank-DEMAND）；16 kHz / 10 ms 帧。仓库实测 48.2K 参数 / 33.0 MMACs（论文口径 23.7K / 39.6 MMACs，**两者不自洽**）。
- 局限：8 kHz 以上高频事件救不回来；掩码不改电平；论文与仓库的算力数字不自洽。
- 对话：与 [S25] 同为端侧降噪的体积下界；其"论文 vs 仓库口径打架"是本综述**为什么要坚持"数字带出处"**的现成例子。

### [S27] Silero VAD（约 2 MB）
- 问题：需要一个能常驻、低延迟的语音活动检测门控。
- 方法：小型神经网络 VAD，有 ONNX 导出。
- 数据：作者自述在多语种多域数据上训练。
- 指标与条件：**30 ms chunk 在 CPU 上 <1 ms**；模型**约 2 MB**。
- 局限：是门控不是识别器；阈值需按场景标定；"CPU"未指明具体型号。
- 对话：**常驻链路的第一道闸门**，与 [S20] 的两级唤醒、[S03] 的亚毫瓦门控构成"门控成本谱"。

### [S28] CLAP（音频–文本对比学习，约 86M+）
- 问题：固定词表要加类就得重训。
- 方法：音频与自然语言描述投到同一嵌入空间，类别集在**推理时给定**（开放词表）。
- 数据：LAION 音频-文本对。
- 指标与条件：参数量 **约 86M+**；可跑 **ONNX Runtime Mobile / CoreML**；体积 **>300 MB**。
- 局限：体积与算力决定它只能进**手机/NPU 触发后短时**档，不能常驻；开放词表的精度通常低于同规模闭集。
- 对话：与 [S01] Oído、[S02] Samsone 构成"开放词表下端"的三档：>300 MB（[S28]）→ 134M（[S02]）→ 13M（[S01]）；**这是 2026 年端侧音频最陡的一条进步曲线**。

### [S29] WaveNorm AGC（Interspeech 2026）
- 问题：传统 AGC 用固定起音/释放常数，只依赖能量、不区分语音与噪声，导致削波、跟随延迟、增益泵浦与噪声过放。
- 方法：**纯时域因果端到端**神经 AGC：膨胀分组 Conv1D ×3 → **GRU bottleneck** → 转置 Conv1D ×3；无 STFT；优化目标为对齐 **ITU-T P.56 / P.79** 的目标响度。
- 数据：48 kHz 训练；TIMIT（clean）与 VoiceBank+DEMAND（noisy）；VAD 实验用 TIMIT + DNS3 构造内部集；16 kHz 加评。
- 指标与条件：**49M MACs / 55 KB 内存**；Silero VAD 阈值 0.5 下 FPR **0.272**、AUC **0.96**（对照 Baseline 0.302/0.92、WebRTC 0.304/0.93、Carnival 0.277/0.92）；作前端使 DFN2/DTLN/GTCRN 的 NISQA 由 3.22/2.28/2.92 提升到 3.57/2.49/3.13。**参数量未给出**。
- 局限：参数量与每帧延迟实测均未给出；**闭环指标零报告**（收敛时间、稳态误差、增益波动、过冲/下冲、削波率全无）；实验在文件级语料上做，未在真实采集链路验证二次增益风险。
- 对话：**本综述唯一一条"端侧增益控制"的现代样本**；与 [S25]/[S26] 的分野是控制对象（掩码 vs 电平）；与 [S03] 同指"前处理才是大头"——增益控制恰恰在前处理里。
