证据附录：docs/research/2026-10-19-on-device-audio-survey-evidence.md（检索日志、筛选台账、单篇卡片、叙事大纲、溯源记录、未核实清单）。

1. 摘要与结论

本文纳入 29 篇文献（编号 S01–S29，覆盖 2020–2026 年，重点 2022–2026；检索、筛选与排除见 §2–§3，逐篇卡片见证据附录 §4），围绕五个问题组织：「端」分哪几档；端侧音频的瓶颈到底在哪；五条降本路线各换来什么；部署后如何在域移下不退化；2026 年的新边界在哪。七条结论：

  1. 「端侧」不是一个词，是四个量级。无加速器的 $5 MCU（[S01] ESP32-S3：240 MHz 双核、512 KB SRAM、无 NPU）、带集成 NPU 的 MCU（[S08] MCXN947）、移动 SoC/NPU（[S28] CLAP >300 MB 体积）、通用 AP（[S16] 树莓派）四档之间差 3–4 个数量级。报"端侧"而不写平台，等于没报——[S08] 的 59× 加速完全来自片上 NPU，[S01] 的 13M 参数则是在没有 NPU 的前提下做到的，两者不可比。
  2. 能耗大头不在模型，在采集与前处理。 [S03] 用模拟二值特征提取替换数字前处理，使数据采集与前处理的能耗降低 29×、占系统份额从 85% 降到 16%。这意味着"把模型再缩小"打的是小头。[S06] 从另一面印证：把 MFCC 到推理的整条流水线一起评测时，"哪个模型最优"这个结论会变。[S05] 则量化了选型本身的误差——用 MACs 当代理，能量与延迟预测误差分别可被降低 3× 与 6.5×。
  3. 五条降本路线省的不是同一种资源。 NAS（[S04]）、架构与算子重设计（[S11]/[S07]/[S13]）、量化与剪枝（[S12]/[S08]）、换计算范式（[S09] SNN、[S03] BNN）、专用硅（[S08]/[S18]）——有的省内存（[S07] 峰值内存 −83.0%）、有的省算力（[S08] 59×）、有的省能量（[S03] 29×）、有的只是省选型试错（[S05] 采集量 −100×）。混称"模型压缩"会掩盖这一点。
  4. 参数量达标 ≠ 端侧有产物。 [S23] EfficientAT 的 0.983M 参数 / 11 MMACs/s 在预算内，但只有官方 PyTorch 权重、未见公开 INT8 发布；[S22] YAMNet 则有完整的 TFLite / TFLite Micro 官方导出路径。本仓 AED 域表的原话是"真实缺口：论文给约束（128K 参数 / 30 MMACs），但部署产物少见"。
  5. 部署后的自适应决定模型寿命，三条路径的差别是要不要标签与要不要反向传播。 [S14] 用 100 条标注恢复 5% 精度、代价 806 mJ / 14 s（内存 <10 kB）；[S15] 用伪标签做到无标注、提升 +19.2% / +16.0%；[S09] 用局部可塑性做到无反向传播的持续自适应。
  6. 真机失效是纸面测不到的。 [S16] 在树莓派上发现持续 CPU 使用导致升温、触发自动降频、进而影响推理延迟；[S26] GTCRN 的仓库实测（48.2K 参数 / 33.0 MMACs）与论文口径（23.7K / 39.6 MMACs）不自洽。两条都指向同一件事：端侧选型要看导出产物与真实硬件，不能只看论文表格。
  7. 2026 年的新边界是开放词表下端，但"能跑"与"能实时跑"还差 2×。 开放词表从 [S28] 的 >300 MB 压到 [S02] Samsone-134M（小型音频语言模型），再压到 [S01] Oído——13M 参数 Conformer-CTC 跑在 $5 无 NPU MCU 上，LibriSpeech WER 3.70% / 8.23%。代价是实板测得 1.97× 时长（约 2 倍慢于实时）。所以正确表述不是"端侧能做开放词表了"，而是"端侧能做开放词表，但暂时只能说完再转"。

边界声明：本综述 29 篇里只有 [S29] 一篇读到全文，[S01]–[S21] 为摘要口径，其数字只作量级与方向证据、不参与跨行比较；硬件档位的功耗阶梯引用本仓既有域表的表格核实口径，未逐篇回原文复核（§9）。

4. 「端」的四档硬件与三本预算账

口径声明：本节引用的 [S01]/[S08]/[S16]/[S18] 均为摘要口径，[S22]–[S28] 为表格核实口径；摘要口径数字只作量级与方向参照，不参与跨行比较（§2.2）。

把 [S01]、[S08]、[S28]、[S16] 并排，"端侧"这个词立即失效——它们分属四个量级。

档位代表平台典型预算本综述的锚点能跑什么
A · 无加速 MCUESP32-S3（240 MHz 双核、512 KB SRAM、8 MB PSRAM、无 NPU）内存数百 KB 级；体积 MB 级[S01] Oído13M 参数 Conformer（int8），但慢于实时 2×；30 KB 级 KWS（[S08] 在有 NPU 时）
B · 带 NPU 的 MCUNXP MCXN947（集成 NPU）同上，但推理快 1–2 个数量级[S08]97.06% KWS / 30.58 KB / NPU 59× 加速；[S06] 的 STM32 N6 取最佳 EDP
C · 移动 SoC / NPU手机、助听器加速器体积百 MB 级、瓦级短时[S28] CLAP（>300 MB）、[S18] NeuralAids开放词表（[S28]）、实时增强（[S18]）、小型音频语言模型（[S02] 134M）
D · 通用 AP树莓派、跑 Linux 的机器空闲即百 mW–W 级[S16]什么都能跑，但会热降频（[S16]），且常驻不划算

三本账必须分开算：mW 账决定能不能常驻，ms 账决定能不能流式，MB 账决定能不能装进去。[S01] 是典型的三本账互相打架——MB 账过了（8.3 MB 的 int4 变体）、mW 账没报、ms 账没过（1.97× 时长）。[S08] 三本都过，但依赖片上 NPU。

本仓既有的功耗阶梯（引用 always-on-recording/hardware-power.md §3，不重算）给的是 mW 账的跨档跨度：定制 ASIC 的常驻检测 47 nW – 1 µW、专用音频 NPU 140 µW、手机传感中枢 <1 mA、通用 MCU/AP 软件方案 26–50 mW、跑 Linux 的通用机器空闲 400–1000 mW——跨档 3–4 个数量级。这个跨度是本综述所有"能不能常驻"判断的分母。

5. 瓶颈不在模型：前处理、采集与真机失效

口径声明：本节引用的 [S03]/[S05]/[S06]/[S16] 均为摘要口径（[S22]/[S23]/[S25]/[S26] 为表格核实）；摘要口径的 29×、3×、6.5× 等倍数只作方向证据，不参与跨行比较（§2.2）。

本节三条证据指向同一个反直觉结论，它们之间是 结论→反例 的承接关系。

第一条（最强）：[S03] 把模拟二值特征提取替换数字前处理，数据采集与前处理的能耗降低 29×、占系统份额从 85% 降到 16%。如果模型是大头，这个改动不可能有 29× 的效果。这意味着"优化模型"打的是小头——把 [S25] RNNoise 的 0.085M 再缩小一半，对整系统的影响远小于把前处理搬进模拟域。

第二条：[S06] 把评测范围从"模型推理"扩展到"MFCC 到推理的整条流水线"，在 STM32 N6/H7/U5 三块板上对比 DS-CNN、LiCoNet、TENet 与 TKWS。结果是 TKWS 以 14.4k 参数取得 92.4% F1，且带神经加速的 N6 取得最佳 EDP。关键在于：换了评测口径，"谁最优"会变——只在推理段评测时最优的模型，放到整条流水线上未必还是。

第三条：[S05] 指出用 MACs、输入参数这类粗代理预测 MCU 上的能量与延迟会失准，改用时钟周期后，能量与延迟的预测误差分别降低 3× 与 6.5×，所需数据采集量减少 100×。这条不省任何能耗，但它说明选型阶段就在靠错的量做决策。

第四条是前面三条的骨架来源：[S10] 是一份面向 MCU 级边缘设备的系统导向综合，它把通用机器学习介绍里通常被隐藏的工程决策逐项摆出来——采样与缓冲、特征提取即降维、类别不平衡下的验证、模型/运行时协同设计、流式部署，并以惯性动作识别与 KWS 两个信号族贯穿。它不提出新方法、也不给单一可比基准，但正是它说明了为什么上述三条会同时成立：端侧音频的成本大头与决策大头都在模型之外。

真机才有的失效是同一件事的另一面。[S16] 在树莓派上部署大规模预训练音频 CNN，发现持续 CPU 使用导致升温、触发自动降频机制、进而影响推理延迟——这是纯软件评测永远测不到的失效模式。它还发现麦克风质量与信号音量同样影响表现：端侧音频的误差不只来自模型。

与之呼应的是"口径不自洽"：[S26] GTCRN 的仓库实测是 48.2K 参数 / 33.0 MMACs，论文口径是 23.7K / 39.6 MMACs，两者打架。以及 [S23] EfficientAT：0.983M 参数 / 11 MMACs/s 完全在预算内，但只有官方 PyTorch 权重、未见公开 INT8 发布；反观 [S22] YAMNet 有完整的 TFLite / TFLite Micro 官方导出路径。"参数量达标"与"端侧有产物"是两件事，本仓 AED 域表把后者称为"真实缺口"。

本节判断：端侧音频的瓶颈按顺序是——采集与前处理（[S03] 的 85%）→ 有没有专用加速（[S08] 的 59×）→ 模型本身。只做第三步的优化，是打偏了。而"能不能落地"还取决于有没有人把量化与导出这一步做完（[S22] vs [S23]）。

6. 五条降本路线：各换来什么、代价是什么

口径声明：本节引用的 [S03]/[S04]/[S05]/[S07]/[S08]/[S09]/[S11]/[S12]/[S13]/[S18] 全部为摘要口径；表内倍数与百分比只作方向证据，不参与跨行比较（§2.2）。

这是本篇的研究对比表（先成表、再叙述）。五列的「限制」一律带实验条件。

方法族代表论文主要思路优势限制（含实验条件）
① NAS / 自动设计[S04] MicroNets、[S09] 硬件感知 NAS在内存/延迟/能量约束下自动搜架构；[S04] 用 op count 作延迟代理，[S09] 用单次推理能量与内存预算做界不需要人工试错，直接把硬件约束写进搜索目标[S04] 的 op count 只是近似代理，[S05] 量化了它的误差（延迟预测误差可改进 6.5×）；[S09] 的 SNN 工具链成熟度低于 CNN

读这张表的方式：同一列里省的东西不一样。①③主要省算力与体积，②主要省内存，④主要省能量，⑤是换档位。把五族统称"模型压缩"会让读者以为它们可互换，而实际上一个缺内存的项目（进不了 SRAM）和一个缺电量的项目（常驻不了）需要的是完全不同的路线。

还有一条不属于任何一族但必须先做：⑤′ 测量方法（[S05] InstMeter）。它不省任何资源，但它让前面四族的选型不再靠猜——能量与延迟预测误差降低 3× / 6.5×，采集量减少 100×。

7. 部署之后与 2026 年的新边界

口径声明：本节引用的 [S01]/[S02]/[S03]/[S09]/[S14]/[S15]/[S17]/[S19]/[S20]/[S21] 均为摘要口径（[S27]/[S28]/[S29] 为表格核实或全文）；摘要口径数字只作量级与方向参照（§2.2）。

7.1 部署后不退化：三条端上自适应路径

模型上线面对的是域移（新噪声、新用户、新麦克风）。三条路径的差别只有两问：要不要标签、要不要反向传播。

  • [S14] 要标签，代价可量化：全端上域自适应，在已经很强壮的 KWS 模型上再取 最高 14% 精度增益；只用 100 条标注语音即可在自适应到复杂语音噪声后恢复 5% 精度；内存开销 <10 kB；在超低功耗 MCU 上一次自适应耗 806 mJ、14 s。
  • [S15] 不要标签，用伪标签：依据与少量用户录音的相似度打分打伪标签，增量微调个性化模型；在参数量最高 0.5M 的模型、两个公开数据集上取得 +19.2% / +16.0%。代价是伪标签会累积错误——这是自训练的固有风险，摘要未见敏感性分析。
  • [S09] 连反向传播都不要：轻量局部可塑性规则，支持端上持续自适应，且落在 Loihi 2 / SpiNNaker 2 / Cortex-M 的事件驱动运行时上。代价是精度比 INT8 CNN 低 1.2 pp。

三者的取舍很清楚：要不要付标注成本（[S14] 100 条）＝ 要不要承担伪标签噪声（[S15]）＝ 要不要接受精度差（[S09] 1.2 pp）。对常驻设备而言，806 mJ / 14 s 还意味着自适应不能频繁做。

7.2 2026 新边界：开放词表与小型音频语言模型

这是本篇进步最陡的一条曲线，[S28] → [S02] → [S01] 是 能力→失效 的承接：

  • [S28] CLAP（2022）：音频–文本对比学习，类别集推理时给定，绕开"加类要重训"。代价是约 86M+ 参数、体积 >300 MB——只能进移动 SoC 档，常驻不可行。
  • [S02] Samsone（2026）：小型音频语言模型（SALM）系列，99M / 134M / 356M 三个缩放点；发布训练代码、权重、移动端优化 checkpoint 与开源 Android 演示应用。摘要自述 134M 在该尺寸级 SOTA，但具体基准数值未核实（本综述不引用）。
  • [S01] Oído（2026）：把开放词表 ASR 压到 $5 无 NPU 的 ESP32-S3——13M 参数 Conformer-CTC，int8 权重 + 逐帧动态 int8 激活 + int8 注意力全落在该芯片的 SIMD 上，调度围绕 flash 与 PSRAM 带宽设计。LibriSpeech test-clean/test-other WER 3.70% / 8.23%（与全精度差 0.12 点内），加片上 1.3M LM 后 3.33% / 7.15%，transducer 头 2.99% / 6.67%，int4 变体装进 8.3 MB。同芯片上比厂商识别器少 2.3–2.8× 错误，也优于笔记本上全精度的 Whisper tiny.en 与 Moonshine tiny。

但失效面同样明确：实板测得固件运行速度为 1.97× 时长，即约 2 倍慢于实时。所以正确结论是——端侧已经能做开放词表识别，但暂时只能"说完再转"，不能"边说边转"。把 [S01] 读成"MCU 上实时 ASR 已解决"是误读；它与 [S27] Silero VAD（30 ms chunk 在 CPU 上 <1 ms）之间那道实时性鸿沟，正是下一步要填的。

7.3 隐私、路由与"端侧"的定义强度

三条工作给出三种强度的"端侧"：

  • [S19] 特征级隐私：提出能分类多类音频、同时具有隐私保护性质的音频特征。它把端侧处理的理由从性能扩展到合规——音频能泄露谈话内容、健康状态、情绪、位置与个人偏好。
  • [S20] 两级唤醒：端上轻量模型实时处理音频流，服务端异构集成模型精炼检测；上云的是音频特征而非原始音频。代价是端上结果不是最终判定，与"全端侧"诉求有张力。
  • [S21] 转发路由可量化：把"是否转发给 ASR"建模为对交互历史的序贯路由（SDAR）而非 utterance 局部分类。在 60 小时多说话人英语留出集上，纯音频 F1 = 0.86（P 0.89 / R 0.83），加摄像头后 F1 = 0.95（P 0.97）。

[S21] 值得单独表扬的地方是它给了绝对值——本综述在别处反复遇到"只报显著提升、无绝对值"的写法（本仓 AED 侧同样如此），而 [S21] 让人能直接算：+0.09 F1 换一个摄像头，值不值？本综述的判断是不值——摄像头带来功耗与旁观者合规两笔账，而 [S21] 的纯音频 0.86 已经可用。

7.4 任务侧落点：门控、事件、增强、增益

端侧不是单一任务，四类任务的预算轴完全不同：

任务端侧锚点关键约束现状判断
门控（VAD/唤醒）[S27] Silero VAD 约 2 MB、30 ms chunk 在 CPU 上 <1 ms；[S03] 亚毫瓦门控常驻，mW 账最紧已解决，且有从软件（[S27]）到专用硅的整条成本谱
音频事件（AED）[S22] YAMNet 3.7M / ~72 MMACs/s（有 TFLite Micro 导出）；[S23] 0.983M / 11 MMACs/s（无量化产物）；[S24] DCASE 10 类 / 29.42 MMACs/s / 53.24%词表固定，加类要重训四年天花板没动（60.8→62.7→62.1→61.5%），端侧档的瓶颈是词表与算力双约束
增强（降噪）[S25] RNNoise 0.085M / <10 MFLOPS；[S26] GTCRN 0.048M / ONNX Runtime Mobile INT8改掩码不改电平体积与功耗地板已很低，再缩收益有限（[S03] 说明大头不在模型）
增益（AGC）[S29] WaveNorm 49M MACs / 55 KB，因果，对齐 ITU-T P.56/P.79必须因果、必须防二次增益唯一现代神经样本，但参数量与闭环指标双空白，只能进观察名单

四类里只有门控真正解决了常驻问题；AED 卡在词表与算力的双重约束且天花板四年不动；增强已到地板；增益刚刚出现神经方案但还没在自己的尺子上报过数。

8. 研究空白与未来方向

口径声明：本节引用的 [S01]/[S02]/[S03]/[S05]/[S06]/[S09]/[S14]/[S15]/[S16] 均为摘要口径；由摘要口径条目推导出的"空白"同样只作方向判断，不作为已证实的领域结论（§2.2）。

每条都追溯到具体局限，并给出验收口径。

  1. 把"整条流水线"变成端侧音频的默认评测口径（源于 [S03] 的局限：只给比例与倍数、无整系统绝对功耗；[S06] 的局限：只到 KWS 与 STM32 三块板；[S16] 的局限：热降频是通用 AP 档才有的现象、未给统一表）。做法：任何端侧音频论文同时报"采集+前处理+推理"三段能耗与延迟。验收：三段之和可核对，且必须声明平台有无加速器。
  2. 补"参数达标 → 量化产物"这一环（源于 [S23] 的局限：0.983M 参数在预算内但只有 PyTorch 权重、无公开 INT8；[S26] 的局限：论文与仓库的算力口径不自洽）。做法：对端侧档的论文，把"是否发布量化导出产物"作为可检索字段。验收：给出一张"参数达标 / 有导出产物"的交叉表，缺口数量化。
  3. 缩小"能跑"与"能实时跑"之间那 2×（源于 [S01] 的局限：实板 1.97× 时长、约 2 倍慢于实时；[S27] 的局限：门控已能做到 <1 ms/30 ms chunk，识别侧却慢 2×）。做法：把 [S01] 的调度与带宽优化思路与流式解码结合。验收：在同等无 NPU MCU 上做到 RTF ≤ 1，并报能耗。
  4. 端上自适应的能耗账需要统一口径（源于 [S14] 的局限：806 mJ / 14 s 是一次自适应的代价，频繁自适应在电池设备上不划算；[S15] 的局限：伪标签累积错误、无敏感性分析；[S09] 的局限：1.2 pp 精度差未必可接受）。做法：报"每恢复 1% 精度所需的能量与标注量"。验收：三条路径在同一数据集上给出该比值，可直接横比。
  5. 开放词表的端侧下沿需要实测而非声明（源于 [S02] 的局限：摘要未给具体基准数值、未给端侧实测延迟与功耗；[S28] 的局限：>300 MB 体积决定它只能进触发后短时档）。做法：对 99M/134M/356M 三档给出移动端实测的延迟、峰值内存与能耗。验收：三档各报三项，缺一项不算通过。
  6. 真机失效清单化（源于 [S16] 的局限：树莓派单平台、未给统一表；[S05] 的局限：预测器需按具体 MCU/软件栈标定）。做法：把热降频、麦克风质量、信号音量、量化产物缺失整理成端侧部署的检查表。验收：至少覆盖四项，每项给出探测方法。
