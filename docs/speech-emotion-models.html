中文场景 · 提醒一 不要选 emotion2vec

英文 IEMOCAP WA 71.79，但 MER2024 中文只有 WAF 56.08，被同为 95M 的 HuBERT-base （69.26）甩开约 13 点——预训练语料 Emo-262 是纯英文。中文侧优先 Chinese-HuBERT（MER2024 WAF 72.67，MIT） 或 HuBERT-base（69.26）。

中文场景 · 提醒二 量化停在 INT8

INT8 在 SER 上有同行评审的「无损」证据（0.88 → 0.88）；INT4 在音频任务上有崩溃证据 （Conformer WER 15.94 → 38.49），且 SER 的 INT4 数据完全空白。SenseVoice-Small 的 Q8_0（254 MB）是官方背书「精度保持一致」的档位。

全档通杀的硬约束 功耗：0 条达标

情感识别的推理功耗落在阶梯第 4–5 级（通用 MCU/AP 26–50 mW ~ 手机 NPU 1–4 W）， 具体位置由「跑什么核」和「跑多频繁」共同决定，与模型大小弱相关。 laos 常驻预算 <5 mW（LPI）/ <50 mW（Active）——只能靠触发，不能靠选模型解决。

04选型决策树

输入是部署约束（能不能出端、有没有 NPU、要不要实时、允不允许联网），输出是档位 + 具体模型。每一步都有判据，判据里带数字的即阈值。

起点：laos 情绪通道选型（46 条记录 / 3 档 × 2 标记）
│
├─ Q1 · 这个通道要不要「无触发也醒着」的常驻？
│     判据：功耗预算是否必须 ≤ 25 mW（≈3%/天）
│     ├─ 否 → 跳到 Q4（触发后运行）
│     └─ 是 → Q2
│
├─ Q2 · 能不能出端？（原生 Android App + aDSP/LPAI 授权）
│     判据：是否有高通授权 + 厂商签名。未授信进程走 fastrpc attach 音频 PD
│           直接返回 -EACCES；第三方 App 能自由使用的只有 HTP（瓦级）
│     ├─ 不能（proot Ubuntu / Termux）→ 判定【常驻否决】 → 转 Q4
│     │     理由：任何醒着的 proot 进程 400–1000 mW，比 aDSP 贵 2–3 个数量级
│     └─ 能 → Q3
│
├─ Q3 · 出端之后拿到的是哪种计算单元？
│     判据：aDSP / Sensing Hub（官方 <1 mA，mW 档） vs HTP / NPU（1–4 W，瓦档）
│     ├─ aDSP / LPAI → ✅【A 档 · 真端侧 · 极小型】
│     │     模型：TIM-Net int8（34,671 参数 / 0.4 MB；蒸馏版 ~174 KB .eaix）
│     │     ⚠ 46 条记录中 0 条有 A 档实测；本条来自 laos 既有原型，
│     │       且无 on-device RTF / 功耗实测（唯一 ≈6 ms 是 CPU 后端推算）
│     └─ 只有 HTP → 判定【常驻仍否决】（1–4 W）→ 转 Q4 触发式
│
├─ Q4 ·（触发后运行）要不要实时 / 近实时？
│     判据：RTF ≤ 0.1（10 s 音频 ≤ 1 s）且端到端在数百 ms 内返回
│     ├─ 是（漏斗③）→ Q5

│

07与 Task 8 落地的关系

  • 候选通道已定：sherpa-onnx 优于 funasr（04 §8）。 sherpa-onnx 有官方 manylinux2014_aarch64 与 android_arm64-v8a wheel、 不依赖 torch、一个前向同时产出文本 / 语种 / 情感 / 事件；而 funasr 路径要装 torch （GB 级内存、数秒加载），且唯一 RTF 证据来自 PC。这条把决策树 Q6 的「一体化」分支钉死了。
  • laos 的真实位置是 A+T 档（漏斗③ 已有 ASR），不是 A 档。 按 05 §6.2，从 A+T 再加视觉的增量只有 +1.5 ~ +5.0 点 （IEMOCAP +1.54 / CMU-MOSEI +1.63 / MER2024-SEMI +2.67 / MER2024-NOISE +4.88 / MER2025 +4.99）， 换来的是 3 条法律否决项 + 2 个数量级的功耗 + 与「原数据即焚」的架构互斥。
  • 这两条如何约束选型：它们把问题从「挑一个 SER 模型」改写成 「挑一条能复用 ASR 前向的通道」。于是 46 条里的 11 条多模态记录全部退化为排除项， 选型空间压到 A / A+T 两类，而 A+T 里真正可用的只有 「一次前向出文本 + 情感」的一体化形态——答案因此收窄到 中型档 SenseVoice-Small（sherpa-onnx）。
  • 留给 Task 8 的两件事（本页不动代码）：① 通道命名建议取 sherpa （由 runtime 名 + 本文结论导出，非凭空命名），最终以 Task 8 为准； ② 新通道与既有 classify_mood()（只输出高唤醒 / 平稳 / 低唤醒 / 短促）的职责边界， 由 Task 8 在 06-adoption.md 里划定。
