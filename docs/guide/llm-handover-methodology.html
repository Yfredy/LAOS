0 · 一句话论点

交接文档的失败不是文采问题，是"知识诅咒"问题：写的人默认自己脑中的上下文对方也有。大模型恰好在这一点上有杠杆——它可以零成本扮演零上下文读者去验收自己写的内容。方法的全部要义：结构先行、证据锚定、写审分离、可执行验收。

配套：同名 Markdown 版（llm-handover-methodology.md）；四个拿来即用的 Prompt 模板见 §5。

1 · 五种失效模式（先钉死敌人）

#失效模式症状根因
F1散文式自传讲了项目心路历程，新人还是不知道怎么跑测试没有结构约束，自由写作必然产出叙事
F2隐性知识蒸发"环境配好之后很简单"——怎么算配好？代理怎么设？凭据在哪？写的人不知道自己知道
F3过期文档文档说 980 个测试，实际 1016 个没有与代码变更绑定的更新协议
F4指针地狱"详见代码"/"详见 wiki"/一串 Jira 链接把"哪里有信息"当成了"信息本身"
F5能跑≠能上手环境跑起来了，然后不知道下一步干什么、什么不能碰只覆盖冷启动，没有日常层和红线层

大模型会放大 F1 和 F4（它极擅长流畅的空洞叙事），框架后半部分全部用来压制这两种倾向。

2 · 交接包的五层信息架构

先给模型骨架，再让它填肉。新人按序消化，每层有明确完成判据：

层回答的问题内容要点完成判据（新人视角）
L0 生存层这是什么？边界在哪？30 秒电梯陈述；"是 X 不是 Y"的否定式定位；一句话技术栈；顶层目录地图我能向第三个人转述这个项目而不脸红
L1 冷启动层怎么从零跑起来？一条命令到绿测试：解释器精确到路径与版本、依赖、代理/镜像、凭据获取、smoke 命令 + 预期输出原文；平台差异坑我在新机器上只凭此文档让测试全绿
L2 日常操作层每天的活怎么干？跑测试（全量/单个）、加一个模块（目录/命名/测试怎么跟）、发版流程、常见错→解法表改任何一类东西前知道看哪里、改完怎么验证
L3 架构决策层为什么长这样？模块职责 + 依赖方向；决策记录：为什么这么定、否掉了什么（不解释历史，就会被人"修复"）我不会把故意设计的边界当 bug 重写
L4 治理红线层什么绝对不能碰？去哪问？红线逐条带违反后果；模块 ownership；提问渠道知道哪些"看起来能改"的地方会出事

层间纪律：L1 每条命令必须带预期输出原文；L3 只写"为什么"（"是什么"归代码与 L0 地图）；L4 红线不带后果就是口号。

3 · 让大模型写好的七个手法

① 读者画像显式注入

prompt 开头钉死："读者是通用 SWE 新人：会写代码、会读英文文档，但不知道（列出领域特有概念）"。不注入画像，模型按"中级同事"水位写，恰好卡在半空。

② 结构先行，骨架给定

把五层架构作为模板发给模型逐层填。骨架是防散文的最强约束。

③ 证据锚定（最重要）

硬性规则：每个声称必须锚定到 file:line / 命令 + 预期输出原文 / commit hash / 文档路径之一。说"配置在 X 文件"必须给精确路径与当前值。

④ 先取数后写作（反幻觉关键工序）

绝不让模型"凭记忆"写：先读仓库产出事实清单（每条带证据）→ 人抽查（尤其数字与路径）→ 确认后才写作；写作只允许重组清单内事实，清单外声称显式标"未核验"。

⑤ 写审分离（双角色互审）

写作用会话 A；验收必须开新会话 B——B 只拿交接包 + 仓库，被要求完成指定任务，卡住的位置就是文档缺口。同一会话自审没有意义（上下文残留 = 开卷考）。

⑥ 反占位词硬约束

禁词表：TBD / 待补 / TODO / 适当处理 / 详见代码 / 略——可写 10 行校验脚本扫（占位词是 F4 的量化指标）。

⑦ 时效标注与单一真相源

文档头部写"基于 commit <hash>（日期）时刻快照"；文档与代码冲突时以代码为准并回来修文档；把"什么变更触发更新哪些小节"写成显式清单（可机器化——见 §7 release.py 例）。

4 · 验收：怎么证明"能直接上手"

文档质量的最终度量是行为，不是观感。冒烟式验收：

  1. 选 3–5 个"新人第一周会做的真实任务"（跑绿测试 / 定位配置 / 解释决策 / 小改动并验证 / 说出红线后果）；
  2. 让零上下文的模型（或真人）只凭交接包执行；
  3. 记录每次卡壳：卡在哪步、缺什么信息、哪句误导；
  4. 修文档，换任务重测，直到连续一轮零卡壳。

五问速查（人工 10 分钟版）：新人能否①一句话说清边界？②说出跑测试的精确命令与预期数字？③指出"最容易被误改"的三个地方？④解释最重要的历史决策（为什么否掉备选）？⑤知道出问题先问谁/查哪？——五问全过，L0–L4 才算闭环。

5 · Prompt 模板集（拿来即用）

模板 A · 交接包生成

你是资深工程师，为项目写交接包。读者：通用 SWE 新人（会写代码，但不知道
<领域特有概念清单>，没有本仓库与团队的任何历史上下文）。

工序（严格按序，不得跳步）：
1. 先读仓库：目录树、README、git log 最近 30 条、<关键文件清单>；
   产出【事实清单】——只列你实际读到的东西，每条带 file:line 或命令
   输出原文。禁止写入清单外的事实。
2. 停下，把事实清单给我抽查。
3. 抽查通过后，按五层骨架写作（L0 生存 / L1 冷启动 / L2 日常操作 /
   L3 架构决策 / L4 治理红线，逐层内容见骨架模板）。
4. 硬约束：禁 TBD/待补/详见代码/适当处理；每个配置项给精确路径与
   当前值；头部写"基于 commit <hash> 快照"；不确定的写"未核验"
   并注明核验方法。

模板 B · 零上下文验收员

你是刚入职的通用 SWE，只拿到一个仓库和一份交接文档，没有任何其他上下文。
按文档完成以下任务，禁止阅读文档未提及之外的资料：
<任务 1：让测试套件全绿>
<任务 2：定位 X 配置，解释它为什么在这个位置>
<任务 3：描述模块 Y 的职责边界与依赖方向>
每完成一步记录：卡壳点（文档缺什么/哪句误导）→ 怎么绕过的。
最后输出缺口清单（逐条定位到五层中的某一层）。

模板 C · 缺口分析（文档 vs 代码双向 diff）

读仓库与交接文档，输出两张表：
①文档说了但代码已不是这样（过期项，给 file:line 证据与 git log 佐证）；
②代码里有但文档从未提及、且新人第一周大概率会撞上的（隐性知识项——
重点扫：环境坑、隐式约定、命名规则、"看起来能改其实不能"的地方）。
每条标层（L0–L4）与优先级。

模板 D · 时效审计

对照 git log（自 <基线 commit> 以来）逐条检查交接文档：哪些小节描述的
东西被这些提交改动了？给出"提交→受影响小节→应改成什么"的修订表。
凡数字（测试数/版本号/文件数）一律以当前实跑为准重新核对。

6 · 反模式清单（见了就打回）

  • 心路历程式开场——历史只保留决策，不保留情绪
  • 贴一张架构图不解释——图不自带语义，每条边都要有文字
  • "详见代码 / 详见 wiki / 详见 Jira"——文档每一节必须能独立成立
  • 把模型生成的"合理推测"当事实写入——必须走先取数后写作
  • 一次写完永不更新——必须配更新协议与快照标注
  • 用同一会话写完自查——必须新会话验收
  • 红线只写"注意安全"——每条红线带违反后果与真实例子
