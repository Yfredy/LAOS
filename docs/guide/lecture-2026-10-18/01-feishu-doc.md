# laos（nanoLAOS）· Linux AgentOS 项目介绍

> Linux 内核的 Agent 治理层——内核强制的能力边界，而不是提示词恳求。
>
> 版本口径：v0.39.0 ｜ 1158 项测试（2026-10-18 实跑）｜ 51 个核心模块 ｜ 17 个受治理驱动 ｜ 116 份调研 ｜ 19,792 篇论文 + 3,724 个开源仓库。
>
> 品牌说明：对外品牌名 **nanoLAOS**；技术名、仓库名、包名 `laos` 与 CLI 名 `laosctl` / `laosd` / `laosweb` 保持不变。

---

## 三十秒版本

今天的 AI Agent 能执行命令、读写文件、操控手机，却拿着用户的全部权限在裸奔。业界的防御是把「不要做危险的事」写进 System Prompt——但提示词是**恳求**，不是**强制**。

laos 是 Linux 内核的 Agent 治理层：**不改内核一行代码**，把 Linux 已经用了五十年的强制原语（namespace / cgroup / seccomp BPF / Landlock）组合起来，给 Agent 的每一次工具调用装上系统调用级别的闸门——能力、作用域、配额、不可逆计价、人审、全量审计。

一句话：**Agent 需要的不是更强的模型，是一个会说「不」的内核。**

# 第一部分 · 由大到小：先把坐标画出来

## 1.1 一次正在发生的迁移

过去两年，AI 产品的主语变了。

- 第一代是 **Assistant**：你问，它答；没有循环，没有工具。
- 第二代是 **Copilot**：它能用工具，但每一步都要你确认。
- 第三代是 **Agent**：它自己循环、自己选工具、自己判断下一步——你给目标，它给执行路径。

这个变化的关键不在于「模型更聪明了」，而在于**执行权转移了**。当 Agent 开始在你的终端里敲命令、在你的手机屏幕上点击、在你的文件系统里读写时，它就不再是一段文本，而是一个**有执行能力的负载**。

操作系统领域对一个「有执行能力的负载」是有成熟答案的：给它身份、给它能力边界、给它资源配额、给它审计流水、把它关进隔离区。这套答案，Linux 已经打磨了五十年。

问题在于：Agent 是新的负载类型，而今天绝大多数 Agent 运行时，**只继承了操作系统的便利，没有继承操作系统的治理**。

## 1.2 Agent 演进的四个阶段

用操作系统的历史做参照，Agent 的演进可以分成四段：

| 阶段 | 形态 | OS 类比 |
|---|---|---|
| 一 | 单 Agent、单轮问答 | DOS：一次只跑一个程序 |
| 二 | 单 Agent、多工具、自主循环 | DOS + 常驻程序（TSR） |
| 三 | 多 Agent 协作、协议互通 | Unix：多进程、管道、IPC |
| 四 | Agent 操作系统：调度、权限、审计、记账成为一等公民 | 成熟期的 Linux |

今天行业大致处在**阶段二到阶段三的过渡期**：Agent 已经会自己循环、会用工具，也开始出现 A2A 这类 Agent 间通信协议；但权限、预算、审计这些「操作系统级」的东西，仍然是各家框架各写各的。

laos 的定位，是**阶段四的一块基础设施原型**——不是要替代 Linux，而是把 Linux 的治理能力延伸到 Agent 这一层。

## 1.3 「AgentOS」这个词，至少有八种含义

调研市面上自称 AgentOS 的项目，会发现它们至少指八种不同的东西：

- 一个 Agent 开发框架（LangChain 类）
- 一个多 Agent 编排器（AutoGen 类）
- 一个带工具调用的运行时（Claude Code 类）
- 一个 Agent 间通信协议（A2A 类）
- 一个端侧智能体手机的操作系统（STEPX Neo 类）
- 一个把 LLM 当内核的学术系统（AIOS / MemGPT 类）
- 一个给 Agent 用的沙箱（E2B 类）
- 一个治理内核（laos 所在的位置）

按**强制力光谱**排，可以分成四级：

| 层级 | 强制方式 | 典型代表 | 边界 |
|---|---|---|---|
| L0 | 约定层：提示词、文档、规范 | 多数 Agent 框架 | 模型可以不听 |
| L1 | 应用层：Hook、审批弹窗 | Claude Code 的 hooks | 进程本身没有 OS 级限制 |
| L2 | 用户态强制层：闸门 + 内核原语组合 | **laos** | 不修改内核，依赖内核既有原语 |
| L3 | 内核 / libOS 层：新调度器、新进程模型 | AIOS 研究、专用 Agent OS | 部署门槛高，生态从零开始 |

laos 明确落在 **L2**。这是一个刻意的工程取舍：L2 能拿到内核级的强制执行，同时保持用户态的迭代速度和部署现实（大量目标场景在 Android / proot 里，拿不到 root，也换不了内核）。

## 1.4 大图景下的那个空位

把上面三件事叠起来看：

- Agent 正在获得执行权；
- 行业正从阶段二走向阶段三；
- 「AgentOS」这个词被八种东西共用，但绝大多数停在 L0/L1。

于是出现一个空位：**谁来对 Agent 的执行说「不」，并且这个「不」是制度性的、可审计的、不依赖模型自觉的？**

这就是 laos 要回答的问题。

# 第二部分 · 由广及近：行业已经替我们论证了一半

## 2.1 五条独立印证

「Agent 需要操作系统级治理」不是 laos 一家之言。项目归档了五条彼此独立的印证链：

1. **学术线**：AIOS（Mei et al., 2024）的标题就是 *LLM Agent Operating System*；MemGPT 把 LLM 当作操作系统来设计，用 page-in/page-out 管理上下文。Agent OS 已经是研究命题。
2. **安全线**：Anthropic 的 containment 研究指出，Agent 需要 OS 级隔离，而不是只靠提示词约束。
3. **商业线**：2026 年 10 月发布的 STEPX Neo / Step AOS 1.0，把感知、记忆、调度、权限列为操作系统的一等公民；它提出的安全四点「可信、可见、可控、可逆」，与 laos 的 sentinel + 不可逆预算几乎逐词同构。
4. **流行论证线**：微信公众号长文《你的二十年系统功底，在 Agent 时代怎么变现？》（AI架构前哨，2026-05-04）用一整篇长文论证「Agent 不替代 OS，Agent 是 OS 之上的新抽象」「Agent 的下半场，不是 ML 的比拼，是系统工程的比拼」。
5. **协议线**：MCP 正在成为 Agent 世界的 POSIX，A2A 正在成为 Agent 间的 IPC。标准化在补上 Agent 的系统接口。

五条线来自不同立场、不同方法，却指向同一个方向：**Agent 需要一套操作系统级的治理语义**。

## 2.2 它们共同的盲区

这五条印证有一个共同边界：**它们都止步于「Agent 运行时像操作系统」**。

- AIOS 解决的是「LLM 怎么调度」；
- MemGPT 解决的是「上下文怎么换页」；
- containment 解决的是「怎么把 Agent 关起来」；
- STEPX Neo 解决的是「手机上的 Agent 怎么产品化」；
- MCP / A2A 解决的是「工具和 Agent 之间怎么通信」。

没有一条系统讨论：**Agent 之间的权限怎么授、预算怎么记、不可逆操作怎么定价、出了事怎么回放。**

MCP 是通信协议，不是权限协议；A2A 是 IPC，不是 capability。它们让 Agent 能互相说话，但没规定谁有资格说什么、说错了谁负责。

这就是 laos 的差异化空位：**不是再做一个 Agent 框架，而是补上治理内核这一层。**

## 2.3 laos 是什么

**laos 是 Linux 内核的 Agent 治理层。**

- 基座是 Linux 内核，不变；
- Agent 是内核之上的新负载，与进程同类；
- laos 是内核治理能力向用户态的延伸：把能力、调度、审计、记账这四件语义，做成 Agent 每次工具调用都要经过的制度。

它不改内核一行代码。它做的是把 Linux 已有的四件强制原语组合起来：

| 原语 | 作用 |
|---|---|
| namespace | 隔离视图：mount / pid / net 各自独立 |
| cgroup v2 | 资源上限：失控的驱动只死自己 |
| seccomp BPF | 系统调用白名单：真拦截，不是君子协定 |
| Landlock | 路径沙箱：未授权目录不可见 |

## 2.4 它不是什么

划清边界和说清定位同样重要：

- **不是 Agent 框架**：laos 不编排 Agent 怎么思考，不提供 prompt 模板，不做 ReAct/CoT 的运行时。
- **不是内核模块**：一行内核代码都不改；laosd 是用户态守护进程。
- **不是 MCP 客户端**：laos 治理 MCP，不实现 MCP；协议本身交给生态。
- **不是沙箱产品**：沙箱只回答「能碰什么」；laos 还回答「能碰多少、值不值得、事后怎么查」。

## 2.5 三个数字

- **39 个语义化版本**：从 2026-09-04 的 v0.1.0 到今天的 v0.39.0，每个版本有 tag、有 Release、有归档。
- **1158 项测试全绿**：主库 `unittest discover` 实跑数字，不是静态统计。
- **17 个受治理驱动**：每一个都过同一套闸门，没有例外。

# 第三部分 · 由浅入深（一）：最小认知模型

## 3.1 三个真实风险

先看问题，不讲概念。

**风险一：一条命令删光家目录。**
一个能干活的 Agent 必须能执行 shell。于是一条构造巧妙的指令、一次模型误判，就可能触发 `rm -rf`。你在 System Prompt 里写「请小心」——但模型没有义务听，文本也可能被注入覆盖。

**风险二：一个恶意 MCP 工具直通隐私。**
装一个 MCP 工具，等于给 Agent 开一扇门。剪贴板、通知、短信、通讯录——如果这个工具本身被劫持，或者它的遥测偷偷外发，你的隐私在没有任何提示的情况下就出去了。

**风险三：不可逆操作没有计价。**
「读取一个文件」和「删除一个文件」「发一条消息」「花一笔钱」，在今天的 Agent 运行时里几乎是同权的。没有记账，就没有预算；没有预算，就没有回放和追责。

三个风险的共同点是：**它们都不是「模型不够聪明」的问题，而是「运行时没有制度」的问题。**

## 3.2 命题：Linux kernel + Agent + MCP

laos 的设计命题可以写成一个等式：

> **Linux kernel + Agent + MCP = Linux AgentOS**

主客关系要读对：

- Linux 内核是基座；
- Agent 是内核之上的新负载；
- MCP 是 Agent 连接外部设备的协议；
- laos 不是「给 Agent 装一个操作系统」，而是**把内核治理延伸到 Agent 这一层**。

这也是为什么 laos 不重写调度器、不造新进程模型：这些内核已经做得足够好。laos 只在用户态补语义层——能力、调度、审计、记账——然后把「设备」交给 MCP 驱动。

## 3.3 一张类比表

| Linux | laos | 含义 |
|---|---|---|
| 进程 | Agent | 有身份、能力集、预算的受管实体 |
| PCB | Agent 控制块 | 能力集、任务作用域、预算余额、审计流水号、污点标记 |
| 系统调用 | MCP tool call | 每一次工具调用都要过闸 |
| 设备驱动 | MCP Server | 17 个驱动 = 17 类受治设备 |
| 内核 | laosd 薄内核 | 只做能力 / 调度 / 审计 / 记账四件语义 |
| insmod | `kernel.load_driver` | 一行外挂任意 MCP 服务器 |

这张表不是修辞，是设计约束：laos 里的每一个概念，都应该能在操作系统教科书里找到对应物，都能用五十年的系统智慧来推理。

## 3.4 五层架构

从上到下：

1. **Agent 层**：业务智能体，消费 syscall 面。
2. **laos 内核（laosd）**：闸门链 + 调度 + 审计 + 预算；51 个模块，纯 Python 标准库。
3. **驱动子进程**：17 个 `drv_*`；重依赖（torch、modelscope 等）全部隔离在各自 venv，主库零依赖。
4. **强制层**：seccomp BPF / cgroup v2 / eBPF + CoW。
5. **Linux / MCP / 外设**：基座不变。

## 3.5 坐标：L2 用户态强制层

再强调一次定位：laos 不是「又一个 Agent 框架」，而是治理内核。它落在强制力光谱的 L2——比提示词和 Hook 硬，比改内核轻。

这个坐标的实际意义是：当你看到任何一个新的「AgentOS」产品，可以用三个问题快速判断它和 laos 的关系：

1. 它的「不」是写在文档里，还是执行在派发前？
2. 它的权限是进程级的，还是应用层的？
3. 它的操作有没有预算和审计，能不能事后回放？

# 第四部分 · 由浅入深（二）：核心机制

## 4.1 闸门链：七道闸 + 一本账

每一次工具调用，从「Agent 想做」到「真正执行」，要过七道闸，最后落一本账。合起来是八环：

| 环 | 名称 | 挡住什么 | 失败语义 |
|---|---|---|---|
| 1 | 能力表（caps） | 没有授权的能力域 | EPERM |
| 2 | task_scope | 路径前缀 / App 白名单 / 时间窗越界 | EACCES |
| 3 | schema 校验 | 参数不合法 | EINVAL |
| 4 | EDQUOT 预算 | 配额耗尽 | EDQUOT |
| 5 | FleetLedger 不可逆计价 | 不可逆操作风险分不足 | EDQUOT / 拒绝 |
| 6 | Jev 预审（opt-in） | 判断「值不值得做」 | 建议 / 拦截 |
| 7 | 确认横幅 | 高危操作未获人审 | 挂起等待确认 |
| 8 | 派发 + 全量审计 | ——（不是闸，是账本） | 留痕，可回放 |

> PPT 第 5 页标题写的是「过七道闸」，指的就是前七环；第八环是派发与审计，不是一道闸，而是一本账。讲的时候主动说明这一点，听众就不会去数环数。

## 4.2 一次拒绝的完整 trace（示意）

场景：Agent 想点击屏幕上某个 App 的按钮。

```
tool_call: screen.tap(x=812, y=1640)
  ├─ 1 caps          screen.* 已授权            → PASS
  ├─ 2 task_scope    pkg:com.example.bank 不在白名单 → DENY (EACCES)
  ├─ 3 schema        （未执行）
  ├─ 4 EDQUOT        （未执行）
  ├─ 5 FleetLedger   （未执行）
  ├─ 6 Jev           （未执行）
  ├─ 7 confirm       （未执行）
  └─ 8 dispatch      （未执行；adb 命令从未发出）
audit: 记录一条 DENY，含调用方、能力、参数摘要、拒绝环、时间戳
```

关键点不是「拒绝」本身，而是：

- 拒绝发生在**派发之前**，设备上什么都没发生；
- 拒绝有**明确的失败语义**（EACCES，不是笼统的「出错了」）；
- 拒绝被**完整记录**，事后可以回放「谁在何时试图用什么权限做什么」。

## 4.3 不可逆计价：先扣账，后派发

第五环是 laos 最有辨识度的设计。

发一条消息、删一个文件、花一笔钱、卸载一个应用——这些操作有一个共同点：**做了就回不去**。对不可逆操作，「事后审计」是不够的，必须在执行前定价。

FleetLedger 的做法是：

1. 给每类不可逆操作一个风险分；
2. 执行前先从 Agent 的账上扣掉；
3. 账上不够，操作不执行；
4. 扣账与执行在同一个事务边界内，避免「扣了没做」或「做了没扣」。

这和操作系统的磁盘配额是同一个思想，只是计价的不是字节，而是**不可逆性**。

## 4.4 强制层三件套

闸门链管的是语义层的决定。但如果驱动子进程本身不听话呢？

| 机制 | 作用 | 一句话 |
|---|---|---|
| seccomp BPF | 进程级系统调用白名单 | 驱动想 fork 一个 curl 外传数据，内核直接杀掉进程 |
| cgroup v2 | CPU / 内存上限 | 驱动死循环或内存泄漏，拖不垮宿主 |
| eBPF + CoW | 行为画像 + 分支隔离 | Agent 在 CoW 分支上试错，不影响主线 |

一句话总结：**语义层靠制度，执行层靠内核。**

## 4.5 用户态为什么能「强制」，以及它的边界

这是技术评审最常被问的问题，必须诚实回答。

laos 的用户态强制，靠的是三件事叠加：

1. **PEP 位置**：所有工具调用必须经过 laosd 派发，Agent 拿不到绕过闸门的执行路径；
2. **内核原语**：驱动子进程被 seccomp/cgroup/Landlock 约束，即使想绕过也没有系统调用权限；
3. **审计闭环**：所有调用留痕，绕过行为可被发现和追责。

它的边界也要说清楚：

- 它防的是**被治理的 Agent 与驱动**，不是防 root 攻击者；
- 它假设 laosd 本身可信；laosd 的完整性属于部署安全，不在当前治理模型内；
- 它是 L2，不是 L3——不提供新的调度器或进程模型。

把边界说清楚，比宣称「绝对安全」更可信。

# 第五部分 · 由浅入深（三）：设备与旗舰案例

## 5.1 驱动即设备

laos 目前有 17 个驱动，按「器官」分三类：

**听觉类（4）**
- `drv_mic`：录音——只由显式 syscall 触发
- `drv_ear`：本地转写 + 音频评估
- `drv_rec`：回放
- `drv_audio`：语音分离 + 回声消除（许可证受限，见 6.4）

**手机操控类（6）**
- `drv_screen`：adb 点击 / 输入 / 截屏 / dump
- `drv_apps`：应用列表与启停
- `drv_notify`：通知
- `drv_comms`：通信录与短信
- `drv_battery`：电量与功耗状态
- `drv_events`：系统事件

**系统与计算类（7）**
- `drv_fs`：受控文件视图
- `drv_proc`：受控进程视图
- `drv_sys`：系统状态
- `drv_npu`：端侧 NPU
- `drv_clef`：密钥管理
- `drv_genie`：代码进化
- `drv_evolve`：元认知实验

三条治理事实：

1. **所有驱动过同一套闸门**：`screen.*` 受 App 白名单，`fs.*` 受路径前缀，没有例外。
2. **外挂驱动默认低能力、低预算**：审计正常后再按需提权，像新硬件建立信任。
3. **零依赖承诺**：`laos/` 核心纯标准库；重依赖只活在驱动子进程的独立 venv。

## 5.2 外挂路线：一行 insmod

任何符合 MCP 协议的服务器，都可以通过 `kernel.load_driver` 外挂进来，像加载内核模块：

```text
kernel.load_driver(name="mobile-mcp", transport="stdio", policy="low-trust")
```

外挂不是「直接给全部权限」，而是走一条信任阶梯：

```text
低能力 + 低预算起步 → 全量审计 → 观察窗 → 按需提权 → 定期复审
```

这条路线我们评估过社区的 `mobile-mcp`，技术上可行；前提是**遥测必须关闭**，这是红线。

## 5.3 旗舰案例：听觉四段漏斗

场景：一个全天候在线的听觉 Agent，怎么「随时待命」又不变成窃听器？

答案是四段漏斗：

1. **常驻检测**：软件 VAD 能量门常开，但不落盘、不留缓存，只回答「现在有没有人声」。功耗在 µW 级。
2. **触发捕获**：有声了，环形缓冲开始记（约 15 秒），唤醒词判断「是不是在叫我」。唤醒词是私有 DTW 模板，纯 JSON，不是声纹。
3. **即时蒸馏**：SenseVoice 本地转写 + 情绪分析，只把文本和标签送进记忆。零上云。
4. **即焚**：原始音频按 TTL 删除，默认 6 小时。

设计的本质是：**音频必须短暂落盘才能送 ASR，但原始音频在系统里活不过 TTL；进记忆的是蒸馏产物，不是声音本身。**

## 5.4 四条红线

一条都不能破：

1. 录音只由显式 syscall 触发；
2. `LAOS_REC=0` 全局禁录，一票否决；
3. 每次 `mic` 调用落审计；
4. ASR 全本地，一个字节不出设备。

行业里已经有同构路线：STEPX Neo 智能体手机用六麦阵列 + 低功耗音频芯片把同一漏斗做进硬件；Apple Watch S12 芯片被验证过类似路径。laos 的差异是：在没有专用芯片的 Android 环境里，用软件把同一套隐私账算平。

# 第六部分 · 由浅入深（四）：判断、证据与工程

## 6.1 Jev 判断层：只回答结构化问题

第六环的 Jev 不是「再叫一个大模型聊天」，而是一个**结构化判断层**：

- **三种判型**：Noul（是非）、Choice（2–255 个选项）、Score（2–10 级）；
- **四个闸门**：高危操作预审、记忆写入过滤、上下文压缩选择、技能质量评估；
- **后端可插拔**：none / rule / cloud / local，全部过同一接口，换后端不改治理面。

它不生成解释，只给结论和置信度——因为治理需要的是可比较、可累计、可校准的判断，而不是一段可能跑题的文字。

**诚实教训**：我们实测过 rule 后端，校准精度 accuracy 只有 **0.519**，高置信桶错误率高达 **33%**——越自信越离谱。于是立了一条规矩：**AUTOGATE 禁配 rule 后端，校准先于自动化**。

一个会把低质量判断自动放行的系统，比没有判断层更危险。

## 6.2 测试与版本

- 主库 **1158 项测试全绿**（2026-10-18 实跑）；
- TDD：先红后绿，每个任务一个 commit；
- SemVer + Keep a Changelog + GitHub Release：一个完整需求波次 = 一次 MINOR；
- 发版自动化：主库测试不绿，`release.py` 直接拒绝发版；介绍性文件的版本/测试锚点自动同步。

## 6.3 复现隔离区：能复现的，全部复现

论文不是引用，是复现。复现区目前六个来源、71 项测试：

| 来源 | 结果 |
|---|---|
| BS.1770-4 响度计量 | R128 校准点 −23.00 LUFS ±0.1；True Peak 4× |
| FxLMS 主动降噪 | 发动机阶次收敛 >20 dB；2×2 多通道约 15 dB |

- **EU AI Act**：职场与教育场景的情绪识别有禁令——laos 的情绪分析能力带场景限制说明。
- **PIPL**：声纹属于敏感个人信息，单独同意是前置条件——不建跨会话声纹库。
- **拒绝伪装采集**：不做「看起来是别的功能、实际在录音」的链路。

合规不是功能清单，是设计约束；有些能力不是「以后再做」，是「不做」。

# 第七部分 · 回到大图景

## 7.1 laos 的生态位

把行业图谱再画一次：

- L0 约定层：提示词、规范、文档——最多。
- L1 应用层：Hook、审批——Claude Code 等。
- L2 用户态强制层：**laos**。
- L3 内核 / libOS：AIOS 研究、专用 Agent OS。

laos 的差异化不在「更聪明的 Agent」，而在**治理语义的完整性**：

| 能力 | 多数框架 | laos |
|---|---|---|
| 权限 | 提示词 / Hook | caps + task_scope，派发前拒绝 |
| 预算 | token 计数器 | EDQUOT + 不可逆计价 |
| 审计 | 日志 | 全量流水，可回放 |
| 隔离 | 容器 / 沙箱 | 内核原语 + 驱动子进程 |
| 设备接入 | 自定义 | MCP + insmod 信任阶梯 |

Linux 内核从来不追求零 bug，它追求的是**每个 bug 的爆炸半径可控**。

变的是工具，不变的是治理。
