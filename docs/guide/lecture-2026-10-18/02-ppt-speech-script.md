## P1 · 封面｜Linux 内核的 Agent 治理层

**页面事实**：主标题「Linux 内核的 Agent 治理层」；副题「内核强制的能力边界，而不是提示词恳求」；等式行「Linux kernel + Agent + MCP —— 不改内核一行代码」；数据块「703 项测试全绿 / 主库 353 · AlwaysOnRec 279 · Repro 71」；页脚「2026-10-05 · v0.9.0」。

**建议时长**：1 分钟

**逐字讲稿**：

> 大家好，今天介绍我做的项目——**laos，全称 Linux AgentOS**。先用一句话说清它是什么：**laos 是 Linux 内核的 Agent 治理层，它做的是内核强制的能力边界，而不是提示词恳求。**
>
> 这句话里有两个关键词。第一个是「治理层」——它不是重写一个操作系统，恰恰相反，它**一行内核代码都不改**；第二个是「强制」——它给 AI Agent 的每一次工具调用装上的是系统调用级别的闸门，不是写在提示词里的「请不要做危险的事」。
>
> 先报三个今天的数字：从 9 月 4 号第一个版本到现在，**39 个语义化版本**；主库 **1158 项测试全绿**；**17 个受治理驱动**，核心包 51 个模块、纯 Python 标准库。封面上的 703 和 v0.9.0 是 10 月 5 号的构建快照，今天以仓库实跑为准。
>
> 接下来 25 分钟，我讲四件事：它要解决什么问题、核心机制长什么样、它和市面上的 AgentOS 有什么不同、以及工程质量是怎么被测试和调研兜住的。

**舞台动作**：开场站定，不急着翻页；说到「一行内核代码都不改」时手势明确否定；说到三个数字时依次伸手指数，节奏放慢。

**过渡句**：要理解 laos 为什么存在，先看今天 Agent 面临的一个真实困境。

**问答预案**：
- Q：为什么叫 laos？A：L-A-O-S，Linux Agent OS 的缩写；对外品牌名 nanoLAOS，技术名和 CLI 名保持 laos 不变。
- Q：一个人做的？A：是，设计、实现、测试、调研全流程单人完成，所以工程纪律（TDD / SemVer / 发版链）是被刻意制度化的。

## P2 · 问题｜Agent 拿着 root 裸奔。

**页面事实**：三条风险台账——R-01「一条 rm -rf 删光家目录」；R-02「恶意 MCP 工具直通隐私」；R-03「不可逆操作无计价」；页脚结论「缺的不是更聪明的模型，是操作系统：能力 · 调度 · 审计 · 记账 · 隔离」。

**建议时长**：2 分钟

**逐字讲稿**：

> 先看问题。今天的 AI Agent——不管是 Claude Code、Cursor 还是各种自动化框架——本质上都运行在用户态，**拿着用户的全部权限在裸奔**。为什么这么说？因为一个能帮你干活的 Agent，必须能执行 shell、读写文件、访问网络、操控手机。于是就有了这张风险台账上的三条。
>
> R-01，**一条 rm -rf 删光家目录**。你把「请小心」写在提示词里——但提示词是文本，模型没有义务听，文本还可能被注入覆盖。
>
> R-02，**一个恶意 MCP 工具直通隐私**。装一个工具，等于开一扇门。剪贴板、通知、短信、通讯录，如果这个工具被劫持，或者它的遥测偷偷外发，你的隐私在没有任何提示的情况下就出去了。
>
> R-03，**不可逆操作无计价**。卸载、发送、删除，和读取几乎是同权的。没有记账，就没有预算；没有预算，就没有回放和追责。
>
> 这里可以借一个很准确的类比：System Prompt 相当于 Agent 的 `/etc/profile`，它是「内核态」配置；而 prompt injection 就是用户态向内核态的**提权攻击**。你用一段文本去防提权，本身就不成立。
>
> 所以结论是页脚这句话：**缺的不是更聪明的模型，是操作系统**——能力、调度、审计、记账、隔离。这些概念操作系统五十年前就解决了，问题是：怎么把它们带给 Agent 这个新负载。

**舞台动作**：三条风险逐条点屏幕，每条停 2 秒；说到「提权攻击」时加重语气；页脚结论放慢，一字一顿。

**过渡句**：laos 的答案是一句话——不改内核一行代码，把 Linux 变成 Agent 的操作系统。这就是我们的命题。

**问答预案**：
- Q：这和容器 / 沙箱有什么区别？A：沙箱只回答「Agent 能碰什么」；laos 还回答「能碰多少、值不值得、事后怎么查」——沙箱是强制层三件套之一，不是全部。
- Q：模型自己变强了还需要这个吗？A：安全边界不能建立在概率上。再可靠的司机也需要刹车，而不是只靠驾照考试。

## P3 · 命题｜Linux kernel + Agent + MCP = Linux AgentOS

**页面事实**：等式「Linux kernel + Agent + MCP = Linux AgentOS」；四件内核原语——namespace（隔离视图）、cgroup v2（资源上限）、seccomp BPF（系统调用白名单）、Landlock（路径沙箱）；底部结论「laosd 是薄内核，只做语义层」。

**建议时长**：2 分钟

**逐字讲稿**：

> laos 的命题可以写成一个公式：**Linux kernel + Agent + MCP = Linux AgentOS**。
>
> 注意这个等式的主客关系：**基座是 Linux 内核**，Agent 和 MCP 是内核之上的新负载和新设备。laos 不是「给 Agent 装一个操作系统」，而是把内核治理延伸到用户态。这个主客关系很重要，说反了，整个项目的定位就错了。
>
> 为什么敢说不改内核？因为 Linux 已经给了我们四件强制原语：**namespace 做隔离视图**，mount、pid、net 各自独立；**cgroup v2 做资源上限**，失控的驱动只死自己；**seccomp BPF 做系统调用白名单**，真拦截，不是君子协定；**Landlock 做路径沙箱**，未授权目录直接不可见。
>
> 这四件都是内核级的强制执行，不是公约。laosd，也就是 laos 的守护进程，把自己定位成「薄内核」：它只做四件语义的事——能力、调度、审计、记账——然后把所有的「设备」留给 MCP 驱动。
>
> 所以这个架构的克制之处在于：**重的东西全在内核，已经在监狱里跑了几十年；语义的东西在用户态，可以快速迭代。** 这是 laos 全部设计的出发点。

**舞台动作**：写等式时用手在空中画「内核在下、Agent 和 MCP 在上」的层次；讲四件原语时逐条点屏，每条配一个短句。

**过渡句**：这个「薄内核」具体怎么薄、又怎么硬？看这张类比表。

**问答预案**：
- Q：为什么不做成真内核模块？A：两个原因。一是迭代速度——用户态治理可以天级发版；二是部署现实——目标场景大量在 Android / proot，拿不到 root。等理念验证完，L3 层可以再讨论 libOS 化。
- Q：零内核改动会不会限死能力？A：landlock + seccomp 对工具调用场景完全够用；真不够的原语才需要考虑内核侧，目前没撞到。

## P4 · 类比｜Linux 的词表，Agent 的语义。

**页面事实**：五行映射——进程 → Agent（PCB · 能力集 · 预算）；系统调用 → MCP tool call（JSON-RPC，每次过闸）；设备驱动 → MCP Server（drv_mic / drv_ear / drv_screen …）；内核 → laosd 薄内核；insmod → kernel.load_driver。

**建议时长**：2 分钟

**逐字讲稿**：

> 这张表是理解 laos 的钥匙，我逐行讲。
>
> 第一行，**进程对应 Agent**——在 laos 里 Agent 不是一段脚本，是一个有身份、有能力集、有预算额度的受管实体，就像进程有 PCB。我们的「Agent 控制块」里存什么？能力集、当前任务作用域、预算余额、审计流水号、污点标记——和 PCB 存寄存器、页表、打开文件是同一思想。
>
> 第二行，**系统调用对应 MCP tool call**——这是全片最核心的一行：每一次工具调用，在 laos 里不是一次普通的 HTTP 请求，是一次要过闸的「系统调用」。
>
> 第三行，**设备驱动对应 MCP Server**——麦克风、耳朵、屏幕，这些都是「设备」，MCP Server 就是它们的驱动。
>
> 第四行，内核对应 laosd 薄内核。第五行最有意思：**insmod 对应 kernel.load_driver**——任何符合 MCP 协议的服务器，可以像加载内核模块一样被外挂进来，一行命令。
>
> 这个类比不是修辞，是设计约束：它意味着 laos 里的每一个概念，你都能在操作系统教科书里找到对应物。顺便说，最近那篇公众号长文也独立得出了同一套映射——System Prompt 是 `/etc/profile`，Agent Loop 是 PID 1，Context Window 是 RAM——这说明这套类比不是我一个人的发明，是行业在收敛。

**舞台动作**：逐行用手指从 Linux 列滑到 laos 列；说到第五行时停顿一下，制造「insmod 也能搬过来」的惊喜感。

**过渡句**：类比表讲的是「像」，下一页讲「硬」——每一次工具调用具体怎么过闸。

**问答预案**：
- Q：MCP 之外的自定义协议能接吗？A：可以写适配驱动，但治理面只认 MCP——协议收敛才能让闸门链通用。
- Q：Agent 的「PCB」具体存什么？A：能力集、任务作用域、预算余额、审计流水号、污点标记——和 PCB 存寄存器 / 页表 / 打开文件是同一思想。

## P5 · 核心机制｜每一次工具调用，过七道闸。

**页面事实**：七道闸的横向流程——能力表 → task_scope → schema → EDQUOT → FleetLedger → Jev → 确认横幅；闸后是派发与全量审计。

**建议时长**：3 分钟（全片核心页，可超时）

**逐字讲稿**：

> 这是全片的核心页，讲 laos 最硬的一个机制：**syscall 闸门链**。
>
> 先校准一个口径：标题写「过七道闸」，指的是派发前的七道检查；第八环是派发之后的全量审计——它不是闸，是一本账。所以完整说法是「七道闸 + 一本账 = 八环链」。
>
> 我按顺序讲，每一道都对应一种真实攻击。
>
> 第一环，**能力表**——这个 Agent 有没有 `screen.*` 这个能力域？没有，直接拒，对应权限位。
>
> 第二环，**task_scope**——就算有 screen 能力，任务作用域限定你只能操作白名单里的 App、只能访问某个路径前缀、只能在某个时间窗内活动；越界即拒。
>
> 第三环，**schema 校验**——参数不合法直接拒，这是 EINVAL 语义。
>
> 第四环，**EDQUOT 预算**——每个 Agent 有配额，配额耗尽即拒，对应磁盘配额思想。
>
> 第五环最有特色，**FleetLedger 不可逆计价**——先扣账、后派发。发一条消息、删一个文件、花一笔钱，这些都是不可逆操作，执行前先把风险分扣掉；账上不够，操作就不执行。
>
> 第六环，**Jev 预审**——一个可选判断层，回答「这件事值不值得做」。下一页不讲它，第 9 页专门讲。
>
> 第七环，**确认横幅**——高危操作必须人审。
>
> 第八环，派发，并且**全量审计**：每一次调用都留痕，事后可以完整回放「谁在何时用掉了什么权限」。
>
> 给大家一个具体例子：Agent 想点击屏幕上的一个按钮，但目标 App 不在白名单里——第二环就拒了，adb 命令根本不会发出去，设备上什么都没发生。而且拒绝有明确的失败语义、有完整的审计记录。
>
> 这八环的意义在于：**安全不依赖任何单点的智能，它是一套制度。**

**舞台动作**：沿七个方框从左到右逐个点；说到第八环时手掌从流程上方划过，表示「账本覆盖全程」；讲拒绝例子时停顿，强调「设备上什么都没发生」。

**过渡句**：制度需要强制执行的人。laos 的「法警」是内核级强制层三件套。

**问答预案**：
- Q：八环全过性能不是爆炸？A：链上全是纯内存检查和一次 JSON 校验，微秒级；贵的是驱动执行本身。1158 项测试里专门有时延用例。
- Q：和 OPA / 策略引擎的区别？A：OPA 是「算完了告诉你违规了」；laos 是「不过闸就不派发」，且不可逆操作带预扣账——策略执行（PEP）和风险定价的合体。
- Q：Jev 是什么？A：一个结构化判断层，第 9 页专门讲；这里先记住它是 opt-in 的、有诚实教训的。

## P6 · 强制层｜强制发生在内核，不在上下文窗口。

**页面事实**：三张规格卡——SPEC-01 seccomp BPF「进程级系统调用白名单。拦截是真实的，不依赖模型自觉」；SPEC-02 cgroup v2「驱动子进程 CPU / 内存上限；驱动失控不拖垮宿主」；SPEC-03 eBPF + CoW「行为画像与执行隔离」。

**建议时长**：1.5 分钟

**逐字讲稿**：

> 闸门链管的是语义层的决定，但任何熟悉系统的人都会问：**如果驱动子进程本身不听话呢？**
>
> 这就是强制层三件套要回答的。
>
> 第一件，**seccomp BPF**——每个驱动子进程在启动时被打包一个系统调用白名单。比如 `drv_screen` 只允许 exec adb 和写 socket；它想 fork 一个 curl 外传数据，内核直接杀掉进程。真拦截，不是约定。
>
> 第二件，**cgroup v2**——每个驱动子进程有独立的 CPU 和内存上限。一个驱动陷入死循环或者内存泄漏，拖不垮宿主。
>
> 第三件，**eBPF profiler 加写时复制**——我们从行为侧给驱动做画像，同时上下文分支用 CoW 隔离，Agent 在分支上试错不影响主线。
>
> 这三件套全是内核既有能力，laos 做的是把它们编排成「驱动治理」的默认姿态。一句话总结：**语义层靠制度，执行层靠内核。**
>
> 也要说清边界：它防的是被治理的 Agent 和驱动，不是防 root 攻击者；laosd 本身的可信属于部署安全。把边界说清楚，比宣称绝对安全更可信。

**舞台动作**：三张卡依次指；讲 seccomp 例子时做一个「掐断」的手势；最后一句放慢。

**过渡句**：制度有了，法警有了，接下来看 laos 管着哪些「设备」。

**问答预案**：
- Q：seccomp 白名单写错了驱动起不来怎么办？A：启动期有 smoke 测试；白名单是 per-driver 声明式配置，改配置不改代码；失败时驱动以 degraded 模式上报而不是静默。
- Q：Windows / macOS 上这套还有吗？A：强制层三件套是 Linux 专属，这是 laos 的部署前提；跨平台沙箱在调研里有对标记录，属远期。

## P7 · 设备｜MCP Server 就是设备驱动。

**页面事实**：驱动名片——`drv_mic / drv_ear`「录音只由显式 syscall 触发；本地 ASR + 韵律评估」；`drv_screen`「adb 屏幕操控 · pkg: 应用白名单收窄」；`drv_notify / comms`「通知与短信——敏感数据走可信闸」；`drv_npu / events` 等。

**建议时长**：2 分钟

**逐字讲稿**：

> laos 现在有 **17 个驱动**，按器官分三类。
>
> 听觉类四个：`drv_mic` 负责录音——注意，录音只由显式 syscall 触发；`drv_ear` 负责本地转写和音频评估；`drv_rec` 负责回放；`drv_audio` 是语音分离和回声消除，许可证有门槛，第 10 页会提。
>
> 手机操控类六个：`drv_screen` 通过 adb 做点击、输入、截屏、dump；`drv_apps` 管应用列表和启停；`drv_notify` 管通知；`drv_comms` 管通信录和短信；`drv_battery` 管电量；`drv_events` 管系统事件。这一整类回应的是「Agent 操作手机」。
>
> 系统与计算类七个：`drv_fs`、`drv_proc`、`drv_sys` 提供受控的文件、进程和系统视图；`drv_npu` 对接端侧 NPU；`drv_clef` 管密钥；`drv_genie` 和 `drv_evolve` 分别是代码进化和元认知实验。
>
> 这里必须强调一个治理事实：**所有这些驱动都过同一套闸门**——`screen.*` 要过 App 白名单，`fs.*` 要过路径前缀，没有例外。
>
> 另一条路线是外挂：任何符合 MCP 协议的第三方服务器，可以用 `kernel.load_driver` 一行 insmod 进来。我们评估过社区的 mobile-mcp，路线可行；但外挂驱动默认低能力、低预算起步，审计正常再按需提权——和 Linux 里新硬件建立信任是一个逻辑。前提是**遥测必须关**。

**舞台动作**：三类驱动用手势分区（左、中、右）；说到「没有例外」时加重；说到 insmod 时做一个「插进去」的动作。

**过渡句**：驱动里最有讲头的是听觉管线——它是 laos 隐私哲学的完整演示。

**问答预案**：
- Q：17 个驱动会不会太多？A：每个驱动对应一类真实「设备」，且都过同一套闸门链——多不是问题，不治理才是。
- Q：第三方 MCP 服务器安全怎么保证？A：外挂默认低能力 + 低预算起步，先过闸跑一段，审计正常再按需提权。

## P8 · 听觉｜常开，但克制。

**页面事实**：四段台账——S-01 常驻检测「PCEN/VAD 低功耗常开，µW 级」；S-02 触发捕获「环形缓冲 + 私有唤醒词 DTW（纯 JSON 非声纹），15s」；S-03 即时蒸馏「SenseVoice 全本地 ASR + 情感，零上云」；S-04 即焚（原始音频按 TTL 删除，默认 6h）。

**建议时长**：3 分钟

**逐字讲稿**：

> 这一页是 laos 隐私哲学的完整演示，我建议放慢速度。
>
> 场景设定：一个全天候在线的听觉 Agent，怎么做到「随时待命」又不变成一个偷录音的窃听器？答案是四段漏斗。
>
> 第一段，**常驻检测**——一个软件 VAD 能量门一直开着，但它不落盘、不留缓存，只回答一个问题：「现在有没有人声？」功耗在微瓦级，因为功耗预算决定一切。没声，什么都没有。
>
> 第二段，**触发捕获**——有声了，环形缓冲开始记，大约 15 秒；同时唤醒词模型判断「是不是在叫我」。注意这个唤醒词是私有的 DTW 模板，存成纯 JSON——**它不是声纹**，不做身份识别。
>
> 第三段，**即时蒸馏**——确认要处理，SenseVoice 本地转写、情绪分析，**只把文本和标签送进记忆系统**。零上云，一个字节不出设备。
>
> 第四段，**即焚**——原始音频按 TTL 删除，默认 6 小时，不留。
>
> 注意这个设计的本质：**音频必须短暂落盘才能送 ASR，但原始音频在系统里活不过 TTL；进记忆的是蒸馏产物，不是声音本身。**
>
> 配合四条红线：录音只由显式 syscall 触发；`LAOS_REC=0` 一票否决全局禁录；每次 mic 调用落审计；ASR 全本地。
>
> 这不是我一个人的偏执。STEPX Neo 智能体手机用六麦阵列加低功耗音频芯片，把同一个漏斗做进了硬件；Apple Watch 的 S12 芯片也被验证过同构路线。区别在于：laos 在没有专用芯片的 Android 环境里，用软件把同一套隐私账算平了。

**舞台动作**：四段用手指从上到下切；说到「它不是声纹」时明确摇头；四条红线逐条数；最后一句放慢。

**过渡句**：漏斗解决「耳朵」的问题，但 Agent 还需要「判断力」——这就是 Jev 层，以及它最值得讲的一个教训。

**问答预案**：
- Q：即焚了，用户想回味上周的对话怎么办？A：回味的是日记文本，不是音频——隐私和便利冲突时隐私优先。要留音频的场景，TTL 可以设长，但要过单独同意门。
- Q：VAD 误触发怎么办？A：能量门 + 滞回 + 最短段过滤；误触发的代价是「多跑一次 ASR」，不是「多录一段音」——失败方向是安全的。
- Q：PCEN 是什么？A：按信道能量归一化，比裸能量门抗噪；轻量版在实验分支，主库先用能量 + 滞回跑通链路。

## P9 · 判断｜快问快答判断层，校准先行。

**页面事实**：三张卡——TYPES「三判型：Noul 是非 · Choice 2–255 选项 · Score 2–10 级」；GATES「四闸门：高危预审 · 记忆过滤 · 压缩选择 · 技能质量」；CALIBRATION「rule 后端 accuracy 0.519；高置信桶错误率 33% → AUTOGATE 禁配 rule」；底部「判断后端可插拔（none / rule / cloud / local）——校准数据说了算」。

**建议时长**：2 分钟

**逐字讲稿**：

> 闸门链的第六环留了一个位置给「判断」——这件事该不该做、值不值得做、可不可逆。这个角色叫 Jev。
>
> 它的设计有一个反直觉的点：**不生成文本，只回答结构化问题。** 三种判型：Noul 回答是非，Choice 在 2 到 255 个选项里选，Score 打 2 到 10 级。为什么这样设计？因为治理要的是可比较、可累计、可校准的结论，不是一段可能跑题的解释。
>
> 它挂在四个闸门上：高危操作预审、记忆写入过滤、上下文压缩选择、技能质量评估。后端可插拔——none、rule、cloud、local，全部过同一接口，换后端不改治理面。
>
> 但这页最重要的内容是右下角这个**诚实教训**：我们实测过 rule 后端——一个本地规则模型——校准精度 accuracy 只有 **0.519**，更糟的是高置信桶的错误率高达 **33%**——它越自信越离谱。
>
> 所以 laos 立了一条规矩：**AUTOGATE 禁配 rule 后端，校准先于自动化。** 一个会把低质量判断自动放行的系统，比没有判断层更危险。
>
> 这组数据是实测口径，不是厂商宣称值。顺带说，这也是整个项目的气质：**宁可记一个难看数字，不要一个漂亮故事。**

**舞台动作**：三张卡依次点；说到 0.519 和 33% 时停顿两秒，让数字落地；最后一句放慢。

**过渡句**：这套判断和治理不是拍脑袋设计的——背后是 19,792 篇论文和 3,724 个开源项目。

**问答预案**：
- Q：0.519 是什么概念？A：约等于抛硬币。高置信桶 33% 错误率意味着「它说非常确定的时候，三分之一是错的」——所以必须人审或换更强后端。
- Q：Jev 现在用哪个后端？A：默认 none → rule 零依赖兜底；云端和端侧 ONNX 后端 opt-in，全部过同一接口。

## P10 · 证据｜设计不拍脑袋。

**页面事实**：四个数字——19,792（双会议全量论文遍历）、9,908（多顶会主题切片 · 35 venue）、3,724（开源仓库普查）、76（采纳总纲映射）；底部「Interspeech 5,507 + ICASSP 14,285；落地 33 / 推荐 23 / 不做 20」。

**建议时长**：2 分钟

**逐字讲稿**：

> laos 的每一个设计决定都有出处，这一页讲家底。
>
> 第一，**论文语料**：我们把语音领域两大顶会 Interspeech 和 ICASSP 做了全量遍历——Interspeech 5,507 篇，ICASSP 14,285 篇，合计 **19,792 篇**，元数据 100% 覆盖。
>
> 第二，**主题切片**：35 个 venue，9,908 条，用来做数据源的结构性地图。
>
> 第三，**开源普查**：3,724 个 GitHub 仓库，按 topic 切片去噪。
>
> 第四，**采纳总账**：每一条调研都落成三条之一——已落地、推荐待做、明确不做；「不做」的也写清理由。这个 76 是 10 月 5 号的快照口径；到今天，调研文档已经积累到 **116 份**，总账数字以 capstone 回源为准。台上我更愿意用两个稳定锚：**19,792 篇论文、3,724 个仓库。**
>
> 举两个例子说明这套家底怎么用。
>
> Speaker 分离为什么用 7 带谱质心做到达顺序聚类？因为调研发现，所有要做「身份」的方案都会撞上 PIPL 敏感个人信息红线；于是我们选了会话内、无身份语义的那条路。
>
> JAEC 回声消除为什么只放在驱动侧可选位？因为它的许可证是 CC BY-NC，禁商用——这种硬门槛不试不知道，试过就必须记账。
>
> **不是拍脑袋设计，是 19,792 篇论文加 3,724 个仓库给的底气。**

**舞台动作**：四个数字从左到右点；说到 76 时主动摆手，标注「快照」；两个案例各讲一句就停，不展开。

**过渡句**：光有论文不够，能复现的论文我们全部复现——这是 71 项测试的复现隔离区。

**问答预案**：
- Q：19,792 篇都读了？A：元数据和摘要全量入库，按主题切片筛出相关子集精读；全量覆盖保证「不会有漏网的瞎打」。
- Q：调研文档写来干嘛，能当饭吃？A：对外是 design by evidence 的证明；对内是跨会话记忆——没有这套文档，我记不住两周前为什么这么决定。

## P11 · 复现｜能复现的，全部复现。

**页面事实**：六条复现台账——F-01 BS.1770-4 响度计量（R128 校准点 −23.00 LUFS ±0.1 · True Peak 4×）；F-02 FxLMS 主动降噪（发动机阶次收敛 >20 dB · 2×2 多通道约 15 dB）；F-03 头部朝向论文全管线（镜像源法 + STFT 相位 + BiGRU-MHSA · 冒烟 56.5°）；F-04 PhaseCoder；F-05 Pipecat 帧管道；F-06 unique_lock 语义。

**建议时长**：2 分钟

**逐字讲稿**：

> 这一页讲 laos 最「笨」也最真的部分：**论文复现隔离区**。
>
> 调研发现一篇有用的论文怎么办？我们的做法是进 Repro 隔离区，用测试把它复现出来，跑通了才谈落地。现在已经复现了六个来源、**71 项测试**。
>
> 举三个。
>
> 第一，**BS.1770-4 响度计量**——这是广播级标准。我们的实现在 R128 校准点上是 **−23.00 LUFS，误差 ±0.1**，True Peak 做 4 倍过采样。这个数字是和行业标准对过表的。
>
> 第二，**FxLMS 主动降噪**——一个经典自适应滤波算法，纯 Python 实现，发动机阶次收敛超过 **20 分贝**，2×2 多通道大约 15 分贝。
>
> 第三，**说话人头部朝向估计**——复现了一篇论文的完整管线：镜像源法、STFT 相位、BiGRU-MHSA；在冒烟测试集上 holdout 精度 **56.5 度**。
>
> 注意这三个数字的策略：**论文里写的数字我们不当断言，自己跑出来的才记。** 跑不动的——比如原论文 4 万个样本我们只跑得起百样本冒烟——偏差全记档，等比缩距并写明。
>
> 还有 PhaseCoder 那个更典型：为了验证麦位编码实现，我们逐行对齐了官方 JAX 源码，跨实现 diff 为零。
>
> 这套方法论的纪律就四句话：**TDD、零新依赖、论文数字不作断言、偏差全记档。**

**舞台动作**：三条复现逐条点；说到 56.5° 时主动补一句「这是冒烟集，不是刷指标」；最后四句像口号一样放慢。

**过渡句**：最后讲这套东西怎么管理自己——版本治理。

**问答预案**：
- Q：56.5 度是不是很差？A：是冒烟 holdout，目的验证「管线真的在学」而不是刷指标；全量数据算力不够，这点在记档里写明了。
- Q：为什么复现区要隔离？A：复现代码常有实验依赖；隔离保证主库「纯标准库」承诺不破，采纳的再按裁决搬进主库。

## P12 · 收尾｜能力边界写在内核里，不写在提示词里。

**页面事实**：主结论「能力边界写在内核里，不写在提示词里」；版本治理行「v0.1 → v0.9 语义化版本 · Keep a Changelog · GitHub Release 页」；纪律「一个完整需求波次 = 一次 MINOR；合规红线前置（EU AI Act / PIPL / 拒绝伪装采集）」；NEXT「drv_screen 真机验收 → 外挂驱动 PoC（mobile-mcp）→ bs1770 响度合入主库」。

**建议时长**：1.5 分钟

**逐字讲稿**：

> 最后一页，讲 laos 怎么管理自己，以及下一步去哪。
>
> 版本治理：**语义化版本 + Keep a Changelog + GitHub Release 页**。从 9 月 4 号第一个版本到今天，**39 个 MINOR**，每个版本有 tag、有 Release、有归档。PPT 上写的是 v0.1 到 v0.9，那是 10 月 5 号的快照；今天是 **v0.39.0**。纪律是「一个完整需求波次等于一次 MINOR」，不允许把半成品发上去。
>
> 合规红线单独列：EU AI Act 对职场和教育场景的情绪识别有禁令——所以 laos 的情绪分析能力有场景限制说明；PIPL 把声纹列为敏感个人信息，需要单独同意——所以 laos 不建跨会话声纹库。这是红线，不是功能欠缺。
>
> 路线图三件事：`drv_screen` 的多轮真机验收；外挂驱动的 PoC，用 mobile-mcp 但遥测必须关；以及更多论文复现——PPT 上写的「bs1770 响度合入主库」已经完成了，现在在队列里的是下一批复现。
>
> 最后用一句话收尾：**Agent 需要的不是更强的模型，是一个会说「不」的内核。** 模型的聪明是概率，治理的边界才是确定性。laos 就是用 Linux 五十年的确定性强制度，去约束 Agent 时代概率性的不确定。
>
> 我的介绍就到这里，谢谢大家。

**舞台动作**：说到「v0.39.0」时明确纠正封面；三条合规红线用手指数；最后一句站定，不看书，收在「谢谢大家」。

**过渡句**：（进入问答）

**问答预案**：
- Q：项目最大的风险？A：单人项目的持续性风险——缓解是文档化：116 份调研 + 计划库 + 发版链全自动，换个人看 ONBOARDING 能直接上手。
- Q：会开源 / 商业化吗？A：仓库在 GitHub 公开（Yfredy/LAOS）；治理内核本身开源，商业空间在驱动生态和合规服务——但那是后话。
- Q：和 AIOS、Anthropic containment 什么关系？A：它们是调研归档里的印证链——学术线、安全线、商业线都指向同一个结论：Agent 需要操作系统级治理。laos 是把这个结论做成可运行原型。
