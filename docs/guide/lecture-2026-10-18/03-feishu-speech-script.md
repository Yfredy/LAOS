# 第一部分 · 由大到小：先把坐标画出来（约 5 分钟）

## 1.1 一次正在发生的迁移（⚡ 精简版保留前半）

**讲什么**：Assistant → Copilot → Agent 的三代变化，本质是执行权转移。

**逐字稿**：

> 过去两年，AI 产品的主语变了。第一代是 Assistant：你问它答，没有循环，没有工具。第二代是 Copilot：它能用工具，但每一步都要你确认。第三代是 Agent：它自己循环、自己选工具、自己判断下一步——你给目标，它给执行路径。
>
> 这个变化的关键，不是「模型更聪明了」，而是**执行权转移了**。当 Agent 开始在你的终端里敲命令、在你的手机屏幕上点击、在你的文件系统里读写，它就不再是一段文本，而是一个有执行能力的负载。
>
> 操作系统对一个「有执行能力的负载」是有成熟答案的：身份、能力边界、资源配额、审计流水、隔离区。Linux 把这套答案打磨了五十年。问题在于：Agent 是新的负载类型，而今天绝大多数 Agent 运行时，**只继承了操作系统的便利，没有继承操作系统的治理**。

**过渡**：把 Agent 放进操作系统的历史里，会看到四个阶段。

## 1.2 Agent 演进的四个阶段

**讲什么**：DOS → DOS+TSR → Unix → 成熟 Linux；laos 是阶段四的基础设施原型。

**逐字稿**：

> 用操作系统的历史做参照，Agent 的演进可以分四段。
>
> 第一段，单 Agent、单轮问答，像 DOS：一次只跑一个程序。第二段，单 Agent、多工具、自主循环，像 DOS 加常驻程序。第三段，多 Agent 协作、协议互通，像 Unix：多进程、管道、IPC。第四段，Agent 操作系统：调度、权限、审计、记账成为一等公民，像成熟期的 Linux。
>
> 今天行业大致在**阶段二到阶段三的过渡期**：Agent 已经会自己循环、会用工具，也开始出现 A2A 这类 Agent 间通信协议；但权限、预算、审计这些操作系统级的东西，仍然是各家框架各写各的。
>
> laos 的定位，是**阶段四的一块基础设施原型**——不是替代 Linux，而是把 Linux 的治理能力延伸到 Agent 这一层。

**过渡**：但「AgentOS」这个词，今天至少指八种东西。

## 1.3 「AgentOS」的八种含义与强制力光谱

**讲什么**：八种自称 AgentOS 的形态；L0–L3 四级；laos 在 L2。

**逐字稿**：

> 调研市面上自称 AgentOS 的项目，会发现它们至少指八种不同的东西：Agent 开发框架、多 Agent 编排器、带工具调用的运行时、Agent 间通信协议、端侧智能体手机的操作系统、把 LLM 当内核的学术系统、给 Agent 用的沙箱，以及治理内核——laos 在最后这一类。
>
> 按**强制力光谱**排，可以分四级。L0 是约定层：提示词、文档、规范，多数 Agent 框架在这里，模型可以不听。L1 是应用层：Hook、审批弹窗，Claude Code 的 hooks 在这里，但进程本身没有 OS 级限制。L2 是用户态强制层：闸门加内核原语组合，**laos 在这里**。L3 是内核或 libOS 层：新调度器、新进程模型，AIOS 研究和专用 Agent OS 在这里，部署门槛高、生态从零开始。
>
> laos 明确落在 L2。这是刻意的取舍：L2 能拿到内核级的强制执行，同时保持用户态的迭代速度和部署现实——大量目标场景在 Android / proot 里，拿不到 root，也换不了内核。

**过渡**：把这三件事叠起来，会看到一个空位。

## 1.4 大图景下的那个空位（⚡ 精简版保留）

**讲什么**：全篇的悬念——谁对 Agent 说「不」，且这个「不」是制度性的。

**逐字稿**：

> 把上面三件事叠起来看：Agent 正在获得执行权；行业正从阶段二走向阶段三；「AgentOS」这个词被八种东西共用，但绝大多数停在 L0 和 L1。
>
> 于是出现一个空位：**谁来对 Agent 的执行说「不」，并且这个「不」是制度性的、可审计的、不依赖模型自觉的？**
>
> 这就是 laos 要回答的问题。接下来的第二部分，先看行业已经替我们论证了什么。

**收尾/过渡**：行业不是没有答案，而是答案停在了半路。

# 第二部分 · 由广及近：行业已经替我们论证了一半（约 6 分钟）

## 2.1 五条独立印证

**讲什么**：学术、安全、商业、流行论证、协议五条线，指向同一结论。

**逐字稿**：

> 「Agent 需要操作系统级治理」不是 laos 一家之言。项目归档了五条彼此独立的印证链。
>
> 学术线：AIOS 的论文标题就是 LLM Agent Operating System；MemGPT 把 LLM 当操作系统设计，用 page-in/page-out 管理上下文。Agent OS 已经是研究命题。
>
> 安全线：Anthropic 的 containment 研究指出，Agent 需要 OS 级隔离，而不是只靠提示词。
>
> 商业线：2026 年 10 月发布的 STEPX Neo，把感知、记忆、调度、权限列为操作系统的一等公民；它提的安全四点「可信、可见、可控、可逆」，和 laos 的 sentinel 加不可逆预算几乎逐词同构。
>
> 流行论证线：那篇公众号长文《你的二十年系统功底，在 Agent 时代怎么变现？》——「Agent 不替代 OS，是 OS 之上的新抽象」「Agent 的下半场，不是 ML 的比拼，是系统工程的比拼」。
>
> 协议线：MCP 正在成为 Agent 世界的 POSIX，A2A 正在成为 Agent 间的 IPC。
>
> 五条线来自不同立场、不同方法，却指向同一个方向。

**过渡**：但五条线有一个共同的边界。

## 2.2 它们共同的盲区

**讲什么**：都止步于「运行时像 OS」；没有权限、预算、审计语义。

**逐字稿**：

> 这五条印证都止步于「Agent 运行时像操作系统」。AIOS 解决的是「LLM 怎么调度」；MemGPT 解决的是「上下文怎么换页」；containment 解决的是「怎么把 Agent 关起来」；STEPX Neo 解决的是「手机上的 Agent 怎么产品化」；MCP 和 A2A 解决的是「工具和 Agent 之间怎么通信」。
>
> 没有一条系统讨论：**Agent 之间的权限怎么授、预算怎么记、不可逆操作怎么定价、出了事怎么回放。**
>
> MCP 是通信协议，不是权限协议；A2A 是 IPC，不是 capability。它们让 Agent 能互相说话，但没规定谁有资格说什么、说错了谁负责。
>
> 这就是 laos 的差异化空位：**不是再做一个 Agent 框架，而是补上治理内核这一层。**

**过渡**：所以，laos 到底是什么？

## 2.3 laos 是什么（⚡ 精简版保留）

**讲什么**：一句话定义 + 四件内核原语。

**逐字稿**：

> **laos 是 Linux 内核的 Agent 治理层。** 基座是 Linux 内核，不变；Agent 是内核之上的新负载，与进程同类；laos 是内核治理能力向用户态的延伸——把能力、调度、审计、记账这四件语义，做成 Agent 每次工具调用都要经过的制度。
>
> 它不改内核一行代码，靠的是把 Linux 已有的四件强制原语组合起来：**namespace** 做隔离视图，mount、pid、net 各自独立；**cgroup v2** 做资源上限，失控的驱动只死自己；**seccomp BPF** 做系统调用白名单，真拦截；**Landlock** 做路径沙箱，未授权目录不可见。
>
> 这四件都是内核级的强制执行，不是公约。

**过渡**：说清它是什么之后，更要说清它不是什么。

## 2.4 它不是什么

**讲什么**：四条边界——不是框架、不是内核模块、不是 MCP 客户端、不是沙箱产品。

**逐字稿**：

> 划清边界和说清定位同样重要。
>
> 它不是 Agent 框架：laos 不编排 Agent 怎么思考，不提供 prompt 模板，不做 ReAct / CoT 的运行时。
>
> 它不是内核模块：一行内核代码都不改，laosd 是用户态守护进程。
>
> 它不是 MCP 客户端：laos 治理 MCP，不实现 MCP，协议本身交给生态。
>
> 它也不是沙箱产品：沙箱只回答「能碰什么」；laos 还回答「能碰多少、值不值得、事后怎么查」。

**过渡**：用三个数字给这个定位一个质感。

## 2.5 三个数字

**讲什么**：39 版本、1158 测试、17 驱动。

**逐字稿**：

> 三个数字。第一，**39 个语义化版本**：从 2026 年 9 月 4 号的 v0.1.0 到今天的 v0.39.0，每个版本有 tag、有 Release、有归档。第二，**1158 项测试全绿**：主库 `unittest discover` 实跑，不是静态统计。第三，**17 个受治理驱动**：每一个都过同一套闸门，没有例外。
>
> 三个数字放在一起，说明的不是「项目很大」，而是「项目在被制度约束着长大」。

**收尾/过渡**：大图景和定位都讲完了，接下来从最小认知模型开始往下钻。

# 第三部分 · 由浅入深（一）：最小认知模型（约 5 分钟）

## 3.1 三个真实风险（⚡ 精简版保留）

**讲什么**：rm -rf、恶意 MCP、不可逆无计价；共同点是运行时没有制度。

**逐字稿**：

> 先看问题，不讲概念。
>
> 风险一，一条命令删光家目录。一个能干活的 Agent 必须能执行 shell；于是一条构造巧妙的指令、一次模型误判，就可能触发 `rm -rf`。你在 System Prompt 里写「请小心」——但模型没有义务听，文本也可能被注入覆盖。
>
> 风险二，一个恶意 MCP 工具直通隐私。装一个 MCP 工具，等于给 Agent 开一扇门。剪贴板、通知、短信、通讯录——如果这个工具被劫持，或者它的遥测偷偷外发，隐私在没有任何提示的情况下就出去了。
>
> 风险三，不可逆操作没有计价。读取一个文件和删除一个文件、发一条消息、花一笔钱，在今天的 Agent 运行时里几乎是同权的。没有记账，就没有预算；没有预算，就没有回放和追责。
>
> 三个风险的共同点是：**它们都不是「模型不够聪明」的问题，而是「运行时没有制度」的问题。**

**过渡**：laos 的答案，可以写成一个等式。

## 3.2 命题：Linux kernel + Agent + MCP

**讲什么**：等式与主客关系；为什么用户态补语义层。

**逐字稿**：

> **Linux kernel + Agent + MCP = Linux AgentOS。**
>
> 主客关系要读对：Linux 内核是基座；Agent 是内核之上的新负载；MCP 是 Agent 连接外部设备的协议；laos 不是「给 Agent 装一个操作系统」，而是把内核治理延伸到 Agent 这一层。
>
> 这也是为什么 laos 不重写调度器、不造新进程模型：这些内核已经做得足够好。laos 只在用户态补语义层——能力、调度、审计、记账——然后把设备交给 MCP 驱动。

**过渡**：理解这个等式最快的办法，是一张类比表。

## 3.3 一张类比表

**讲什么**：五行映射，逐个讲。

**逐字稿**：

> 第一行，进程对应 Agent——它不是脚本，是有身份、能力集、预算的受管实体。第二行，系统调用对应 MCP tool call——每一次调用都要过闸。第三行，设备驱动对应 MCP Server——17 个驱动就是 17 类受治设备。第四行，内核对应 laosd 薄内核——只做能力、调度、审计、记账四件语义。第五行，insmod 对应 `kernel.load_driver`——一行外挂任意 MCP 服务器。
>
> 这张表不是修辞，是设计约束：laos 里的每一个概念，都应该能在操作系统教科书里找到对应物，都能用五十年的系统智慧来推理。
>
> 顺便说，那篇公众号长文也独立得出了同一套映射——System Prompt 是 `/etc/profile`，Agent Loop 是 PID 1，Context Window 是 RAM。这说明这套类比不是我一个人的发明，是行业在收敛。

**过渡**：类比给出词表，分层给出结构。

## 3.4 五层架构

**讲什么**：Agent / laosd / 驱动子进程 / 强制层 / Linux 基座。

**逐字稿**：

> 从上到下五层。第一层，Agent 层：业务智能体，消费 syscall 面。第二层，laos 内核 laosd：闸门链、调度、审计、预算；51 个模块，纯 Python 标准库。第三层，驱动子进程：17 个 `drv_*`，重依赖全部隔离在各自 venv，主库零依赖。第四层，强制层：seccomp BPF、cgroup v2、eBPF 加 CoW。第五层，Linux、MCP 和外设：基座不变。
>
> 这个分层最重要的信息是：**复杂度和依赖被推到了驱动子进程，主库保持轻；强制执行被推到了内核，语义层保持快。**

**过渡**：最后给这个项目一个精确坐标。

## 3.5 坐标：L2 用户态强制层

**讲什么**：不是又一个框架，是治理内核；三个判断问题。

**逐字稿**：

> 再强调一次定位：laos 不是「又一个 Agent 框架」，而是治理内核，落在强制力光谱的 L2——比提示词和 Hook 硬，比改内核轻。
>
> 这个坐标的实际意义是：当你看到任何一个新的 AgentOS 产品，可以用三个问题快速判断它和 laos 的关系。第一，它的「不」是写在文档里，还是执行在派发前？第二，它的权限是进程级的，还是应用层的？第三，它的操作有没有预算和审计，能不能事后回放？
>
> 三个问题都答「是」，它在 laos 这一层；只答前两个，它在 L1；一个都答不上，它还在 L0。

**收尾/过渡**：模型建好了，下一部分进入最核心的机制。

# 第四部分 · 由浅入深（二）：核心机制（约 8 分钟）

## 4.1 闸门链：七道闸 + 一本账（⚡ 精简版保留，核心节）

**讲什么**：逐环讲，每环对应一种攻击；最后强调制度。

**逐字稿**：

> 这是全项目的核心机制。先校准口径：**七道闸 + 一本账 = 八环链**。前七环是派发前的检查，第八环是派发后的全量审计——它不是闸，是账本。
>
> 第一环，能力表：没有授权的能力域直接拒，对应权限位。第二环，task_scope：路径前缀、App 白名单、时间窗，越界即拒。第三环，schema 校验：参数不合法直接拒，这是 EINVAL 语义。第四环，EDQUOT 预算：配额耗尽即拒。第五环，FleetLedger 不可逆计价：先扣账、后派发——发消息、删文件、花钱，执行前先把风险分扣掉，账上不够就不执行。第六环，Jev 预审：可选判断层，回答「值不值得做」。第七环，确认横幅：高危操作必须人审。第八环，派发，并且全量审计：每一次调用留痕，事后能完整回放「谁在何时用掉了什么权限」。
>
> 八环的意义在于：**安全不依赖任何单点的智能，它是一套制度。**

**过渡**：制度长什么样？看一次拒绝的完整路径。

## 4.2 一次拒绝的完整 trace（示意）

**讲什么**：screen.tap 被 pkg 白名单拒绝；强调派发前拒绝、明确语义、完整审计。

**逐字稿**：

> 场景：Agent 想点击屏幕上某个 App 的按钮。
>
> 调用进来，第一环能力表：`screen.*` 已授权，通过。第二环 task_scope：目标包名 `com.example.bank` 不在白名单，拒绝，失败语义是 EACCES。后面的 schema、预算、计价、Jev、确认、派发全部不执行——**adb 命令从未发出，设备上什么都没发生。**
>
> 审计里留下一条 DENY，包含调用方、能力、参数摘要、拒绝环、时间戳。
>
> 关键点不是「拒绝」本身，而是三件事：拒绝发生在派发之前；拒绝有明确的失败语义，不是笼统的「出错了」；拒绝被完整记录，事后可以回放。

**过渡**：八环里最有辨识度的是第五环——不可逆计价。

## 4.3 不可逆计价：先扣账，后派发

**讲什么**：风险分、预扣、事务边界、与磁盘配额同构。

**逐字稿**：

> 发一条消息、删一个文件、花一笔钱、卸载一个应用——这些操作有一个共同点：**做了就回不去。** 对不可逆操作，事后审计是不够的，必须在执行前定价。
>
> FleetLedger 的做法是四步：给每类不可逆操作一个风险分；执行前先从 Agent 的账上扣掉；账上不够，操作不执行；扣账与执行在同一个事务边界内，避免「扣了没做」或「做了没扣」。
>
> 这和操作系统的磁盘配额是同一个思想，只是计价的不是字节，而是**不可逆性**。

**过渡**：语义层的制度之外，还要有执行层的法警。

## 4.4 强制层三件套

**讲什么**：seccomp、cgroup、eBPF+CoW；语义层靠制度，执行层靠内核。

**逐字稿**：

> 闸门链管的是语义层的决定。但如果驱动子进程本身不听话呢？
>
> seccomp BPF：每个驱动子进程启动时被打包一个系统调用白名单。驱动想 fork 一个 curl 外传数据，内核直接杀掉进程。cgroup v2：每个驱动有独立的 CPU 和内存上限，死循环或内存泄漏拖不垮宿主。eBPF 加 CoW：行为画像加分支隔离，Agent 在分支上试错不影响主线。
>
> 一句话：**语义层靠制度，执行层靠内核。**

**过渡**：技术评审一定会问：用户态凭什么能「强制」？

## 4.5 用户态为什么能强制，以及它的边界

**讲什么**：PEP 位置、内核原语、审计闭环；三条边界。

**逐字稿**：

> 三个东西叠加。第一，**PEP 位置**：所有工具调用必须经过 laosd 派发，Agent 拿不到绕过闸门的执行路径。第二，**内核原语**：驱动子进程被 seccomp、cgroup、Landlock 约束，想绕过也没有系统调用权限。第三，**审计闭环**：所有调用留痕，绕过行为可被发现和追责。
>
> 边界也要说清楚：它防的是被治理的 Agent 和驱动，不是防 root 攻击者；它假设 laosd 本身可信，laosd 的完整性属于部署安全；它是 L2，不提供新的调度器或进程模型。
>
> 把边界说清楚，比宣称绝对安全更可信。

**收尾/过渡**：机制讲完，下一部分看它管的具体设备。

# 第五部分 · 由浅入深（三）：设备与旗舰案例（约 6 分钟）

## 5.1 驱动即设备

**讲什么**：17 个驱动三类；三条治理事实。

**逐字稿**：

> laos 目前有 17 个驱动，按器官分三类。
>
> 听觉类四个：`drv_mic` 录音，只由显式 syscall 触发；`drv_ear` 本地转写和音频评估；`drv_rec` 回放；`drv_audio` 语音分离和回声消除，许可证受限。
>
> 手机操控类六个：`drv_screen`、`drv_apps`、`drv_notify`、`drv_comms`、`drv_battery`、`drv_events`，回应「Agent 操作手机」。
>
> 系统与计算类七个：`drv_fs`、`drv_proc`、`drv_sys` 提供受控视图；`drv_npu` 对接端侧 NPU；`drv_clef` 管密钥；`drv_genie` 和 `drv_evolve` 是代码进化和元认知实验。
>
> 三条治理事实：所有驱动过同一套闸门，`screen.*` 受 App 白名单，`fs.*` 受路径前缀，没有例外；外挂驱动默认低能力、低预算，审计正常再提权；核心包纯标准库，重依赖只活在驱动子进程的 venv。

**过渡**：外挂路线值得单独说，因为它是生态的入口。

## 5.2 外挂路线：一行 insmod

**讲什么**：kernel.load_driver、信任阶梯、遥测红线。

**逐字稿**：

> 任何符合 MCP 协议的服务器，都可以通过 `kernel.load_driver` 外挂进来，像加载内核模块。但外挂不是「直接给全部权限」，而是走一条信任阶梯：低能力加低预算起步，全量审计，观察窗，按需提权，定期复审。
>
> 这条路线我们评估过社区的 mobile-mcp，技术上可行；前提是**遥测必须关闭**，这是红线。

**过渡**：17 个驱动里，最能说明 laos 气质的是听觉管线。

## 5.3 听觉四段漏斗（⚡ 精简版保留）

**讲什么**：四段漏斗 + 四条红线 + 行业印证。

**逐字稿**：

> 场景：一个全天候在线的听觉 Agent，怎么「随时待命」又不变成窃听器？
>
> 四段漏斗。第一段，常驻检测：软件 VAD 能量门常开，但不落盘、不留缓存，只回答「现在有没有人声」，功耗在微瓦级。第二段，触发捕获：有声了，环形缓冲记大约 15 秒，唤醒词判断「是不是在叫我」；唤醒词是私有 DTW 模板，纯 JSON，**不是声纹**。第三段，即时蒸馏：SenseVoice 本地转写加情绪分析，只把文本和标签送进记忆，零上云。第四段，即焚：原始音频按 TTL 删除，默认 6 小时。
>
> 本质是：**音频必须短暂落盘才能送 ASR，但原始音频在系统里活不过 TTL；进记忆的是蒸馏产物，不是声音本身。**
>
> 四条红线：录音只由显式 syscall 触发；`LAOS_REC=0` 一票否决全局禁录；每次 mic 调用落审计；ASR 全本地。
>
> 行业里已经有同构路线：STEPX Neo 用六麦阵列加低功耗音频芯片把同一漏斗做进硬件；Apple Watch S12 芯片也被验证过类似路径。laos 的差异是：在没有专用芯片的 Android 环境里，用软件把同一套隐私账算平。

**过渡**：漏斗是隐私哲学的演示；判断层是治理哲学的演示。

## 5.4 四条红线

**讲什么**：把红线再钉一遍。

**逐字稿**：

> 这四条我再重复一遍，因为它们不是功能，是前提：录音只由显式 syscall 触发；`LAOS_REC=0` 全局禁录，一票否决；每次 mic 调用落审计；ASR 全本地，一个字节不出设备。
>
> 一条都不能破。破了任何一条，前面四段漏斗的设计就失去意义。

**收尾/过渡**：设备讲完，最后看判断、证据与工程。

# 第六部分 · 由浅入深（四）：判断、证据与工程（约 6 分钟）

## 6.1 Jev 判断层：只回答结构化问题

**讲什么**：三判型、四闸门、可插拔、0.519/33% 教训。

**逐字稿**：

> 第六环的 Jev 不是「再叫一个大模型聊天」，而是一个结构化判断层。三种判型：Noul 是非，Choice 在 2 到 255 个选项里选，Score 打 2 到 10 级。四个闸门：高危操作预审、记忆写入过滤、上下文压缩选择、技能质量评估。后端可插拔：none、rule、cloud、local，全部过同一接口，换后端不改治理面。
>
> 它不生成解释，只给结论和置信度——因为治理需要的是可比较、可累计、可校准的判断，不是一段可能跑题的文字。
>
> 诚实教训：我们实测过 rule 后端，校准精度 accuracy 只有 0.519，高置信桶错误率高达 33%——越自信越离谱。于是立规矩：**AUTOGATE 禁配 rule 后端，校准先于自动化**。一个会把低质量判断自动放行的系统，比没有判断层更危险。

**过渡**：判断层之外，工程质量靠什么兜底？测试和版本。

## 6.2 测试与版本

**讲什么**：1158、TDD、SemVer、发版自动化。

**逐字稿**：

> 主库 1158 项测试全绿，2026 年 10 月 18 日实跑。TDD，先红后绿，每个任务一个 commit。SemVer 加 Keep a Changelog 加 GitHub Release，一个完整需求波次等于一次 MINOR。发版自动化：主库测试不绿，`release.py` 直接拒绝发版；介绍性文件的版本和测试锚点自动同步。
>
> 这套纪律的意义不是「流程好看」，而是让一个单人项目在 39 个版本之后，仍然能说清每个决定是什么时候、为什么做的。

**过渡**：测试之外，还有一块专门用来复现论文的隔离区。

## 6.3 复现隔离区：能复现的，全部复现

**讲什么**：六来源 71 测试；三个代表数字；方法论四句。

**逐字稿**：

> 论文不是引用，是复现。复现区目前六个来源、71 项测试。
>
> 举三个。BS.1770-4 响度计量：R128 校准点 −23.00 LUFS，误差 ±0.1，True Peak 4 倍过采样。FxLMS 主动降噪：发动机阶次收敛超过 20 分贝，2×2 多通道大约 15 分贝。说话人头部朝向论文全管线：镜像源法加 STFT 相位加 BiGRU-MHSA，冒烟 holdout 56.5 度。
>
> 方法论四句：**TDD、零新依赖、论文数字不作断言、偏差全记档。** 跑不动的等比缩距，并写明偏差。

**过渡**：复现是「做」的证据，调研是「想」的证据。

## 6.4 调研家底与许可证红线

**讲什么**：19,792、9,908、3,724、116；76 是快照；两个红线案例。

**逐字稿**：

> 双会议全量语料：Interspeech 5,507 加 ICASSP 14,285，合计 19,792 篇。多顶会主题切片：35 个 venue，9,908 条。开源仓库普查：3,724 个。调研文档：116 份，每条落成「已落地、推荐、不做」三态。

>
> 两个红线案例。FLASepformer 加 JAEC：能力匹配，但许可证是 CC BY-NC 禁商用，记为驱动侧可选位，不进默认链路。声纹方案：PIPL 把声纹列为敏感个人信息，需要单独同意，全部否决，改为会话内到达顺序聚类，不做跨会话身份库。

**过渡**：最后是合规——有些能力不是「以后再做」，是「不做」。

## 6.5 合规红线

**讲什么**：EU AI Act、PIPL、拒绝伪装采集。

**逐字稿**：

>
> 合规不是功能清单，是设计约束。

# 第七部分 · 回到大图景（约 4 分钟）

## 7.1 laos 的生态位

**讲什么**：L0–L3 再定位；治理语义完整性对比表。

**逐字稿**：

> 把行业图谱再画一次：L0 约定层最多，L1 应用层有 Claude Code 这类，L2 是 laos，L3 是 AIOS 研究和专用 Agent OS。
>
> laos 的差异化不在「更聪明的 Agent」，而在治理语义的完整性。权限：多数框架靠提示词和 Hook，laos 是 caps 加 task_scope，派发前拒绝。预算：多数是 token 计数器，laos 是 EDQUOT 加不可逆计价。审计：多数是日志，laos 是全量流水、可回放。隔离：多数靠容器沙箱，laos 是内核原语加驱动子进程。设备接入：多数是自定义，laos 是 MCP 加 insmod 信任阶梯。

**过渡**：位置清楚了，下一步去哪？

## 7.2 路线图

**讲什么**：近期、中期、远期。
