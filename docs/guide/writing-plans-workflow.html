0 · 一句话论点

计划不是记录，是"写给零上下文执行者的可执行契约"。writing-plans 的每一条苛刻要求——无占位符、2–5 分钟一步、跨 Task 签名逐字一致——都不是文档洁癖，而是对冲同一个风险：执行者（人或子代理）看不到你的脑子，只看纸面。纸面缺一寸，执行就偏一尺。

Skill 是同一范式的另一半：把流程、交付物定义与禁止事项在动手前写死，让模型无法用更便宜的产物交差。文章里那句「不能只给一份目录或几张表格就算完成」，和 writing-plans 的「TBD / 加适当错误处理 = 计划失败」，是同一条规则在两个领域的投影。

学习对象：~/.workbuddy/skills/writing-plans/SKILL.md + plan-document-reviewer-prompt.md；配套技能 executing-plans / subagent-driven-development / finishing-a-development-branch。
关联来源：微信「AI前沿速递」《WorkBuddy + 综述Skill，20 分钟写出一篇投稿级综述》（2026-10-18），其综述 SOP 已沉淀在 docs/research/2026-10-18-litreview-skill-workflow.md，本文不重复、只取同构部分（§7）。

1 · 技能原文拆解：十条硬要求

#条文（技能明文）一句话意图
1Overview：假设工程师对代码库零上下文、判断力可疑；DRY / YAGNI / TDD / 频繁提交计划的读者是"聪明的陌生人"，不是未来的自己
2Scope Check：spec 覆盖多个独立子系统 → 拆成多份计划，每份都能独立产出可测试软件一份计划只解决一个可验收的切面
3File Structure：先定文件与职责，再定 Task；小文件优先；一起改的文件放一起；按职责而非技术层切分分解决策在写代码前锁定
4Task Right-Sizing：Task = 携带自己测试周期、值得单独过评审门的最小单元；setup/配置/脚手架/文档折进需要它的 Task切分点是"评审者可能否决这个而批准相邻那个"
5Bite-Sized：每步 2–5 分钟、一个动作（写失败测试 → 跑它确认红 → 最小实现 → 跑绿 → 提交）粒度小到不可能走神
6Plan Header：Goal / Architecture / Tech Stack / Spec（路径） + Global Constraints + 执行子技能声明spec 随计划同行，计划从 spec 立论
7Task Structure：Files（Create / Modify path:123-145 / Test）+ Interfaces（Consumes / Produces 精确签名） + checkbox 步骤（代码块必给）执行者只见自己那一段，靠 Interfaces 学邻段名字
8No Placeholders：禁 TBD /「加适当错误处理」/「为上述写测试」/「类似 Task N」/ 无代码块的描述性步骤占位符 = 计划失败，不是待办
9Self-Review（自查非派发）：① spec 覆盖 ② 占位符扫描 ③ 类型一致性三查是发布闸门
10Execution Handoff：保存后给用户二选一（Subagent-Driven 推荐 / Inline Execution），各自绑定 REQUIRED SUB-SKILL计划写完不是终点，交接才是
配套评审模板（plan-document-reviewer-prompt.md）给出派发式评审的四维度：Completeness / Spec Alignment / Task Decomposition / Buildability，并附一条校准线——只在"会导致实现期真问题"时才提 issue，否则放行。这条校准线很关键：它把评审员从"文风挑刺"拉回"实现风险"。

失效模式症状被哪条挡住

4 · laos 增量纪律：原技能没有的部分

本仓 docs/superpowers/plans/README.md 已于 2026-10-09 把该技能内化为三条增量纪律，另有三条仓库特有约定：

维度writing-plans 原文laos 增量为什么加
三查#9 自查三项同三项，但明确保存前必跑、不派发子代理派发会把"写计划"变成"等评审"，拖慢节奏
Task 尺寸#4 自带测试周期的最小单元追加：步骤 2–5 分钟，但 Task 不是步骤的机械聚合防止把 40 步拆成 40 个 Task
跨 Task 引用#7 Interfaces追加硬禁令：禁"类似 Task N"，代码块照抄zones/ 并行执行是常态，执行者乱序读
完成度判据checkbox 勾选checkbox 执行时不勾选；判据 = 交付物在 git log --all -- <path> 可证 + 验收清单勾选是自证，git 历史是他证
状态登记无plans/README.md 状态表三值（已执行 / 部分执行 / 待执行）+ 落点摘要50 份计划需要单一状态入口
数值纪律#6 逐字照抄追加：分档左闭右开、数字写实跑值而非静态计数跨文档引用同一阈值时口径必须唯一
一句话概括差异：writing-plans 管"计划怎么写"，本仓纪律管"计划怎么被证伪"。后者补上了原技能的空白——原技能假设执行完就结束，本仓要求三个月后还能用 git 证明做过什么。

5 · 可复用计划骨架（本仓体例，直接抄）

# <功能名> Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 一句话说明构建什么
**Architecture:** 2–3 句说明路径与取舍
**Tech Stack:** 关键技术 / 库（含版本与依赖边界）
**Spec:** `<spec 路径>` —— 计划从 spec 立论，执行者两份都读

## Global Constraints
- 每条一行，数值**逐字照抄 spec**，正文不得改写
- 依赖红线 / 目录纪律 / 既有校验器必须常绿 / 发版锚点不动 …

## File Structure
| 路径 | 职责 |        ← 新增文件在此登记，临时物只进 var/

### Task N: <组件名>
**Files:** Create / Modify `path:行号` / Test
**Interfaces:**
- Consumes: 前序 Task 提供的精确签名
- Produces: 后续 Task 依赖的精确签名与返回类型（逐字符一致）
- [ ] Step 1: 写失败测试（**给完整测试代码**）
- [ ] Step 2: 跑，确认红（给命令 + 期望报错原文）
- [ ] Step 3: 最小实现（给代码，禁止占位符）
- [ ] Step 4: 跑，确认绿
- [ ] Step 5: commit（给 git add 与 commit message）

保存前必跑：spec 覆盖 → 占位符扫描 → 类型一致性。保存后必登记：plans/README.md 状态表加一行（落点摘要 + 状态）。

6 · 三个真实坑（严格按体例也会踩）

2026-10-18 brain 可靠性波实录：计划本身完全合规，实现期仍抓到三个坑——

① 断言漏记收尾轮：脚本 Brain 每次 think 都记账，断言只算了部分序列 → 收尾 done 轮的 temperature 没算进去。
② 计数器生命周期错位：repeat_counts 初始化写在步循环内 → 按步清零、跨步永远到不了阈值 3。规则：计数器的生命周期必须与语义辖域一致。
③ abstract 签名变更的连锁：think 加参后，全仓 def think( 的旧签名 test double 秒崩 TypeError，且崩在轮询断言之前，极难定位。

裁决原则：以 Produces 语义 + 测试意图为准，偏差写进 commit body，不静默改测试。

⚠️ 推论：计划自带的测试代码也会错。所以"跑红 → 跑绿"不只是验证实现，也在验证计划；发现测试本身错了，改测试并说明，而不是把实现改成让错测试通过。

7 · Skill 工程学：writing-plans 与 LitReview 的五处同构

文章把 Skill 定义为「一份给 AI 的任务说明」。把两个技能放在一起看，有效的 Skill 都有同样的五要素：

要素writing-planslit-review（据文章）作用
① 触发条件"有 spec、写代码前""要写综述时"防止在不该用的时候被调用
② 流程前置规定四段头 → File Structure → Task 分解 → 步骤定范围 → 查筛读 → 比较 → 成文不允许模型自己发明顺序
③ 交付物定义完整计划（含代码块的步骤）完整综述 + 参考文献定义质量下限
④ 反降级硬边界禁 TBD / 禁"适当处理" / 禁"类似 Task N"禁只给目录或表格堵住最便宜的交差方式
⑤ 自审与门禁Self-Review 三查未核实内容必须标注让模型自己先过一遍
可用于以后写任何 Skill 的推论：流程与交付物定义决定上限，反降级边界决定下限。只写流程、不写禁止事项的 Skill，模型会用最小代价满足流程——那正是文章里"目录 + 几张表格"的结局。

8 · 计划写作验收清单

写之前

  • 有 spec，且路径写进了 Header；spec 覆盖多个独立子系统 → 已拆成多份计划
  • worktree / 隔离区已就绪（不在 master 上实施）

写之中

  • File Structure 先于 Task 定稿；一起改的文件放一起
  • 每个 Task 自带测试周期；setup / 文档已折进需要它的 Task
  • 每步 2–5 分钟、一个动作、代码块完整（测试步骤必给测试代码）
  • Global Constraints 数值逐字照抄 spec（含左闭右开这类边界写法）
  • Interfaces 的 Produces 与后续 Task 的 Consumes 逐字符一致

写之后（三查 + 登记）

  • spec 每个需求都能指到某个 Task
  • 全文无 TBD / "加适当错误处理" / "为上述写测试" / "类似 Task N"
  • 跨 Task 的函数名、参数、字段名、规则名无漂移
  • 已登记进 plans/README.md 状态表
  • 已向用户给出执行方式二选一并绑定子技能

交付后

  • 每 Task 一 commit，落点可用 git log --oneline --all -- <path> 证明
  • checkbox 保持未勾选（完成度看 git，不看勾）

9 · 边界与诚实声明

  • 适用边界：writing-plans 面向代码实施。调研 / 综述类任务沿用其骨架时，必须额外加「证据等级」与「来源诚实」两栏（本仓做法：核验层级四值 + 未核实清单隔离），否则会产出"看起来完整、实际无法溯源"的产物。
