# 让大模型写出"同事能直接上手"的交接内容 —— 方法框架

> 2026-10-09 · 定位：**通用方法论**（不绑定任何具体项目；例证取自 laos 仓库的真实实践，均为可查证的既有做法）
> 读者：项目所有者——你要用大模型给项目生成交接包，目标是"另一位**通用 SWE 新人**（不熟悉你的领域、工具链与历史决策）只凭交接包 + 仓库就能上手干活"
> 配套：本文件的同名 HTML 版（深色单文件，`llm-handover-methodology.html`）；四个拿来即用的 Prompt 模板在 §5

## 0. 一句话论点

**交接文档的失败不是文采问题，是"知识诅咒"问题**：写的人默认自己脑中的上下文对方也有。大模型恰好在这一点上有杠杆——它可以**零成本扮演零上下文读者**去验收自己写的内容。所以方法的全部要义是：**结构先行、证据锚定、写审分离、可执行验收**，而不是"让模型好好写"。

## 1. 失效模式：为什么大多数交接文档没用

写框架之前先钉死敌人。五种典型失效（按出现频率排）：

| # | 失效模式 | 症状 | 根因 |
|---|---|---|---|
| F1 | 散文式自传 | 讲了项目心路历程，新人还是不知道怎么跑测试 | 没有结构约束，自由写作必然产出叙事 |
| F2 | 隐性知识蒸发 | "环境配好之后很简单"——怎么算配好？代理怎么设？凭据在哪？ | 写的人不知道自己知道（知识诅咒的经典形态） |
| F3 | 过期文档 | 文档说 980 个测试，实际 1016 个；文档说改 A 文件，代码早重构到 B | 没有与代码变更绑定的更新协议 |
| F4 | 指针地狱 | "详见代码"/"详见 wiki"/一串 Jira 链接，没有一处能独立成立 | 把"哪里有信息"当成了"信息本身" |
| F5 | 能跑≠能上手 | 新人照文档把环境跑起来了，然后不知道下一步干什么、什么不能碰 | 只覆盖冷启动，没有日常操作层和红线层 |

**大模型会放大 F1 和 F4**（它极擅长生成流畅的空洞叙事和"详见某处"），所以框架的后半部分全部是用来压制这两种倾向的。

## 2. 交接包的五层信息架构

先给模型骨架，再让它填肉。五层从"活下来"到"能决策"，新人按序消化，每层都有明确的**完成判据**：

| 层 | 回答的问题 | 内容要点 | 完成判据（新人视角） |
|---|---|---|---|
| **L0 生存层** | 这是什么？边界在哪？ | 30 秒电梯陈述；"是 X 不是 Y"的否定式定位；一句话技术栈；仓库顶层目录一句话地图 | 我能向第三个人转述这个项目而不脸红 |
| **L1 冷启动层** | 怎么从零跑起来？ | **一条命令到绿测试**的完整链路（解释器精确到路径与版本、依赖装法、代理/镜像、凭据获取方式、首个 smoke 命令 + 预期输出原文）；平台差异（Windows/WSL/Linux 各自的坑） | 我在一台新机器上只凭此文档让测试全绿 |
| **L2 日常操作层** | 每天的活怎么干？ | 高频任务 cookbook：跑测试（全量/单个）、加一个模块（放哪个目录、命名约定、测试怎么跟）、发版流程、常见报错→原因→解法对照表 | 我知道改任何一类东西前该看哪里、改完怎么验证 |
| **L3 架构与决策层** | 为什么长这样？ | 模块划分图（每模块一句职责 + 依赖方向）；**决策记录**：关键取舍的"当时为什么这么定、被否掉的方案是什么"（ADR 精神——历史决策不解释就会被人'修复'） | 我不会把故意设计的边界当 bug 重写一遍 |
| **L4 治理与红线层** | 什么绝对不能碰？去哪问？ | 红线清单（数据/安全/合规/硬约束，逐条带理由）；谁管什么（模块 ownership）；提问渠道与响应预期 | 我知道哪些"看起来能改"的地方会出事 |

**层间纪律**：L1 的每条命令必须带**预期输出原文**（不是"应该会成功"）；L3 只写"为什么"，"是什么"归代码与 L0 地图；L4 的红线每条必须带违反后果，否则就是口号。

## 3. 让大模型写好的七个手法

这是框架的核心——**你怎么 prompt，决定模型产出的是文档还是散文**：

1. **读者画像显式注入**。在 prompt 开头钉死："读者是通用 SWE 新人：会写代码、会读英文文档，但**不知道**（列出你领域特有的东西——如 Qualcomm/QNN、你们的内部术语、历史事件）。默认读者没有你脑中的任何上下文。" 不注入画像，模型会按"中级同事"水位写，恰好卡在半空。

2. **结构先行，骨架给定**。把 §2 的五层作为模板发给模型，逐层填。自由命题必产 F1。骨架本身是防散文的最强约束。

3. **证据锚定（本框架最重要的一条）**。硬性规则：每个声称必须锚定到可核验证据之一——`file:line`、命令 + 预期输出原文、commit hash、文档路径。**说"配置在 X 文件"必须给出 X 的精确路径与当前值**。模型不知道真实值时会编——所以下一条必不可少。

4. **先取数后写作（反幻觉的关键工序）**。绝不让模型"凭记忆"写交接——流程必须是：模型**先读仓库**（目录树、关键文件、README、git log）产出"事实清单"，人**抽查清单**（尤其数字与路径），确认后才允许进入写作。写作阶段只允许重组清单内的事实，清单外的新声称要显式标注"未核验"。

5. **写审分离（双角色互审）**。写作用的会话 A；验收**必须开新会话 B**（或新代理），B 只拿到交接包 + 仓库，被要求完成指定任务（"把测试跑绿"/"找到 X 配置并解释为什么在这"/"描述模块 Y 的职责边界"）。B 卡住的位置就是文档的缺口。**同一会话自审没有意义**——模型对自己刚写的内容有上下文残留，等于开卷考。

6. **反占位词硬约束**。禁词表：`TBD`、`待补`、`TODO`、`适当处理`、`详见代码`、`略`。可以写一个 10 行的校验脚本扫这些词（laos 的 `table_lint.py`/计划自检就是这么做的）——占位词是 F4 的直接量化指标。

7. **时效标注与单一真相源**。文档头部必须写"基于 commit `<hash>`（<日期>）时刻快照"；凡文档与代码冲突，**以代码为准并回来修文档**。发版/接口变更/目录迁移时更新哪些小节，写成显式清单（laos 发版纪律的"五类锚点"就是这个协议的实例——`release.py --apply` 机器同步，人只做 CHANGELOG）。

## 4. 验收：怎么证明"能直接上手"

**文档质量的最终度量是行为，不是观感。**冒烟式验收（对应手法 5）：

1. 选 3–5 个"新人第一周会做的真实任务"（跑绿测试 / 定位某配置 / 解释某决策 / 做一个小改动并验证 / 找到红线并说出后果）；
2. 让零上下文的模型（或真人）只凭交接包执行；
3. 记录每次卡壳：卡在哪一步、缺什么信息、文档哪句误导了；
4. 修文档，换一批任务重测，直到连续一轮零卡壳。

**五问速查**（人工 10 分钟版）：新人能否①用一句话说清项目边界？②说出跑测试的精确命令与预期数字？③指出"最容易被误改"的三个地方？④解释最重要的一个历史决策（为什么否掉备选）？⑤知道出问题先去问谁/查哪？——五个都能，L0–L4 才算闭环。

## 5. Prompt 模板集（拿来即用）

**模板 A · 交接包生成（骨架 + 证据锚定）**

```
你是资深工程师，为项目写交接包。读者：通用 SWE 新人（会写代码，但不知道
<领域特有概念清单>，没有本仓库与团队的任何历史上下文）。

工序（严格按序，不得跳步）：
1. 先读仓库：目录树、README、git log 最近 30 条、<指定的关键文件清单>；
   产出【事实清单】——只列你实际读到的东西，每条带 file:line 或命令输出
   原文。禁止写入清单外的事实。
2. 停下，把事实清单给我抽查。
3. 抽查通过后，按以下五层骨架写作：
   L0 生存层（30秒定位+目录地图）/
   L1 冷启动层（一条命令到绿测试：解释器精确路径、依赖、代理、凭据、
     smoke 命令+预期输出原文、平台差异坑）/
   L2 日常操作层（跑测试/加模块/发版/常见错→解法表）/
   L3 架构决策层（模块职责+依赖方向；每个关键决策写"为什么这么定、
     否掉了什么"）/
   L4 治理红线层（红线逐条带后果；ownership；去哪问）。
4. 硬约束：禁 TBD/待补/详见代码/适当处理；每个配置项给精确路径与当前值；
   文档头部写"基于 commit <hash> 快照"；你不确定的写"未核验"并注明
   核验方法。
```

**模板 B · 零上下文验收员**

```
你是一名刚入职的通用 SWE，只拿到一个仓库和一份交接文档，没有任何其他
上下文。按文档完成以下任务，禁止阅读文档未提及之外的资料：
<任务 1：让测试套件全绿>
<任务 2：定位 X 配置，解释它为什么在这个位置>
<任务 3：描述模块 Y 的职责边界与依赖方向>
每完成一步记录：卡壳点（文档缺什么/哪句误导）→ 你是怎么绕过的。
最后输出缺口清单（文档应补的内容，逐条定位到五层中的某一层）。
```

**模板 C · 缺口分析（文档 vs 代码双向 diff）**

```
读仓库与交接文档，输出两张表：
①文档说了但代码已不是这样（过期项，给 file:line 证据与 git log 佐证）；
②代码里有但文档从未提及、且新人第一周大概率会撞上的（隐性知识项——
重点扫：环境坑、隐式约定、命名规则、"看起来能改其实不能"的地方）。
每条标层（L0–L4）与优先级。
```

**模板 D · 时效审计**

```
对照 git log（自 <基线 commit> 以来）逐条检查交接文档：
哪些小节描述的东西被这些提交改动了？给出"提交→受影响小节→应改成什么"
的修订表。凡数字（测试数/版本号/文件数）一律以当前实跑为准重新核对。
```

## 6. 反模式清单（见了就打回）

- ❌ 心路历程式开场（"项目从 X 月开始，我们经历了……"）——历史只保留**决策**，不保留**情绪**
- ❌ 贴一张架构图不解释（图不自带语义，每条边都要有文字）
- ❌ "详见代码 / 详见 wiki / 详见 Jira"（F4；文档每一节必须能独立成立）
- ❌ 把模型生成的"合理推测"当事实写入（必须走 §3-4 的先取数后写作）
- ❌ 一次写完永不更新（必须配 §3-7 的更新协议与快照标注）
- ❌ 用同一会话写完自查（必须新会话验收，§3-5）
- ❌ 红线只写"注意安全"（每条红线带**违反后果**与**真实例子**）

## 7. 与本仓库实践的对照（例证，均可查证）

- **跨会话记忆**：`AGENTS.md`——交接包 L4/治理层的活体实例（红线+纪律+口径，代理开工前必读）
- **证据锚定与 Run/Expected 模式**：`docs/superpowers/plans/*.md` 的每个步骤都是"命令 + 预期输出原文"——L1/L2 的标准写法
- **时效快照注记**：计划头部"生成于 `<commit>` 时刻快照，执行时以实跑为准"——§3-7 的实例
- **机器同步锚点**：`scripts/release.py --apply` 把版本/测试数五类锚点在发版时机器化同步——"文档更新协议"从纪律上升为工具的范例
- **占位词拦截**：`scripts/table_lint.py` 对 `待补/TBD` 的校验——§3-6 的脚本化实例
- **写审分离**：subagent-driven-development 的"任务审查者实跑复现"——§4 冒烟验收的流程化版本

*本框架按自身标准交付：头部带日期与定位（快照语义）、五层骨架自洽、例证全部锚定到仓库既有文件、无占位词。HTML 版为同内容深色单文件零依赖。*
