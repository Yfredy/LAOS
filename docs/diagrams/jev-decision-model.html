1技术实质

System One：不生成文本的决策模型

TypeSafe AI 的 System One（对标 Kahneman 快慢分工中的「快系统」）。transformer-based，但不生成文本——非自回归 + 并行采样器。训练方法 RLCD（Reinforcement Learning for Calibrated Decisions，对标 RLHF）。

与「小 LLM」的本质区别不是参数量，而是输出空间在推理前就被定义。 LLM 从整个词表采样；Jev 从调用方给定的候选集里选。

三个原语

裁定 J6：Noul 无独立 confidence，laos 落点不得自行补该字段。

confidence 的语义（最容易讲错的一点）

confidence 来自概率分布形状，不是胜出选项的概率。

官方示例：billing 拿到 0.84（最高），但 confidence 只有 0.596——因为 technical 仍占 0.159，分布不够"尖"。

置信档处置说明
高自动执行分布足够尖
中入复核队列次优选项仍有分量
低转人工阈值按错判代价缩放

4端侧可行性（实测，非 README）

yzfly/edgejev — 跑通ONNX int8 · 运行时不依赖 torch
wfzyx/von — 否决torch + 1.5 GB 权重，手机装不下
laya-rust — 否决需 cargo 编译，峰值 RAM 2.4 GB

edgejev 实测数字（本机 x86，AMD Zen 3）

指标实测值备注
首次加载2144 ms加载 324 MB ONNX + 初始化会话；不能频繁启停
median 延迟157.5 ms3 题齐发，单 forward pass（单题约 80–130 ms）
p95 延迟233.1 ms同上
峰值 RSS494.8 MB含 324 MB 模型驻留
模型目录358.9 MBmodel.onnx 324.5 MB + tokenizer 34.4 MB
README 宣称的 15.6 ms 被否证 —— 实测慢约 10×
✅ 模型体积 324 MB 一致　✅ 运行时无 torch 一致　❌ 延迟不一致
15.6 ms 是在 4 vCPU Intel Xeon Cascade Lake（AVX512-VNNI） 上测的硬件特例；本机 AMD Zen 3 无 AVX512-VNNI，int8 只能走 AVX2。裁定 J7：README 的 15.6 ms 不得在落点代价中引用。

外推到 proot aarch64（量级估计，无可靠系数）

假设：aarch64 上 onnxruntime int8 走 SDOT（优于 x86 AVX2），但手机 Cortex-A 核心更弱、核数更少 → 净延迟不确定。x86 → aarch64 没有可靠换算系数，以上只是量级估计。

一句话结论：端侧现在能跑 yzfly/edgejev（ONNX int8，359 MB，onnxruntime，无 torch），但延迟比 README 慢约 10×，且须先在构建机用 torch 跑 edgejev build 才能拿到权重——只够漏斗③蒸馏，不够漏斗①常驻。

落地顺序 P0–P4

优先级落点原语理由
P0上下文压缩(8) + 记忆召回精排(4)Noul / Score均离线非实时，不碰常驻每帧路径；157.5 ms/批、每天数百次 → 常摊 4.6 mW；压缩钩子骨架已就位，落地成本最低
P1蒸馏重要度(2) + 记忆类别路由(3)Score / Choice漏斗③蒸馏后触发（非每帧）；共享同一常驻 session，加题不增延迟

P3记忆半衰期分档(5) + 技能路由(7)Score / Choice半衰期需重构 recall 的 recency 项（中改动）
P4Brain 路由(9)Choice改动最大、收益边际
否决漏斗①常驻(1)Noul（两级）纯每帧调用不可行（0.5–1.5 W）；两级结构可行但属实时触发路径，须先在 proot aarch64 实测功耗后评估

映射分布：Choice × 3（类别路由 / 技能路由 / Brain 路由）· Score × 4（重要度 / 召回精排 / 半衰期 / 不可逆闸门）· Noul × 2（触发 / 压缩）。

laos/judge.py 四个后端：RuleBackend（规则兜底）/ CloudBackend（TypeSafe API）/ LocalBackend（LAOS_JEV_ENDPOINT）/ SafeJudge（异常降级）。

✅ 值得肯定：默认不走云端

def select() -> JudgeBackend:
    want = os.environ.get("LAOS_JEV_BACKEND", "none").strip().lower()
    if want == "cloud":  return CloudBackend()
    if want == "local":  return LocalBackend()
    return RuleBackend()   # none | rule | 未知值 → 零依赖兜底

默认 none → RuleBackend()，零依赖、零网络；云端必须显式设环境变量才启用。这与「中国大陆未开放 + 本地优先」的硬约束不冲突。SafeJudge 也在异常时 fail-open 回落既有行为。

⚠ 必须点名：LocalBackend 与实测唯一的端侧候选接口不匹配

LocalBackend 是 OpenAI 兼容 HTTP 端点：{endpoint}/v1/chat/completions，把整体载荷 JSON.stringify 成 user 消息，再从生成结果里解析 {"verdict":..., "confidence":...}。

而本次实测唯一跑通的 yzfly/edgejev 是 进程内 ONNX 直推（system_one(questions) → 单次 forward pass），不是 HTTP 服务。

三个后果：
  • 要接 edgejev，须先写一个 OpenAI 兼容的 HTTP shim，额外工程量 + 引入常驻 HTTP 服务。
  • 更本质：走 chat completions = 从生成结果解析 JSON verdict，这是 §3b 里「复现(单token打分)」那一类的形态，不是真非自回归决策头 → 延迟是生成式绑定的，拿不到实测的 157.5 ms。
  • LocalBackend docstring 写的是「NanoJev/simple-jev」——这两个没有一个被本次实测验证过端侧可跑。
建议：若要真正吃到 edgejev 的 157.5 ms，应新增一个 OnnxBackend（进程内直推），而不是把它塞进 LocalBackend 的 HTTP 契约里。
