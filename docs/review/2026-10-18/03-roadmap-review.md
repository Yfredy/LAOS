## 4. 版本节奏

| 规则 | 内容 |
|---|---|
| minor = 波次 | 每个 minor 对应一个可演示的能力波，必须有退出标准 |
| patch = 修复 | 只修缺陷与锚点，不夹带新能力 |
| 发版门禁 | `release.py --apply` 真跑测试，不绿拒绝发版；锚点自动同步；CHANGELOG 人工插入 |
| 归档 | 每版 `docs/releases/` 一文件 + `gen_release_notes.py` 对齐 |
| 节奏建议 | 一个 minor 至少间隔一个完整评审/回归周期；避免同日多 minor 叠加导致计数与文档漂移 |

**近期版本建议**：

| 版本 | 内容 | 前置 |
|---|---|---|
| v0.40.0 | M-02 + M-03（A/D）+ 计数/文档锚点归零 | 本场评审通过 |
| v0.41.0 | M-04（屏幕语义）+ M-06（B/C） | Q-05 冻结；M-05 启动 |
| v0.42.0 | M-05 长跑结论 + M-09 记忆分层 | 7 天 soak 完成 |
| v0.43+ | M-07/M-08（硬件前提满足后） | KWS/TTS/真机验收 |

## 5. 资源与约束

| 约束 | 内容 | 对路线的影响 |
|---|---|---|
| 人力 | 单人主线开发 + 代理协助 | WIP=1；硬件依赖项不能与软件波并行 |
| 依赖 | 核心零第三方依赖；重依赖只在驱动子进程 | 说话人分离默认走 stdlib；模型接入必须证明不可替代 |
| 模型体量 | 常驻链路 ~50MB 上限（含推理内存） | CAM++ 类可常驻；Sortformer 只做离线后处理 |
| 硬件 | KWS/Android/ADSP 需真机 | M-07/M-08 不先排日期，排“验收条件” |
| 环境 | Windows 开发 + Linux 完整形态 | 强制层相关验收必须在 Linux 跑 |
| 文档 | 发版必须同步全部介绍面 | 每个 minor 预留文档与归档时间 |

## 6. 路线风险

| ID | 风险 | 影响 | 缓解 |
|---|---|---|---|
| **RR-01** | 多波并行导致半成品堆积 | 质量与文档漂移 | WIP=1；未达退出标准不开发下一波 |
| **RR-02** | 硬件依赖阻塞主线 | 路线停摆 | 软件波与硬件验收解耦；硬件项只设验收门槛 |
| **RR-03** | 计数/锚点漂移（CHANGELOG v0.39.0 写 1158=发版时点正确值；当日 +22 未发版回归后门禁实跑 1180） | 评审材料不可信 | 实跑为准（1180）；两档口径已确立：介绍面持发版时点 1158、ONBOARDING 持门禁实跑 1180，差 +22 待下次发版由 release.py 统一刷新；发版链继续强制同步 |
| **RR-04** | 模型接入压力突破零依赖红线 | 供应链与可移植性受损 | 50MB 红线；模型只进驱动子进程；默认关闭 |
| **RR-05** | 长跑验收后置 | 上线后才发现慢泄漏 | M-05 提前到近期，作为后续波的基线 |
| **RR-06** | 单人 bus factor | 交接风险 | 评审包 + ONBOARDING 门禁 + 计划状态登记 |
