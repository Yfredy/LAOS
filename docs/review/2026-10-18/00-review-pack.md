## 2. 会议议程（90 分钟标准场）

| 时段 | 议程 | 产出 |
|---|---|---|
| 0–5 min | 定位与边界重申（每次必讲，防止评审跑偏成产品愿景会） | 无异议记录 |
| 5–35 min | 需求评审：逐条过 Must/Should/Won't，处理 Q-01…Q-08 | 需求结论 + 条件清单 |
| 35–75 min | 技术评审：架构、契约、威胁模型、风险债务，处理 ADR 分歧 | 技术结论 + 必须闭环项 |
| 75–90 min | 路线评审：确认下一波、里程碑退出标准、资源前提 | 路线结论 + 责任人与时间盒 |

**主持规则**：每个议题只允许两类发言——「有证据的反对」与「可执行的修正」。没有证据的偏好可以记录，但不占用决议时间。

## 3. 决议规则

| 结论 | 定义 | 后续动作 |
|---|---|---|
| **通过** | 无阻塞项；条件项可并行处理 | 进入下一阶段 |
| **有条件通过** | 存在阻塞项，但已有明确闭环方案与责任人 | 条件未闭环前不得宣称通过 |
| **不通过** | 存在无法在当前范围/资源内闭环的阻塞项 | 回到需求或架构层重做，不进入排期 |

- 阻塞项必须写成「**现象 + 证据 + 验收标准 + 责任人 + 时间盒**」五元组，否则不算阻塞项，只算意见。
- 任何「不是缺陷」「风险可控」的结论必须有实测或代码证据；口头判断不进入决议。
- 评审结论只认文档里的勾选与签署，不认会后的口头补充。

## 5. 三场评审的共同前提

1. **定位红线**：基座是 Linux 内核，Agent 是新负载（与进程同类），laos 是内核治理在用户态的延伸。禁止「给 AI Agent 装上操作系统」类主客反转表述。
2. **品牌口径**：对外 nanoLAOS；技术名/仓库名/包名 `laos`、CLI 名 `laosctl`/`laosd`/`laosweb`、`LAOS_*` 环境变量不变。
3. **隐私红线**：录音只由显式 syscall 触发；`LAOS_REC=0` 全局禁录；ASR 全本地；原始音频 TTL 即焚。
4. **依赖红线**：`laos/` 核心纯标准库；任何新依赖提案默认不通过，除非先证明无法用标准库实现。
5. **证据纪律**：评审材料里的每个数字都要能指到代码、测试或调研文档；指不到的数字降级为「待核实」。
