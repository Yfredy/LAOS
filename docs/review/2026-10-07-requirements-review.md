# laos 上线前需求评审（2026-10-07）

> **评审对象**：laos v0.19.0（主库 691 项测试实跑通过；页脚总数 1041 = 主库 691 + 隔离区 279 + 复现区 71）。
> **定位重申（叙事红线）**：基座是 Linux 内核，Agent 是内核之上的新负载（与进程同类）；laos 是内核治理在用户态的延伸，不是"给 AI Agent 装上操作系统"。
> **数字口径**：本文全部性能数字取自仓库既有实测（计划事实基线 + README + 引用调研文档），未实测维度一律明写"未实测"，不引入外部宣称值。
> **本文角色**：本评审是《埋点设计》（docs/design/2026-10-07-instrumentation-design.md，Task 3）的需求源头；§6 问题域清单编号冻结（P01…），Task 3 诊断矩阵逐条消费。

## §1 评审范围与"上线"定义

### 1.1 laos 的三类目标形态

| # | 形态 | 内容 | 服务对象 |
|---|---|---|---|
| 1 | **端侧常开录音研究平台** | 四段漏斗（VAD 常驻检测 → 触发捕获 → 即时蒸馏 → 原音频即焚）+ 三通道 ASR + 语料/评测研究资产 | 开发者本人 |
| 2 | **Agent 治理语义层** | Linux 内核之上的用户态治理：能力表 / syscall 审计 / 不可逆预算 / 分支 / 记忆，把 Agent 当新负载管起来 | 引用 laos 内核库的开发者 |
| 3 | **对话控制面组件库** | WakeGate / dialogsched / knowledge / speechchunk / turnpolicy / turnbuf 等可复用组件（v0.17.0 语义复现波次） | 组装语音对话系统的开发者 |

### 1.2 "上线"定义（本评审口径）

**第一场景 = 开发者自部署上线**：开发者在自己的机器（Linux 桌面/服务器为完整形态；Windows/macOS 自动降级为"仅能力表"）克隆仓库、跑通 691 项测试、按 README 启动 `laosd` / `laosweb` / `journal` 管线并日常使用。

**明确非目标（不承诺）**：

- **无对外 SaaS 承诺**：laos 不提供托管服务、无 SLA、不做云端默认上传（ASR 全本地是红线，见 §4.3）；
- **不做多租户**（Won't，见 §3）；
- 不做面向终端消费者的合规认证——隐私按仓库既有红线纪律执行；
- 不修改 Linux 内核（用户态延伸，非新内核）。

三类形态共享同一套 Go/No-Go 门槛（§5）；形态 2/3 的"被第三方引用"额外依赖接口契约冻结度，属技术评审（Task 2）范围。

## §2 用户画像与核心场景

**用户画像**：P1 自部署开发者（第一场景用户：在自己的机器上跑 laos 并日常使用听觉/对话/治理能力）；P2 Agent 治理研究者（引用能力表/审计/预算语义做多 Agent 实验）；P3 语音/语料研究者（消费调研语料与评测工具链）。

### 2.1 核心场景表（用户动作 → 系统行为 → 完成度）

| 场景 | 用户动作 → 系统行为 | 完成度 |
|---|---|---|
| **S1 常开录音日记** | 开发者显式触发录音 syscall → StreamingVAD 门控（仅"有没有人声"一比特，静音不落盘）→ 捕获有人声片段 → funasr/SenseVoice 转写+情感 → journal 入库（mem.remember）→ diary/mood_report 聚合 → rec_gc 6 小时即焚原音频 | **✅ 完整**（漏斗四段全落地，真录音/真 ASR 用例实测；说话人分离缺位为增强项，不阻塞） |
| **S2 语音问答**（唤醒→识别→知识库/LLM→TTS） | 说唤醒词 → KWS 音频触发 WakeGate 四态会话（文本永不唤醒）→ 三通道 ASR 识别 → knowledge bigram 短路（阈值 0.58）或 LLM 流式 → speechchunk 切句清洗 → TTS 合成播报；抢话时 generation 版本化打断（过期代宁可丢不可播） | **◐ 部分**：WakeGate 会话机 ✅（有模块有测试，无 KWS 实测触发）、三通道 ASR ✅、知识库短路 ✅、refiner ✅、打断 ✅；**TTS 合成 ○（laos 尚无 TTS 能力面，TtsRouter 只是路由/降级语义）**——端到端闭环未成 |
| **S3 Agent 治理审计** | 起 Agent 干活 → 每次 tool call = 一条带 errno 的 syscall 审计（含被拒路径）→ laosctl ps/trace/denied/budget/spans 回放；eBPF 内核真值 + AgentProf 语义 span | **✅ 完整**（审计流 + 内核真值 + 语义剖析三层齐备） |
| **S4 语料研究** | 检索/评测 → 120,234 行 38 venue 调研语料 + AASR-Bench 917 例 refiner 评测 + WER 工具链 | **✅ 完整**（语料资产 + 评测管线可用） |

### 2.2 场景支撑能力完成度分解（与仓库实际一致）

| 能力 | 完成度 | 依据 |
|---|---|---|

| Refiner | ✅ | AASR-Bench 917 例错误率 0.4571→0.3875（**-15.2%**）；端到端（TTS 口吃语音→funasr→refiner）CER 1.563→0.042；已知局限=子句级替换型 |
| 唤醒会话机（WakeGate） | ✅ 模块级 | `laos/wakegate.py` 四态（follow-up 12s / 会话 120s / 6 轮），12 例测试全迁移路径覆盖；**无 KWS 真机实测**（见下行） |

| 打断（generation 版本化） | ✅ | `laos/dialogsched.py` 23 例测试（代数/合并/latest-only/降级不换声线，实跑核对 2026-10-07） |

| 审计 | ✅ | 每次 syscall 带 errno 审计；录音成功**与被拒**均写 `event:"mic"` |

| 知识库检索 | ✅ | `laos/knowledge.py` bigram 检索（0.7/0.3 双向覆盖+子串=1.0+交集≥2+阈值闸），11 例测试含上游真数据 fixture |

## §4 非功能需求

### 4.1 延迟预算表（对照 voicenpu 上游 RK3576 实测；laos 未实测处如实标注）

| 链路段 | 上游 voicenpu（RK3576 实测，对照锚点） | laos v0.19.0 现状 |
|---|---|---|
| 唤醒触发（KWS→会话开） | sherpa-onnx zipformer 3.3M 在链路内 | **未实测**（KWS 模型/词表已拿到，真音频触发未跑，◐） |
| ASR 端点→终稿 | ~88ms | **未实测** |
| ASR 流式首字 ttft | （流式 Zipformer RKNN，未单列） | whistle 通道 **651ms 实测**（~300 tok/s）；funasr 通道非流式 |
| ASR 精度（参考口径） | wenetspeech 3.3M transducer | funasr en WER 2.7% / zh CER 0.0%；whistle en WER 10.8%（实测） |
| Refiner 修正延迟 | — | **未实测**（现有口径为精度：错误率 -15.2%、e2e CER 1.563→0.042） |
| 知识库检索 | retrieval_ms 记入指标 | **未实测**（本地 JSONL bigram 检索） |
| LLM 首 token | RKLLM Qwen3-VL-2B w4a16 | **未实测**（laos 无常驻 LLM 通道；brain 可接 OpenAI 兼容端点） |
| TTS 首音 | 在线豆包 / 离线 MeloTTS | **无此段**（TTS 能力面 ○） |
| 端到端首音 | **1.44s** | **未实测** |
| 抢话保护 | AEC ready 后启用 barge-in；无 AEC 时播报期间+400ms 锁麦 | MicrophoneGate guard **400ms**（设计值，dialogsched） |
| 判断层 | — | edgejev 端侧 **median 157.5ms 实测**（README 宣称 15.6ms 已被实测否证） |
| 常驻内存 | 1951MB | **未实测** |

**结论**：laos 当前只有片段级实测（whistle ttft、jev median、WER/CER 精度、refiner 精度），**端到端延迟全线未实测**——上线后"为什么慢/是否劣化"（→P04）目前无数据可答。这是埋点设计（Task 3）的核心动机之一。

### 4.2 功耗预算（引 always-on-recording 调研口径）

"常开"是跨 4 个数量级的功耗阶梯（docs/research/always-on-recording/hardware-power.md）：

| 阶梯 | 量级 | 例证 |
|---|---|---|
| 定制 ASIC | 亚 µW（0.047–1 µW） | VAD ASIC 47 nW；AAD 门控 KWS 0.36–0.8 µW |
| 专用音频 NPU | 百 µW | Syntiant NDP120 always-on 140 µW |
| 手机传感中枢 / aDSP | 数 mW | 高通官方口径 Sensing Hub 全部处理 <1 mA；laos 真机目标 ADSP LPAI **<5 mW（≈0.62%/天）** |
| 通用 AP 常醒 | 数百 mW–瓦 | 跑通用 Linux 的机器**空闲即 400–1000 mW** |

**对第一场景的判定**：

1. **工程准入线**：常开能力 ≤25 mW（≈3%/天）；进入 100 mW 量级即一天吃掉 1/4 电，用户会立刻关掉。
2. **落盘比"听"贵 1–2 个数量级**（听 ≤25 mW vs 写 SD 17–70 mW）——四段漏斗"只存有声段"同时是最大的省电措施，不只是隐私设计。
3. **桌面/proot 形态的移动常开不成立**（Python 进程醒着就在数百 mW 量级）：第一场景的常开形态定位为**台式供电的研究平台**；移动常开走原生 App + ADSP 路线，不在本评审门槛内。

### 4.3 隐私合规（红线逐条）

| # | 红线 | 落法 |
|---|---|---|
| 1 | 录音只由显式 syscall 触发 | `drv_rec.rec_start` / App `/rec/*`；无后台静默录音路径 |
| 2 | `LAOS_REC=0` 全局禁录 | 返回 EACCES，一键关闭 |
| 3 | ASR 全本地 | funasr/whistle 本机推理；server 通道默认 127.0.0.1 端点 |
| 4 | 录音成功**与被拒**都写审计 | `event:"mic"`（放行/拒绝两路径） |
| 5 | 原音频即焚 | `rec_gc(keep_hours=6)`——即使前环被滥用，原始音频最多活 6 小时 |
| 6 | 标识信息脱敏 | `LAOS_PRIVACY_MASK=1`（主机名等） |
| 7 | 埋点约束（为 Task 3 预立） | 埋点默认**不采集音频内容与转写文本明文**；内容类只允许长度/哈希/计数/时长等脱敏字段；埋点挂既有审计流（`event:"mic"` 联动），**不开新后道**；`LAOS_REC=0` 时音频内容类埋点同步静默 |

## §6 上线后问题域清单（编号冻结：P01–P15）

> 本清单是 Task 3《埋点设计》诊断矩阵的需求源头，**编号冻结**：Task 3 逐条映射埋点字段；后续新增问题顺延 P16+，不得复用已冻结编号。每条给"用户视角症状 → 系统面候选成因 → 现有观测点"。

| 编号 | 问题域 | 用户视角症状 | 系统面候选成因 | 现有观测点 |
|---|---|---|---|---|
| **P01** | 唤醒不灵 | 喊唤醒词没反应，会话开不起来 | KWS 漏唤醒（阈值/词表不匹配）、音频前端未起、WakeGate 状态机在非 idle 态 | WakeGate 状态可注入时钟测试；真音频路径无事件 |
| **P02** | 误唤醒 | 没叫它却自己醒（电视/他人对话触发） | KWS 假阳性、易混词命中（负样本生成器已备但未接入）、VAD 灵敏度 | 无事件记录误触发 |
| **P03** | ASR 误识别劣化 | 转写越来越错（专名错、方言错、CER 上升） | 模型加载错版本、通道误切（funasr↔whistle↔server）、音频前端增益漂移、refiner 回归 | 精度仅有离线评测口径（AASR-Bench/WER），线上无逐轮记录 |
| **P04** | 端到端延迟劣化 | 对话越来越卡、首音变慢 | 某段延迟膨胀（检索/LLM/ASR）、系统负载、投机窗判定退化 | **全线未实测**（§4.1），无任何分段数据 |
| **P05** | 打断失效（过期代播放） | 已经抢话了，它还在播旧回答 | generation 代数核对缺失路径、TTS 队列未清空、turnpolicy 与 GenerationGate 未组合 | dialogsched 有代数语义与测试；线上无打断成败事件 |
| **P06** | 会话异常（超时/轮数提前睡） | 还在聊着呢它突然睡了 | follow-up 12s / 会话 120s / 6 轮边界误判、时钟注入错误、休眠词误命中 | WakeGate 测试覆盖边界；线上无状态迁移事件 |
| **P07** | TTS 降级频繁 | 声线突变/播报失败/降级到不说话 | 在线通道失败率高（豆包 wss）、降级路由抖动、句中换声线保护触发 | TtsRouter 降级语义有测试；线上无降级事件（TTS 落地后生效） |
| **P08** | 模型加载失败 | 启动报错或某通道静默不可用 | SenseVoice/whistle 模型路径缺失、conda 解释器探测失败（LAOS_EAR_PYTHON）、磁盘满 | 驱动 status 工具可查；无 load 失败事件 |
| **P09** | 音频设备断连 | 麦克风/声卡拔掉后链路死掉 | USB ENODEV、ALSA EPIPE/ESTRPIPE/EIO——上游有自愈语义（close+200ms 重开循环），laos 未接 | 无设备事件；上游自愈语义已在文档记录 |
| **P10** | 内存增长 | 跑几天越来越胖直至 OOM | 审计/记忆 JSONL 无界增长、队列积压、上下文 swap 失效——上游常驻 1951MB 对照 | 无 RSS 采样事件 |
| **P11** | 崩溃后恢复 | laosd/驱动子进程 crash 后状态不一致、录音开关态丢失 | 崩溃时审计 flush 缺失、驱动子进程重启后注册表漂移 | 审计为追加式 JSONL；无崩溃/恢复事件 |
| **P12** | 审计缺失 | 某次调用/录音查不到记录（红线级） | 审计写入路径异常、异常吞掉审计、errno 被包成 EIO 类问题复发 | 审计流存在但无"应记未记"的自证机制 |
| **P13** | `LAOS_REC=0` 旁路 | 禁录开关下仍有录音行为（红线级） | 检查点遗漏路径、驱动子进程未继承环境、新驱动绕过闸门 | `event:"mic"` 记被拒路径；无禁录态全局断言 |
| **P14** | 投机取消风暴 | 回答变慢且 token 消耗异常 spike | resume 判定过敏（≥96ms×16 采样误判）→投机轮反复启动又取消——上游有 speculative_tokens_wasted 指标口径 | laos 未实现该指标（Task 3 吸收） |
| **P15** | 音频队列 overrun 风暴 | 识别断续、丢字 | 生产>消费→SPSC 队列 overrun→清队列+reset ASR 循环反复触发（上游 overrun 自愈语义的副作用） | 无 overrun 计数事件 |

**清单口径说明**：P01–P13 为计划既定 13 类；P14/P15 为评审补充（上游 metrics 已有对应字段口径：speculative_tokens_wasted、队列自愈语义），一并冻结。

## §7 需求评审结论

### 7.1 TOP5 风险

| # | 风险 | 依据 |
|---|---|---|
| R1 | **端到端延迟全线未实测**——上线后无法回答"为什么慢/是否劣化" | §4.1：对照上游 1.44s 首音锚点，laos 侧无任何端到端数字（→P04） |
| R2 | **唤醒链路未实测**（KWS ◐）——语音问答第一环就是断的 | §2.2：WakeGate 模块级 ✅ 但真音频触发未跑（→P01/P02） |
| R3 | **TTS 能力面缺失**——语音问答闭环缺最后一环 | §2.2：TTS ○，S2 场景只能降级形态上线（→P07） |
| R4 | **上线后问题诊断无观测面**——只有 JSONL 审计，无分段延迟/降级/故障事件 | §5 G8：P01–P15 大半无数据可定位 |
| R5 | **半双工且无 AEC**——抢话体验受 400ms guard 约束，与全双工标杆有代差 | §4.1：MicrophoneGate guard 400ms；AEC 音频合同仅入档（Could C1） |

### 7.2 TOP3 放大器（让风险变贵的机制）

| # | 放大器 | 作用机制 |
|---|---|---|
| A1 | **埋点缺失**（本波 Task 3 的对象） | 任何问题的定位时间放大 N 倍：用户只能报"不好用"，开发者只能靠复现；分段归因不可能 |
| A2 | **三棵树同步漂移**（主库/隔离区/复现区） | 版本或计数漂移→文档宣称与实际行为不符→问题报告不可信 |
| A3 | **长时运行无巡检** | 常开场景 7×24 无人值守，慢泄漏/慢劣化（P10/P04）无人发现，直到用户侧爆发 |

### 7.3 结论

以**开发者自部署研究平台**形态（S1 常开录音日记 / S3 治理审计 / S4 语料研究），laos **满足上线门槛**；**语音问答（S2）按降级形态上线**（KWS 实测与 TTS 落地前不承诺完整体验）；**上线后最大短板=可观测性**——本波埋点设计（Task 3）以 §6 的 15 条问题域（P01–P15，编号冻结）为需求源头，事件设计须继承 §4.3 第 7 条的隐私红线约束。
